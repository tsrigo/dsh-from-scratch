# Nano DSH 内容候选

## 1. 筛选目标

Nano DSH 是一个原创的 TypeScript 教学实现，并配套交互式教学网站。它不追求完整复刻 DeepSeek Harness（DSH），只保留少量能够解释 DSH 核心设计、又值得读者了解的内容。

本文件把先前确定的五项教程骨架与新筛出的社区问题合并。重复内容只保留一个位置，并按教学顺序重新排列：

- “从 Agent Loop 到 Harness”与 Agent Loop、LLM 输入和工具执行合并为 M01。
- 上下文组织与 Prompt Cache 前移为 M02。
- 插件内核、会话日志和自修改依次为 M03–M05。
- 长程任务后移为 M06，是否进入首版继续由贯穿任务筛选。
- Code Mode 与工具结果裁剪不单独成为章节。

上游 `../deepseek-harness/` 只作设计参考，不复制源码；`pi-from-scratch` 只作教学形式参考。安全、权限、审批和沙箱不进入 Nano DSH。

## 2. 演示策略

首版已经放弃“六章共用一个业务任务”的约束。强行让购物车任务同时承担上下文、插件、事件日志、自适应和长程续行，会让业务细节盖过机制本身。六章改用彼此独立的最小样本，只要求概念关系连续：Loop 产生历史，上下文投影历史，插件管理能力变化，Session Log 记录过程，运行时工具开放受控变更，Goal 再把同一目标带到下一轮。

完整购物车任务只保留为独立静态回放，不进入章节讲解。章节右侧的请求、事件和能力图属于机制样本，不宣称与历史 checkpoint 源码来自同一次执行；源码与样本共同证明的是同一设计关系。

## 3. 调整后的章节候选

### M01 从 Agent Loop 到 Harness

**核心问题：Agent Loop 已经能工作，为什么还需要 DSH？**

从最小的“调用模型—执行工具—继续调用”循环开始。本章的落地问题仍是：**在 DSH 中，模型是怎么执行工具的？**

- 每次模型请求包含 system prompt、当前历史、tool schemas 和实际使用的动态上下文。
- 一个 turn 表示一次用户任务；一个 step 表示一次模型请求及其工具结果。
- 模型生成工具名和参数，DSH 校验并执行，再把工具结果交还模型；工具结果会触发下一 step，没有新的工具调用时 turn 才结束。
- Code Mode 作为组合工具特性简短介绍：模型可以编写一小段程序，在一次运行中组合多个工具，完成循环、条件、数据处理和并行调用。Nano 不实现完整 Code Runtime。

Provider 只负责把统一请求转换为具体模型 API 的请求，不单独成为章节。本章先让 Agent Loop 工作，再说明实际 Agent 还需要上下文管理、可替换能力、过程记录和运行时扩展。

### M02 上下文组织与 Prompt Cache

**核心问题：DSH 如何组织模型上下文，并尽量提高 Prompt Cache 命中率？**

这个问题讨论每次请求中信息的顺序和变化频率，与 M01 的“模型会看到什么”不同：

- 稳定的 system prompt 与 tool schemas 形成可复用请求前缀。
- 新的对话和工具结果尽量追加在已有前缀之后。
- 巨大工具结果在后续请求中只保留必要片段和省略说明。
- 压力仍然过高时，再用摘要检查点替换较早历史。
- 插件变化、工具目录变化和历史压缩都会改变请求前缀，并从变化位置开始影响缓存复用。

教学网站显示请求各部分的 token 估算、可复用前缀以及裁剪或压缩前后的差异。Nano 不实现模型提供方的缓存，只解释 DSH 如何组织输入以便缓存复用。

M02 先建立上下文压力和请求组织问题；摘要检查点如何在不丢失原始执行记录的前提下改变模型历史，等 M04 引入 Session Log 后完成。

### M03 插件内核

**核心问题：“一切皆插件”如何实现，为什么能力能够安装、替换和卸载？**

只实现 Nano DSH 后续内容依赖的最小插件机制：插件通过同一个 Context 注册服务、工具、Prompt 贡献和监听器；每次注册都带有撤销方法；卸载插件时，它贡献的能力一起消失。Tool 是模型能够调用的动作，Plugin 是向运行时贡献 Tool 或其他能力的安装单元。

Skill、Preset、完整依赖图和 Cordis 的其他能力不属于必要前置，除非最终选中的内容确实使用它们。

### M04 会话日志

**核心问题：DSH 是怎么记录和保存 Agent 执行过程，并据此重建请求和回放的？**

用只追加的 Session Log 记录用户消息、模型回答、工具调用、工具结果、turn／step 边界，以及重建请求所需的信息。下一次模型请求和教学网站 Trace 都从同一份日志推导，不维护另一份隐藏的消息历史。

M02 的工具结果裁剪和摘要检查点只改变从日志派生的模型历史，原始执行记录继续保留。Nano 必须实现内存中的记录、请求重建和回放。是否增加简单 JSONL 落盘，用来演示关闭后恢复，是筛选时需要决定的实现范围；SQLite、迁移和完整 fork 机制不进入 Nano。

### M05 运行时自进化

**核心问题：DSH 所说的运行时自进化，在最小实现中究竟是什么？**

先解释 DSH 如何检查当前运行时，并通过普通插件机制安装或卸载受信任能力。`word_count` 只是验证设计的例子：安装前没有该工具；安装后的下一次模型请求出现它；Agent 调用它完成统计；卸载后它从后续请求中消失。Session Log 和教学网站展示整个变化过程。

运行时变更必须复用 M03 的安装与卸载机制，不能为演示另写一条特殊注册路径。这里实现的是白名单插件热插拔，不是生成新代码、模型学习或跨会话保留经验。

### M06 长程任务

**核心问题：DSH 是怎样让 Agent 持续完成长程任务的？**

只讲最小的长程任务机制：保存当前目标、状态和已开始的 Round 数；一轮结束后判断是否继续；完成、阻塞或达到轮次上限时停止。Nano 用确定性的 fake 场景展示多个 Round 如何推进同一个目标，不实现完整 Goal 服务。

M06 放在 M01–M05 之后，是否进入首版由贯穿任务继续筛选。Todo 可以作为进度展示，但不扩展为独立系统。Schedule、后台 Job、Subagent 和 Workflow 属于可选延伸，见下文。

## 4. 可选延伸

这些内容不与主线并列，只有明确保留后才进入相应章节：

| 候选 | 放置位置 | 当前建议 |
|---|---|---|
| 模型调用失败后的恢复 | M02 | 只保留“上下文溢出后先压缩，取得实际进展才重试”；普通固定重试不讲 |

教学网站不是独立章节。它贯穿 M01–M05，展示模型请求、工具往返、上下文变化、Session Events 和插件安装／卸载；若保留 M06，再增加长程 Round。
