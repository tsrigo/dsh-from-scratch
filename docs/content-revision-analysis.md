# 教程内容改版分析：把六章讲成一个完整的故事

> 依据：官方仓库 [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)（本地克隆 `/tmp/dsh-official`，depth 1，commit 对应官方 main）
> 问题：当前版本内容平铺直叙、没有重点、章节之间不接力、口吻词典化。
> 本文回答三个问题：重点讲什么、怎么串起来、用什么口吻。

---

## 一、现状诊断：平铺直叙的四个根源

### 1.1 六章同构，节奏单一

六章（`docs/lessons/m01.md` … `m06.md`）几乎共用同一个骨架：

> 定义句开头 → 机制说明 → 「完整 DSH 使用 X。Nano DSH 浓缩为 Y。」→ 总结卡

m02 的「投影只影响当前模型请求」「请求内容按变化频率排列」「不同变化对应的前缀失效位置」，m04 的「Session Log 按发生顺序追加事件」「同一组事件生成模型请求和执行过程」「持久化保存 Session Log」——每一章都是三个并列小节，节与节之间没有递进关系。读者读第三章时能预判第四章的结构。

### 1.2 只讲「是什么」，不讲「为什么必须这样」

每章都在解释机制，但很少交代**约束与代价**：

- m02 讲「请求按变化频率排列」，没有先讲清「历史无限增长、token 有成本、KV 缓存按前缀复用」这条因果链。读者不知道这个排列是在解决什么硬问题。
- m04 讲「Session Log 是 append-only」，没有先提出「进程崩溃后如何原样恢复」这个故障场景。
- m03 讲「一切皆插件」，没有展开官方真正的论点：**不存在需要打补丁的特权内核**，连 Agent Loop 本身都是插件。

机制没有动机，就没有重点。

### 1.3 章节之间不接力

- 第一章结尾说「后五章分别管理这组循环的输入、能力、记录、运行时变更和跨轮协调」，但后五章开头从不回指这句话。
- 术语不复用：m01 定义的 Turn / Step，到 m06 才重新解释；m04 说「第二章先用 Agent 内存表示完整记录」，但 m02 正文没有呼应。
- 证据卡是平行部件：`request` / `events` / `graph` 卡片各自展示数据，正文没有先提问、再让读者从卡片得出结论。卡片变成了「附带组件」而不是「论证的落点」。

### 1.4 口吻词典化

每段都是陈述句 + 术语定义（「token 是模型处理文本时使用的计量单位」）。没有任务、没有矛盾、没有数字、没有收益点。全篇像一个术语表按章节展开，不像一次讲解。

## 二、重点应该放在哪里：官方 DSH 的五条承重叙事

官方仓库的架构文档（`docs/architecture.zh.md`）、Cordis 入门（`docs/cordis-primer.zh.md`）、术语表（`docs/glossary.zh.md`）反复强调五件事。这五件事正是教程应该讲透的重点，且恰好一一对应六章：

### 叙事 1：无特权内核（对应 m03）

> 「不存在需要打补丁的特权内核：扩展 dsh 的方式是把插件挂载到其他插件旁边，而各项注册都是副作用，会在其插件卸载时撤销。」—— `docs/architecture.zh.md`

官方对「一切皆插件」的表述比教程强得多：**Agent Loop 本身只是 `Agent` 公开契约的一个默认实现，可替换**（`docs/subsystems/core.md`：「agent-loop is the one concrete implementation of the public `Agent` contract … so the loop stays swappable」）。教程 m03 现在只讲了插件树、Context、effect，没有把「运行时没有内置与插件之分」这个论点立起来。

### 叙事 2：模型可见即已记录（对应 m04）

> 「**模型可见即已记录。** 抵达模型请求的一切都必须能从日志重建，并由一项运行时不变量断言这一点。」—— `docs/architecture.zh.md`

这是整个 DSH 最深的一条设计：会话日志是唯一真源，模型输入、回放、UI、遥测、持久化全部从同一组事件派生。教程 m04 讲了 append-only、重建、持久化三件事，但没有把这条不变量点出来作为章眼。

### 叙事 3：请求是投影，前缀稳定就是钱（对应 m02）

官方把「系统提示词组装 + 从日志派生历史」分成 `system-prompt` 与 `session` 两个子系统，另有 `compaction`（压缩）与 `token-meter`。教程 m02 的「固定区 / 累积区 / 本步区」排列，本质是回答「如何让相同前缀尽可能长」——这正是 KV 缓存复用与成本问题的答案。m02 缺的是把**约束（上下文会满、token 要钱）**放在机制前面。

### 叙事 4：生命周期可逆（对应 m03 / m05）

> 「注册是可逆的副作用。提示词片段、工具 schema、适配器、提供方和监听器通过 `ctx.effect()` 或 `ctx.on()` 安装，reload 和 teardown 时会按预期撤销。」—— `docs/cordis-primer.zh.md`

m03 的 effect 栈、m05 的 `cordis_stop` / `cordis_undefine` 都是这条叙事的实例。教程目前分开讲，没有点明「挂载、回滚、卸载共用一套机制」是插件系统的安全属性。

### 叙事 5：层级 Step ⊂ Turn ⊂ Round ⊂ Goal（对应 m01 / m06）

> 「一个**步骤**是一次模型请求加上它调用的工具。一个**轮次**包含零个或多个步骤：它在领取首条输入之前打开，并在不再欠下任何工作时关闭。」—— `docs/architecture.zh.md`

> 「目标是一种状态，不是调度器，也不是一段独立对话；会话日志仍是其真源。」—— `docs/glossary.zh.md`

m01 讲 Turn/Step，m06 讲 Goal/Round。官方术语表把四层循环关系写得很清楚：Round 是承载一个轮次的外层策略迭代，Round 计数器归策略所有。教程 m06 没有点破「每轮 = 一次普通 Turn + 追加的目标消息」，m01 也没有预告「Turn 会结束，但任务可能没完」。

### 教程的定位

官方仓库 80MB、40+ 包，教程不可能也不应该覆盖产品功能。教程的定位应该是：**用最小实现讲清五条承重叙事对应的运行机制**——循环、投影、插件、日志、续行。凡是官方有、但与这五条无关的功能（审批、沙箱、subagent、工作流、调度……），正文不展开，只在需要时用一句话标注「完整 DSH 有对应机制」。

## 三、每章改法：核心问题、论证主线、证据卡、钩子

### m01 Agent Loop —— 焦点：一次工具往返 + 职责分离

- **核心问题**：模型怎么从「不知道」到「知道」？运行时在这中间负责什么？
- **论证主线**：
  1. 开头给具体任务：让 Agent 回答「首尔现在几点」。模型不知道时间，只能先调用 `get_time`，拿到结果再回答——一次任务需要两次模型请求。
  2. 讲最小循环：请求 → Tool Call → 校验执行 → Tool Result 进历史 → 再请求。这是本章主菜，证据卡 `m01-request-feedback` 直接作为论证落点（两份请求对比：第二份在末尾追加了调用与结果）。
  3. 再定义层级：一次工具往返在一个 Turn 里，每次请求 + 其工具执行是一个 Step；Turn 在「不再欠下任何工作时」结束（官方原话）。
  4. 职责分离收束：模型负责选择动作，运行时负责校验和执行，接口是工具接口——失败也作为结构化结果返回，循环因此能自我修正。
- **钩子**：循环每走一步，请求里堆积的历史就多一份。下一次请求还能装下多少？→ m02。
- **官方素材**：`docs/architecture.zh.md` 轮次流程时序图（turn/start → step/start → … → turn/end）；`agent/pre-step`、`llm/stream`、`tools/*` 瀑布事件是「拦截点」的伏笔（m03 可回指）。

### m02 上下文与缓存复用 —— 焦点：请求是投影，前缀稳定是钱

- **核心问题**：历史无限增长，请求不能无限增长，怎么办？
- **论证主线**：
  1. 从约束出发：第 10 个 Step 时，请求里大部分是旧内容；模型服务按前缀复用 KV 缓存，前缀越长，成本越低（用教程已有的 token 估算数字举例，例如 6 个部分里「系统规则 + 工具定义 + 历史」占了约 115/119 token）。
  2. 投影是设计选择：完整记录与模型视图分离；Nano DSH 用固定字符数头尾裁剪演示「长结果不进请求」。
  3. 排列是第二个选择：固定区（系统规则、Tool Schema）→ 累积区（历史）→ 本步区（动态说明）。代价是本步说明变化会截断前缀，收益是首次失效位置尽量靠后。证据卡 `m02-prefix` 验证：首次失效位置 = 新追加的历史。
  4. 压缩是兜底：超出窗口后，完整 DSH 用摘要替换旧消息（`compaction`），摘要从插入处改变后续前缀——一句话预告，不展开（避免提前引入 m04 的日志）。
- **钩子**：请求是从哪份「完整记录」投影出来的？谁保存它、怎么保证投影与记录一致？→ m04。
- **官方素材**：`system-prompt`（提示词片段与工具 schema 组装）、`deriveMessages()`（从日志派生历史）、`compaction` seam、`token-meter`。

### m03 一切皆插件 —— 焦点：无特权内核 + 生命周期可逆

- **核心问题**：运行能力从哪里来？装上去的东西怎么安全地卸下来？
- **论证主线**：
  1. 先立论点：运行时能力没有「内置」与「插件」之分；连 Agent Loop 都是插件（官方：`agent-loop` 是默认实现，可替换）。「一切皆插件」的含义是**没有特权内核**。
  2. 插件树与依赖：插件通过声明依赖（官方 `inject` / 教程 `use()`）等待服务就绪，加载顺序由依赖决定，不靠手动编排。证据卡 `m03-owners` 验证「每项能力有归属」：Tool、Prompt、Service、Listener 都记录提供方。
  3. effect 是安全属性：注册即副作用，卸载按相反顺序执行清理；挂载失败时沿同一栈回滚——主动卸载与失败恢复共用一套机制（教程 m03 第二节已有此内容，需要提升为论点而不是实现细节）。
  4. 回指 m01：Agent Loop 每次请求前从 Context 读工具列表与系统 Prompt——这是「插件变更在何时生效」的答案。
- **钩子**：能力装好卸掉，但整个过程只留在内存里。运行时到底发生了什么、能不能恢复？→ m04；能力能不能在运行时由 Agent 自己变？→ m05。
- **官方素材**：`docs/cordis-primer.zh.md` 五个核心概念；`docs/architecture.zh.md`「不存在需要打补丁的特权内核」。

### m04 让运行有迹可循 —— 焦点：模型可见即已记录

- **核心问题**：进程崩溃后，怎么把对话原样恢复？事后怎么检查 Agent 到底做了什么？
- **论证主线**：
  1. 从故障出发：模型输入只存在内存里，恢复后就变了样；要恢复、要审计、要回放，三者都指向同一件事——把事实按顺序记下来。
  2. 立章眼：**模型可见即已记录**。抵达模型请求的一切都能从日志重建，这是一条不变量。证据卡 `m04-rebuild` 验证：给定 `request/header` 快照 + 此前的消息事件，请求原样重建。
  3. append-only 与连续编号是顺序保证：先后关系由编号确定，工具结果位于调用之后、下次请求之前——证据卡 `m04-events` 展示一次工具往返的六条事件。
  4. 持久化是完整版的选择：JSONL / SQLite 两个后端，flush 语义；Nano DSH 用数组 + `tutorial.json` 保留「同一数据源」关系。回放（`replayTrace`）与请求重建读同一组事件。
- **钩子**：记录能恢复过去，但改变不了未来。如果任务进行到一半发现缺一个工具呢？→ m05。
- **官方素材**：`docs/architecture.zh.md`「模型可见即已记录」；`docs/subsystems/session.md`「日志是唯一真源」；`persistence` seam（JSONL + SQLite、崩溃恢复）。

### m05 运行时自进化 —— 焦点：一次完整的能力实验

- **核心问题**：Agent 在执行中发现自己缺一个工具，怎么办？
- **论证主线**（当前六章里叙事最好的，保留实验结构，强化动机与验证）：
  1. 场景化开头：任务需要一个当前没有的工具；Agent 先检查现状（`cordis_inspect`），确认缺口，再决定自己补上——这是「运行时才发现的能力缺口」，不是提前装好的。
  2. 定义与挂载分离：`cordis_define` 只登记代码，`cordis_run` 才挂载生效；生效从下一次模型请求开始（回指 m03 的「请求前读 Context」）。证据卡 `m05-before` / `m05-installed` 两图对照验证「挂载前没有、挂载后有」。
  3. 验证是本章强调点：挂载成功 ≠ 工具可用。调用 `word_count` 得到 `words: 3` 才算闭环（证据卡 `m05-verified`）。
  4. 撤销回到基线：`cordis_stop` / `cordis_undefine` 复用 m03 的卸载机制，最后一张图与基线对照——插件和工具数量回到起点。三张图构成「基线 → 处理 → 回滚」的实验方法。
  5. 全程进入 Session Log（回指 m04）：定义、挂载、调用、移除都有事件，能确定模型从哪次请求开始看到新能力。
- **钩子**：一次 Turn 内装的能力，任务超过一轮还能用吗？谁来决定再来一轮？→ m06。
- **官方素材**：`extensions` 子系统（versioned dynamic Cordis plugins，激活 / 审批 / 检查 / 生命周期拆除）。

### m06 长程任务续行 —— 焦点：Goal 是状态，Round 是策略

- **核心问题**：Turn 会结束（回指 m01），但任务没完。谁决定再来一轮？
- **论证主线**：
  1. 开头的矛盾：m01 的 Turn 在模型不再调用工具时结束；但「整理三条发布说明」这类任务需要多轮。Turn 结束 ≠ 任务完成。
  2. 讲清层级：Step ⊂ Turn ⊂ Round ⊂ Goal。Goal 保存目标状态（`objective`、`phase`、已启动轮数、轮数上限）；Goal Round Driver 在 Agent 空闲时检查状态，追加一条带目标和轮次编号的消息，再启动一个普通 Turn——**每轮就是一次普通 Turn + 追加的目标消息**，复用 m01 的整个循环。
  3. 决策权在驱动器：`progressed` / `completed` / `blockedReason` 三个字段决定继续或停止；Goal 只保存状态，不自己推动自己（官方术语表原意，按本仓库风格改写：「Goal 只保存状态。是否续行由 Goal Round Driver 在每轮结束后判断。」）。
  4. 同一 Session 续行是本章证据：证据卡 `m06-round-history` 显示第二份请求开头保留「已找到两项，仍缺一项」——前一轮进展直接进入下一轮的请求，不需要重建对话历史。
  5. 收尾把六章叠起来：输入（m02）、能力（m03/m05）、记录（m04）都服务于同一条循环（m01），而 Goal（m06）是循环外面的续行机制。
- **官方素材**：`docs/subsystems/goal.zh.md`（phase：active / paused / blocked / complete；GoalRef 修订号）；`goal/change` 事件；`docs/glossary.zh.md` 循环层级条目。

## 四、讲述逻辑：怎么把全书串起来

### 4.1 总主线

六章围绕一条主线展开，每章是主线上的一个环节：

> **把一次模型调用，放大成一次可靠的长程执行。**

| 章 | 主线上的位置 | 上一章留下的问题 |
|---|---|---|
| m01 | 一次调用不够 → 循环（Turn/Step） | —— |
| m02 | 循环会让请求膨胀 → 投影与排列 | m01：下一次请求装得下多少历史？ |
| m03 | 循环需要能力 → 能力来自插件 | m02：工具和规则是谁装的？ |
| m04 | 循环要可恢复、可检查 → 日志是真源 | m03：运行过程记在哪？ |
| m05 | 循环的能力可以变 → 运行时自进化 | m04：记录能恢复过去，能改变未来吗？ |
| m06 | 循环会结束，任务没完 → 目标续行 | m05：一轮装的能力，跨轮还能用吗？ |

### 4.2 章节接力的三条硬规则

1. **每章开头必须显式回指上一章留下的问题**，用一两句话（例如 m02 开头：「第一章的循环每走一步，请求里就多一份历史……」）。
2. **术语一经定义，全书复用**：Turn / Step 在 m01 定义，m06 直接说「每轮 = 一次普通 Turn」；Context 在 m03 定义，m05 直接说「挂载到当前 Context」；不再重复解释。
3. **每章结尾两句话**：一句总结本章机制（机制收束），一句留下开放问题（钩子）。这两句是章节之间的承重墙。

### 4.3 每章内部的论证结构

把现在的「定义 → 机制 → 对比 → 总结」换成：

> **具体任务或故障 → 约束 → 设计选择 → 用证据验证 → 代价与边界 → 遗留问题**

- **具体任务或故障**：一个能让读者产生「这怎么办」的问题（查时间、历史膨胀、崩溃恢复、缺工具、任务没完）。
- **约束**：硬限制（上下文窗口、token 成本、进程会崩、Turn 会结束）。
- **设计选择**：DSH 在这个约束下选了哪条路（投影、排列、插件、日志、Goal）。
- **用证据验证**：证据卡是论证的落点，不是附带组件。
- **代价与边界**：每个选择都有代价（裁剪丢中间内容、前缀从摘要处失效、动态插件只在当前 Session 生效），交代代价才显得诚实。
- **遗留问题**：即 4.2 的钩子。

### 4.4 证据卡的使用规则

现在证据卡由 `block.description` 自动出现，正文和卡片各说各的。改成：

1. **正文先提问，卡片给证据，文字解释结论**。例如 m01 正文写「比较两份请求，看第二份比第一份多了什么」，然后 `m01-request-feedback` 卡片出现，正文再解释「多了调用与结果，且位置在末尾」。
2. **三张证据卡各司其职**：源码卡（机制：看代码怎么实现）、数据卡（结果：请求 / 事件 / 图展示运行产物）、总结卡（收束：本章答案与下一章问题）。
3. **描述文案（`block.description`）也按论证结构改写**，从「查看……」改成「对比 X 与 Y，确认 Z」。

## 五、口吻：让讲述自然

### 5.1 现状问题

- 全篇陈述句 + 定义句，「X 是 Y」开头频率高。
- 「完整 DSH 使用 X。Nano DSH 浓缩为 Y。」的固定配对出现 20+ 次，节奏完全可预测。
- 没有数字、没有任务、没有收益点，也没有「读者此刻在想什么」的回应。

### 5.2 建议规则（在 AGENTS.md 风格约束内）

1. **任务驱动开头**。每章第一段给一个具体任务或故障，把定义推迟到需要时。m01 开头从「首尔现在几点」进入，而不是从「一次模型调用只产生一次回复」进入。
2. **先矛盾，后解决**。把「上下文会满」「进程会崩」「Turn 会结束」这类矛盾放在机制前面，机制成为矛盾的答案。
3. **数字具体化**。引用真实的 token 估算（如「固定区 + 累积区约 115 token，本步区 4 token」）、行号、事件编号、步骤数。数字是「重点」最便宜的实现方式。
4. **用「选择 + 代价」代替「设计」**。把「请求内容按变化频率排列」改写为「把本步说明放在末尾：收益是首次失效位置靠后，代价是本步区每次都会截断前缀」。
5. **打破「完整版 / 最小版」的固定配对**。由论证需要决定何时讲完整版（作为「更复杂场景下的同一机制」）、何时讲最小版（作为「这段代码里的对应实现」）。同一章内最多出现一次完整配对。
6. **每章一句机制收束 + 一个开放问题**（见 4.2）。
7. **严格遵守 AGENTS.md 风格**：不用「不是……而是」「是 X 不是 Y」句式（官方术语表「目标是一种状态，不是调度器」是官方原文，引用其含义时改写为「Goal 只保存状态。是否续行由驱动器判断。」）；少用引号与破折号；缩写首次出现给全称；不用比喻与拟人；自包含。

### 5.3 改前 / 改后示例

**m01 开头**

- 改前：「一次模型调用只产生一次回复。Agent（智能体）处理任务时，模型可能需要先确定缺少的信息，调用工具取得结果，再根据结果选择下一步。」
- 改后：「让 Agent 回答『首尔现在几点』。模型不知道时间，只能先调用 `get_time` 工具，拿到结果再回答。一次回答需要两次模型请求，两次请求之间的衔接由运行时负责。这一章回答：一次工具往返是怎样完成的。」

**m02 开头**

- 改前：「模型每次根据当前请求生成回复。随着 Agent 持续运行，用户消息、模型回复和工具结果不断增加；如果每次请求都包含全部原文，内容最终会超过模型上下文可容纳的 token 数量。」
- 改后：「循环每走一步，请求里就多一份历史。第 10 个 Step 时，请求里 90% 是旧内容；模型服务按前缀复用 KV 缓存，前缀越长，成本越低。上下文管理的任务只有一个：让相同前缀尽可能长。」

**m04 章眼**

- 改前：「DSH 把 Agent 的完整交互过程保存为一条 Session Log（会话日志）。」
- 改后：「进程崩溃后，怎样才能把对话原样恢复？DSH 的答案是一条不变量：模型可见即已记录。抵达模型请求的一切，都必须能从日志重建。」

**m06 核心句**

- 官方原意（术语表）：「目标是一种状态，不是调度器。」
- 本仓库改写（遵守风格约束）：「Goal 只保存目标状态。什么时候继续、什么时候停止，由 Goal Round Driver 在每轮结束后判断。」
