# Agent Loop 把模型判断变成可执行的反馈循环

单独调用一次模型，只能得到一次输出。Agent 要处理的是另一类问题：模型先判断缺少什么信息，调用工具取得结果，再根据结果决定下一步。事先无法知道它会调用几次工具，也无法把完整流程写成固定的工作流，因此需要一个循环来承接模型的每次选择。

## 模型决定下一步，Harness 负责把它做成

一个 Turn 从用户提出任务开始。DSH 先把系统规则、当前工具、已有历史和本步说明整理成统一请求，再交给模型。模型返回普通文字，也可以返回一组带名称和参数的工具调用；它只是在提出动作，并没有亲自执行任何代码。

Harness 接手后会查找工具、校验参数并执行。未知工具、参数错误和执行异常都不会被藏在控制流里，而会被包装成模型可读的结果。这样，决定“做什么”的模型与决定“能不能做、怎样执行”的运行时之间，有一道清楚的边界。

## 工具结果必须进入下一次请求

工具执行完并不等于任务完成。结果会连同对应的调用编号写入历史，循环随后进入下一个 Step，再次请求模型。模型这时看到的不是一句“工具已经跑过”，而是自己刚才提出的调用和运行时返回的实际结果，因此可以修正计划、继续调用别的工具，或者给出最终回答。

右侧的小请求只演示这一次变化：第一份请求要求模型取得时间；第二份请求保留原来的规则和问题，并在后面追加工具调用与查询结果。反馈被放回上下文，Agent Loop 才真正闭合。

## Turn、Step 与停止条件

在这份教学实现里，一个 Turn 表示一次用户任务；一次模型请求及其随后触发的工具执行构成一个 Step。一个 Turn 可以包含多个 Step。模型仍在调用工具，说明反馈循环还没有结束；模型不再调用工具，Harness 才把这次回复当作 Turn 的终点。

循环还必须由运行时设边界。工具失败会作为结果交还模型，让它有机会换一种做法；连续 Step 达到上限仍未结束，则由 Harness 明确终止，而不是无限消耗资源。Provider 只把统一请求翻译成具体模型接口，它可以替换，但不拥有 Agent Loop 的控制逻辑。

因此，DSH 的 Agent Loop 可以收成一条完整链路：组装请求，调用模型，执行经过校验的工具，把结果追加回历史，再根据新的模型输出继续或停止。后面五章所做的事，都是让这条小循环在真实运行中仍然可管理、可扩展、可追溯。
