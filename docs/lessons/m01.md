# 一次工具往返：Agent Loop 的起点

先看一个具体任务：用户要知道北京当前时间。模型理解问题，却没有实时数据；它需要调用 `get_time`，读取返回值，再给出回答。这个过程把模型、工具和运行时放进同一条执行链，是 DSH 后续机制共同依赖的起点。

许多 Agent Harness 都能完成一次工具调用。DSH 的差异会在后面的运行时组织中逐渐显现：工具、提示词、会话和 Agent Loop 都能被插件组装，执行事实也会进入共同日志。本章先把最小循环讲清楚，后面的设计才有稳定的落点。

`agent.ts` 先声明模型适配器、工具定义、一次 Turn 的返回值，以及 `Agent` 持有的状态。读代码前先确认这几个边界：**模型负责提出下一步，运行时负责准备输入、执行动作并保存反馈。**

## 1.1 一次回答为什么会变成多个 Step

模型第一次看到系统规则、`get_time` 的参数说明、用户问题和本步说明。它无法从这些文字得出当前时间，于是返回一次 Tool Call（工具调用）。运行时执行查询，把工具结果加入消息历史；下一次请求带着这条新事实再次发给模型。模型返回普通文本时，这个 Turn（一次连续执行）结束。

**Step 是一次模型请求及其触发的工具执行，Turn 可以包含多个 Step。**为了让每个 Step 遵守同一套边界，构造 `Agent` 时先固定模型适配器、工具表、参数校验器、系统规则和最大步数。这样，循环开始后不需要在每次请求中重新猜测这些依赖来自哪里。

准备完成后，`runTurn()` 才开始处理用户输入。它把输入写入历史，在每个 Step 创建一份独立请求，调用模型，再把模型回复写回历史。模型发出工具调用时，循环继续；没有工具调用时，当前回复就是最终答案。这里把请求构造、模型回复和工具往返放在同一个控制流里，读者可以直接对照一次 Turn 的完整顺序。

## 1.2 工具执行需要一条统一的反馈入口

模型只能给出工具名和参数，无法直接决定执行是否安全或成功。运行时需要查找已注册的工具，检查参数是否符合 Schema（参数结构规则），再执行工具函数。查询成功、工具名不存在、参数无效和工具抛出异常，都应回到同一种工具结果消息中。

因此 `runTurn()` 不把校验细节塞进循环体，而是调用 `#executeTool()`。**所有成功与失败都回到同一种工具结果消息中。**这个小函数把三类失败转换为带 `ok: false` 的结构化结果，并把成功值原样返回。下一次请求可以读取同一种消息格式，模型也能据此修改参数或选择其他动作。

## 1.3 这条循环在 DSH 中处于什么位置

这个最小实现把工具往返变成可检查的程序流程，却仍把工具列表、系统规则和消息历史直接保存在 `Agent` 内部。任务变长后，请求输入会增长；运行能力变动后，构造器也会变得拥挤；程序结束后，内存里的历史无法支撑回放。

完整 DSH 保留这条执行边界，同时把输入投影、能力组装和会话记录交给独立的运行时机制。理解本章的 Step 和 Turn，才能看清这些机制分别接住了循环的哪一部分。
