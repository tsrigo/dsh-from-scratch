# 一次工具往返：Agent Loop 的起点

让 Agent 回答：查一下北京现在的时间。模型不知道时间，只能先调用 `get_time` 工具，拿到结果后再回答。一次回答需要两次模型请求，两次请求之间的衔接由运行时负责。这一章回答：一次工具往返是怎样完成的。

## 1.1 循环：请求、执行、再请求

第一次请求包含系统规则、工具定义、用户问题和一句本步说明，共约 62 token。模型从这些内容里读不出时间，于是返回一个 Tool Call（工具调用）：调用 `get_time`，参数是北京。

Harness 收到 Tool Call 后查找工具、校验参数并执行，把结果连同调用编号写入历史，然后开始下一个 Step（步骤），再次请求模型。第二份请求保留了第一份的全部内容，只在末尾追加了模型刚才的调用和工具返回的结果，共约 119 token。模型读取结果后直接回答，Turn（轮次）结束。

请求对比卡只展示这一处变化。先比较两份请求的开头：系统规则、工具定义和用户问题完全相同。再从末尾找差异：第二份多了模型回复与工具结果。这一处变化就是 Agent Loop 的最小闭环：模型提出动作，运行时执行动作，结果进入下一次请求，模型根据结果决定下一步。

## 1.2 模型选择动作，Harness 校验并执行

把上面的一次往返拆开，可以看到两种职责。模型负责选择动作：调用哪个工具、传什么参数。Harness 负责判断动作能否执行：查找工具、校验参数、执行并捕获异常。职责的边界是工具接口。

具体到执行路径：Harness 先按工具名查找注册表，再用参数规则校验传入的参数，然后调用工具，最后捕获执行异常。四步中的任何失败都产生一个结构化结果。

未知工具返回 `Unknown tool`，参数不符合规则返回 `Invalid tool arguments` 与问题清单，执行异常返回异常信息。这些结果与正常结果一样写入历史，供模型在下一步读取。

模型读取失败原因后调整参数，或改用其他工具。失败的调用因此也能进入下一次请求，循环依靠这条反馈自我修正。

## 1.3 Step、Turn 与停止条件

一次模型请求及其触发的工具执行，构成一个 Step。Turn 是这些 Step 的容器：它在接收用户消息时开始，在模型不再调用工具时结束。Nano DSH 的 `runTurn()` 接收一条用户消息，在同一个 Turn 里连续执行多个 Step。

Turn 有两个停止条件。正常条件：模型返回不含工具调用的回复，当前 Turn 结束。防御条件：Step 数量达到上限，Harness 明确终止运行。工具失败不触发停止条件，它作为结果返回给模型，由模型决定下一步。

完整 DSH 的边界更宽。它在每个 Step 结束时检查当前 Turn 是否仍有待处理的工具结果或新输入；Provider（模型服务适配器）负责把统一请求转换为具体模型接口所需的格式，并处理流式返回。Agent Loop 负责推进 Turn 和 Step，后五章分别管理这条循环的输入、能力、记录、运行时变更和跨轮协调。
