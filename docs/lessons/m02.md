# 让相同前缀尽可能长

第一章的循环每走一步，都会把更多消息带进下一次请求。短任务里，这个做法足够直观；工具返回很长的文本后，模型输入会很快占满上下文窗口。运行时此时要同时保留两份数据：**完整事实用于审查和恢复，当前模型视图用于本次推理。**

DSH 的上下文设计先解决输入可控的问题，再利用稳定的请求顺序争取前缀缓存复用。**先让输入可控，再尽量延长稳定前缀。**缓存并非一段单独的优化代码，它依赖请求中哪些内容保持不变、哪些内容只在末尾追加。读这一章时，先跟着完整事实和模型视图的分工走，再看代码怎样维持这个分工。

`context.ts` 开头定义投影规则、请求部件和比较结果。它们给出了三个后续函数共享的语言：多长的工具结果需要裁剪、请求由哪些部分组成、两次请求从哪里开始不同。

## 2.1 模型视图可以缩短，完整事实必须保留

让 Agent 回答备忘录内容时，`read_note` 可能返回很长的文本。每个 Step 都携带全文会持续增加输入长度；直接覆盖原结果又会让后续回放失去依据。Nano DSH 因此在请求前生成一份投影，只处理模型这次要读取的消息，原始消息保持不变。

投影函数逐条复制消息，只对 Tool Result（工具结果）调用裁剪函数。短结果原样保留；长结果保留开头、结尾和省略字符数。开头帮助模型辨认来源，结尾常含结论、状态或错误信息，省略标记明确说明中间内容没有进入本次视图。

这段代码刻意把复制与裁剪放在一起：**裁剪发生在请求视图生成时，完整事实不被改写。**完整 DSH 会把原始事实保存到 Session Log（会话日志），供之后的重建、回放和恢复使用。

## 2.2 请求的排列决定变化落在哪里

裁剪控制单条结果的体积，请求部件的顺序决定新增内容会影响哪里。Nano DSH 先放系统规则和 Tool Schema（工具名称与参数规则），随后按时间追加消息历史，最后加入每个 Step 都会变化的说明。相邻请求从开头比较时，变化慢的内容会留下更长的相同前缀。

`describeRequest()` 将这个顺序写成显式数组。**变化慢的内容放在前面，新增内容追加到后面。**它没有调用模型服务，也不管理缓存；它负责把请求拆成可观察的部件，让页面和比较函数都能依据同一种顺序理解一次模型调用。把排序逻辑集中在这里，工具往返增加消息后，新增部分自然落在历史尾部。

## 2.3 用可重复的比较检查结构是否稳定

页面需要说明第二次请求复用了多少开头，但页面无法直接得知模型服务的真实缓存命中。`compareRequestPrefix()` 因此做一项确定性的结构检查：将部件规范化后从头比较，记录相同部件数、估算的文本量和首次变化位置。真实缓存命中与计费仍以模型服务返回的数据为准。

比较函数还需要估算 token（模型处理文本时使用的切分单位）数量，并稳定排序对象字段。它们没有改变请求内容，只让同一份结构在本地比较时得到一致结论。源码将这些辅助计算与前缀比较放在一起，避免读者把展示用估算误认为模型服务的缓存实现。

当工具、提示词或模型适配器在运行中改变时，请求的稳定部分也会随之改变。DSH 将这些能力交给运行时组织；上下文模块继续负责把当时有效的能力和历史排成可发送的输入。
