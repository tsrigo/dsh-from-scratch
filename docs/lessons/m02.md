# 上下文管理的核心，是把完整记录与模型输入分开

模型每次只能看到当前请求，并不会天然记得上一步。Agent 运行得越久，用户消息、模型回复和工具结果就越多；如果把所有原文无条件塞进请求，上下文窗口迟早会被耗尽。DSH 因而需要两种视角：一份权威记录保留发生过的内容，本次请求则是从记录生成的模型视图。第二章的 checkpoint 暂时把原文留在 Agent 内存；第四章再把权威记录正式迁入 Session Log。

## 投影只改变“这次给模型看什么”

工具结果是最容易突然膨胀的部分。测试日志、搜索结果或文件内容可能比其余历史加起来还长。Nano DSH 对长结果保留开头、结尾和明确的省略标记：开头通常能说明结果的身份，结尾往往包含结论或错误，而标记告诉模型中间确实被裁掉了多少内容。

这里的关键不是某个固定字符数，而是信息分层。完整工具输出仍留在权威记录中：本章暂存在 Agent 内存，第四章再进入 Session Log；裁剪只发生在构建模型请求时。以后需要更激进的压缩，也应当生成新的历史投影，而不是反过来改写已经发生的记录。

## 一份请求按变化速度排列

请求最前面是固定区：系统规则与工具 Schema。中间是累积区：用户、模型和工具消息按发生顺序只向后追加。最后是本步区：只服务于当前 Step 的动态说明。三者并不是视觉上的分类而已，它们对应三种不同的变化频率。

这样排列是为了保住尽可能长的稳定前缀。多数模型服务的 Prompt Cache 复用的是相邻请求开头那段完全相同的 token；它不关心两份请求“意思差不多”，只关心从开头起能连续匹配多久。把频繁变化的本步说明放在最后，新消息也尽量追加而不重排旧内容，变化就更可能发生在请求后部。

## 哪些变化会让缓存提前失效

如果系统规则改变，前缀从第一部分就不同；插件安装导致工具目录变化，失效点会落在工具 Schema；普通的新消息通常只影响历史尾部。历史压缩则处在两者之间：摘要能减少总长度，但它替换了较早内容，也会从摘要所在位置改变后续前缀。因此，上下文变短和缓存复用变好不是同一件事，需要分别权衡。

本教程展示的是请求结构提供的缓存机会，而不是服务端真实命中率。模型提供方是否启用缓存、以什么粒度计费，属于 Provider 的实现。DSH 能做的是保持序列确定、稳定内容前置、增量内容后置，并把每次首次变化的位置解释清楚。

所以第二章的答案包含两层：上下文通过“完整事件记录 → 本次请求投影”组织；缓存则通过稳定前缀、追加式历史和末尾动态说明获得复用机会。裁剪与摘要负责控制体积，顺序与稳定性负责保护缓存，它们解决的是相邻但不同的问题。
