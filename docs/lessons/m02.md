# 上下文管理分别保存完整记录与模型输入

模型每次只能读取当前请求，不会自动保留上一步的内容。随着 Agent 持续运行，用户消息、模型回复和工具结果不断增加；如果每次请求都包含全部原文，内容最终会超过模型上下文可容纳的 token 数量。token 是模型处理文本时使用的计量单位。DSH 保存一份包含完整内容的记录，并从中生成每次请求所需的模型视图。第二章暂时把原文保存在 Agent 内存中；第四章再把完整记录迁入 Session Log（会话日志）。

## 投影只影响当前模型请求

工具结果的长度可能突然增加。测试日志、搜索结果或文件内容有时比其余历史的总和还长。Nano DSH 对长结果保留开头、结尾和明确的省略标记。开头可用于识别结果内容，结尾常包含结论或错误，省略标记则记录中间删去了多少字符。

固定字符数只是本示例的投影配置。完整工具输出仍保存在原始记录中：本章使用 Agent 内存，第四章改用 Session Log。裁剪只发生在模型请求的构建阶段。需要进一步压缩时，可以生成新的历史投影，同时保留已经发生的原始记录。

## 请求内容按变化频率排列

请求最前面是固定区，包含系统规则与 Tool Schema（工具定义及参数规则）。中间是累积区，用户消息、模型回复和工具结果按发生顺序向后追加。最后是本步区，只包含当前 Step 使用的动态说明。这三个区域的变化频率不同。

这种顺序可保留较长的稳定前缀。多数模型服务的 Prompt Cache（提示词缓存）复用相邻请求开头连续相同的 token。缓存比较的是实际内容及其顺序；语义接近但文本不同的内容无法直接复用。把频繁变化的本步说明放在末尾，并追加新消息而不重排旧内容，可以把首次变化的位置留在请求后部。

## 会让缓存提前失效的变化

系统规则改变时，前缀从第一部分开始变化；插件安装改变工具目录时，变化位置落在 Tool Schema；普通新消息通常只影响历史末尾。历史压缩位于更靠前的位置：摘要可以减少请求长度，也会从摘要插入处改变后续前缀。上下文长度和缓存复用率需要分别评估。

本教程展示请求结构能够提供的缓存复用机会，不代表服务端的真实命中率。模型服务商是否启用缓存以及采用何种计费粒度，由具体服务决定。DSH 能控制序列的确定性、固定内容的位置、历史的追加顺序，并记录每次请求最早发生变化的位置。

第二章把完整记录投影成当前模型请求，并通过固定内容前置、历史追加和动态说明后置来延长稳定前缀。裁剪与摘要控制请求长度，内容顺序与稳定性影响缓存复用。
