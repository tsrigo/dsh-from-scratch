# 上下文管理分别保存完整记录与模型输入

模型每次根据当前请求生成回复。随着 Agent 持续运行，用户消息、模型回复和工具结果不断增加；如果每次请求都包含全部原文，内容最终会超过模型上下文可容纳的 token 数量。token 是模型处理文本时使用的计量单位。DSH 从完整的 Session Log（会话日志）生成每次请求所需的模型视图。Nano DSH 在第二章先用 Agent 内存中的消息表示完整记录，第四章再用 Session Log 表达同一关系。

## 投影只影响当前模型请求

工具结果的长度可能突然增加。测试日志、搜索结果或文件内容有时比其余历史的总和还长。Nano DSH 使用固定字符数触发裁剪，对长结果保留开头、结尾和明确的省略标记。开头可用于识别结果内容，结尾常包含结论或错误，省略标记则记录中间删去了多少字符。

固定字符数是这个最小样本的投影配置。完整工具输出仍保存在 Agent 内存中，裁剪发生在模型请求的构建阶段。完整 DSH 会在 token 压力达到阈值后剪枝过长的工具结果；如果请求仍然过长，再用摘要替换较早的模型视图。原始事件继续保存在 Session Log 中。Nano DSH 用固定阈值的头尾裁剪集中展示完整记录与模型视图的分工。

## 请求内容按变化频率排列

请求最前面是固定区，包含系统规则与 Tool Schema（工具定义及参数规则）。中间是累积区，用户消息、模型回复和工具结果按发生顺序向后追加。最后是本步区，只包含当前 Step 使用的动态说明。这三个区域的变化频率不同。

这种顺序可保留较长的稳定前缀。这里的缓存复用指模型服务对相同请求前缀的 KV Cache（Key-Value Cache，键值缓存）复用。缓存比较的是实际内容及其顺序；语义接近但文本不同的内容会产生不同的缓存键。把频繁变化的本步说明放在末尾，并按顺序追加新消息，可以把首次变化的位置留在请求后部。

## 不同变化对应的前缀失效位置

系统规则改变时，前缀从第一部分开始变化；插件安装改变工具目录时，变化位置落在 Tool Schema；普通新消息通常只影响历史末尾。历史压缩位于更靠前的位置：摘要可以减少请求长度，也会从摘要插入处改变后续前缀。上下文长度和缓存复用率需要分别评估。

页面比较相邻请求的最长相同前缀，并用字符数估算对应的 token 数量。这个结果用于解释请求结构产生的缓存复用机会，页面会将它标记为教学估算。实际缓存命中和计费按照具体模型服务返回的数据判断。完整 DSH 通过稳定排列系统提示词和工具定义、按顺序追加历史来保留可复用前缀。Nano DSH 的页面进一步标出相邻请求最早发生变化的位置。

第二章把完整记录投影成当前模型请求，并通过固定内容前置、历史追加和动态说明后置来延长稳定前缀。本章的头尾裁剪与第四章的摘要共同控制请求长度，内容顺序与稳定性影响缓存复用。
