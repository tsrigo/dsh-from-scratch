# Session Log 保存观察事件，其他视图从中派生

只维护一个 `messages` 数组，足以继续聊天，却不足以解释一次 Agent 运行。它通常没有保存某个 Step 当时使用的系统规则、工具目录和投影设置，也很难回答插件何时安装、一次工具结果属于哪个调用、Agent 为什么在这里停止。

DSH 因此不把“模型消息”当作全部历史，而是把运行中观察到的事件写成 Event。用户输入、Step 开始、请求头、模型回复、工具调用、工具结果、上下文检查点和运行时变化，都在同一条 Session Log 中获得类型与递增编号。

## Event 是记录格式，Trace 是阅读方式

日志采用 append-only 约束：新事件只追加到末尾，已经记录的事件不就地改写。这样做首先是为了保留因果顺序，其次才是为了展示。一个工具结果排在某次调用之后、下一次请求之前，这个位置本身就在说明它怎样进入了后续上下文。

右侧只截取一次工具往返所需的六条关键事件，不试图把所有事件一次铺满。它们足以看见用户消息、第一份请求、模型工具调用、工具结果和第二份请求之间的顺序。完整实现还有 Turn、Step、checkpoint 与运行时事件；这些仍属于同一套记录，不是另一张时间线。

## 任意一步的请求都能从日志重建

为了还原某个 Step，`buildRequest()` 先找到它的 `request/header`。Header 保存当时的系统规则、工具 Schema、本步说明与投影配置；Header 之前的用户、模型和工具事件则按原顺序还原成消息。工具调用会重新挂回产生它的模型回复，工具结果继续保留对应的调用编号。

如果历史中已有上下文 checkpoint，请求构建器会用摘要代表检查点覆盖的旧事件，再拼接它之后的新事件。注意，被覆盖的原始 Event 并没有从 Session Log 删除；变化的是模型当前要看的投影。这也把第二章的“完整记录与模型输入分离”落到了可重建的数据结构上。

页面上的 Trace 同样只是对 Event 的翻译：事件类型变成人能读的标题和说明，原始 payload 仍可展开。于是请求检查、执行时间线和能力变化不会各自维护一份容易漂移的副本，它们都引用同一记录源。

这里的“重建”是语义层的 Unified Request 重建，不是逐字节复现 Provider payload；“回放”也是把事件重新投影成 Trace，不会再次调用模型或重新执行工具。模型流式分片、网络重试和供应商请求编号也没有进入这份最小日志。

当前 Nano DSH 把 Session Log 保存在内存中，已经证明记录、重建和回放的模型，但没有声称进程重启后仍能恢复。若要跨进程保存，可以把同一组 Event 追加写入 JSONL 或数据库；持久化介质是下一层工程选择，不改变本章的事件结构。

所以“有迹可循”并不是多打几行日志，而是建立共同记录源：Event 负责记录观察结果，Session Log 保留顺序，Request 与 Trace 从中派生，checkpoint 只改变模型视图而不抹去历史。
