# 模型可见即已记录

第三章结束时，插件挂载、工具调用、模型回复都只存在内存里。进程退出后，这些过程全部消失：对话无法恢复，执行过程无法检查，之前发生了什么只能靠记忆。要恢复、要审计、要回放，三个需求指向同一件事：把运行中发生的事实按顺序记下来。这一章回答：DSH 怎样记录一次运行，又怎样从记录里重建请求？

## 4.1 日志按发生顺序追加事件

DSH 把 Agent 的完整交互过程保存为一条 Session Log（会话日志）。日志中的每一项称为 SessionEvent（会话事件）：轮次开始、步骤开始、用户消息、模型回复、工具调用、工具结果，以及请求头。每个 SessionEvent 都有事件类型、连续编号、发生时间和对应数据。

日志采用 append-only（只追加）结构：新事件写在末尾，已经写入的事件保持原样。先后关系因此可以从编号直接确定：工具结果位于对应的工具调用之后、下一次模型请求之前，也就说明了这份结果怎样进入后续上下文。Nano DSH 的 `SessionLog.append()` 复制事件、分配递增编号，再把它加入数组；`sessionPlugin()` 还会监听插件加载和卸载通知，把运行时能力变化写入同一条日志。

事件卡展示一次工具往返的六条事件：用户消息、第一次请求头、模型回复、工具调用、工具结果、第二次请求头。按编号依次阅读，就能看到请求、执行与反馈的先后关系。

## 4.2 模型可见即已记录

日志不只是流水账，它是模型请求的唯一来源。完整 DSH 有一条运行时不变量：模型可见即已记录。抵达模型请求的一切都必须能从日志重建。因此，新增一项模型可见的输入，就需要新增一类 SessionEvent。

请求重建的路径如下。`request/header` 保存某个 Step 当时的模型配置、系统 Prompt、Tool Schema、动态说明和投影设置；`buildRequest()` 先找到目标 Step 的请求头，再把此前的用户消息、模型回复和工具结果按顺序还原，工具调用重新归入发起调用的模型回复。历史中存在 `context/checkpoint` 时，构建器先加入摘要，再追加检查点之后的事件；被概括的原始事件仍保留在日志中。

Nano DSH 为每个 Step 都记录一条完整的 `request/header`，请求因此可以逐字重建。页面上的请求对比、Trace（执行过程视图）和事件卡都从同一份日志生成，各自维护副本只会让它们逐渐不一致。

## 4.3 持久化是完整版的选择

内存日志能演示记录与重建，但进程重启后仍然丢失。完整 DSH 把 SessionEvent 分批复制到存储：JSON Lines（JSONL，每行一条 JSON 记录）或 SQLite 两种实现，显式 flush（刷新）等待当前批次写入完成，重新加载会话时再从持久化记录恢复日志。

Nano DSH 在一次运行中把事件保存在 `SessionLog` 数组里，教程生成器把这些事件写入网站使用的 `tutorial.json`，页面随后根据这份静态记录重建请求并回放 Trace。这份最小实现保留了事件记录、请求投影和回放共用同一数据源的关系。

边界需要说明：本章重建的是语义一致的统一请求，不保证与模型服务商的原始请求逐字节相同；回放不会重新调用模型或执行工具，模型的流式分片、网络重试和服务商请求编号没有进入这份最小日志。
