# Session Log 保存事件并生成其他视图

DSH 把 Agent 的完整交互过程保存为一条 Session Log（会话日志）。日志中的每一项称为 SessionEvent（会话事件），例如表示轮次开始的 `turn/start`、表示步骤开始的 `step/start`，以及用户消息、模型回复、工具调用和工具结果。每个 SessionEvent 都有事件类型、连续编号、发生时间和对应数据。

这里的 SessionEvent 表示需要写入会话历史的事实。第三章介绍的 Cordis Event 用于插件之间的运行时通信；需要长期保留的信息，会由事件处理方追加为 SessionEvent。DSH 的插件还可以扩展 SessionEvent 类型，例如加入上下文压缩记录。

## Session Log 按发生顺序追加事件

Session Log 采用 append-only（只追加）结构。新事件写在日志末尾，已经写入的事件保持原样，因此 Turn、Step、模型回复和工具执行之间的先后关系可以从编号直接确定。工具结果位于对应的工具调用之后、下一次模型请求之前，也就说明了这份结果怎样进入后续上下文。

Nano DSH 的 `SessionLog.append()` 会复制事件，分配递增的 `id`，再把它加入数组。`sessionPlugin()` 还会监听插件加载和卸载通知，把运行时能力变化写入同一条日志。右侧展示一次工具往返中的六条事件，可以依次查看用户消息、第一次请求、工具调用、工具结果和第二次请求。

## 同一组事件生成模型请求和执行过程

完整 DSH 从 Session Log 派生模型消息。`user/message`、`assistant/message` 和 `tool/result` 等事件组成模型可见的消息历史；`request/header` 保存模型配置、渲染后的系统 Prompt 和 Tool Schema。当请求头发生变化时，DSH 会追加一份完整快照。读取目标位置之前最近的请求头，再结合当时的消息历史，就可以重建模型请求。

Nano DSH 为每个 Step 都记录一条完整的 `request/header`，其中包含 provider（模型服务提供方）、model（模型名称）、系统 Prompt、Tool Schema、动态说明和投影设置。`buildRequest()` 先找到目标 Step 的请求头，再把此前的用户消息、模型回复和工具结果按顺序还原。工具调用会重新归入发起调用的模型回复，工具结果继续使用原来的调用编号。

Nano DSH 的 `context/checkpoint` 表示一段较早历史的摘要。重建请求时，`buildRequest()` 先加入摘要，再追加检查点之后的事件。完整 DSH 的上下文压缩也会追加新的 SessionEvent，让摘要替换模型当前看到的一段旧消息；被概括的原始事件仍保留在 Session Log 中。

Nano DSH 的 `replayTrace()` 读取同一组 SessionEvent，为每条事件生成标题和说明。网站把这个结果称为 Trace（执行过程视图）。Trace 回放只读取已经记录的事件，模型请求重建和执行过程展示因此使用同一份数据。

## 持久化保存 Session Log

完整 DSH 在内存中追加 SessionEvent，并通过 `session/event` 通知持久化插件。持久化插件分批复制这些事件，通过统一的 `SessionPersistence` 服务写入存储。DSH 提供 JSON Lines（JSONL，每行一条 JSON 记录）和 SQLite 两种实现；重新加载会话时，再从持久化记录恢复 Session Log。显式 flush（刷新）会等待当前批次写入完成。

Nano DSH 在一次运行中把事件保存在 `SessionLog` 数组里。教程生成器会把这些事件写入网站使用的 `tutorial.json`，页面随后可以根据这份静态记录重建模型请求并回放 Trace。这段最小实现保留了事件记录、请求投影和回放共用同一数据源的关系。

DSH 通过 SessionEvent 记录运行事实，由 Session Log 保存事件顺序，再通过持久化服务写入 JSONL 或 SQLite。模型请求、文本记录和回放视图都从这条日志派生，因此保存下来的事件可以继续用于恢复和检查 Agent 的执行过程。
