# 模型可见即已记录

前三章已经产生多种状态：用户消息和工具结果构成模型历史，插件改变可用工具和系统规则，页面还要展示执行过程。若这些信息分别停留在消息数组、调试输出和界面状态中，同一次运行很容易出现几份互相对不上的版本。

**DSH 先把运行事实写入一条仅追加的 Session Log（会话日志），再从这条日志派生模型历史、回放、界面和持久化数据。**这个顺序建立了一条可检查的约束：**模型能够看到的内容，必须能从记录中重建。**本章把第二章的模型视图、第三章的运行时变化接到同一个事实来源上。

`session.ts` 开头列出一次运行可能产生的 `SessionEvent`，并定义 `SessionLog` 的基本状态。事件类型比一张宽泛的日志表更具体：请求头、工具调用、工具结果、插件变化和 Goal 状态各自带着重建所需的数据。

## 4.1 先按发生顺序保存事实

一次工具往返至少包含用户消息、请求头、模型回复、工具调用和工具结果。`SessionLog.append()` 复制传入事件，分配递增编号，再追加到末尾。编号让页面能够指向确定事件，**追加顺序保留了因果关系：工具结果位于工具调用之后、下一次请求之前。**

上下文检查点也是事件。它记录一段摘要及其覆盖到的最后一个事件编号，原始事件仍保留在日志中。后续请求可以从摘要和较新的事件构建较短视图，审查和回放仍可回到完整事实。把编号、追加和检查点放在一个小类中，正是在为后面的重建函数准备可靠输入。

## 4.2 日志必须跟随运行时能力变化

只记录消息仍然不够。第三章中插件的挂载和卸载会改变工具列表与提示词；如果这些变化没有进入同一份记录，之后就无法解释某个 Step 当时为什么看到了某个工具。`sessionPlugin()` 将 Session Log 作为服务提供给 Context，并监听插件挂载、卸载事件，将它们追加为会话事实。

这一层连接了插件运行时和会话记录。它不负责生成模型请求，也不参与工具执行；职责是保证运行时发生的能力变化能够与消息、工具结果出现在同一条时间线上。

## 4.3 请求头给重建过程划出当时的边界

消息历史本身无法描述一份完整请求。系统规则、Tool Schema（工具名称与参数规则）、模型配置、本步说明和投影设置都可能随时间变化。**`request/header` 保存一个 Step 当时完整的输入边界。**Nano DSH 为每个 Step 写入它，重建时先按 `stepId` 找到这条头部，再只读取它之前的事件。

`buildRequest()` 接着寻找最近的上下文检查点，确定哪些旧事件已经被摘要覆盖；它把尚需读取的用户消息、模型回复和工具结果投影为模型消息。工具调用单独记录，重建模型回复时再按 Step 归回对应回复，最后调用第二章的 `projectMessages()` 生成当前模型视图。这里的数组处理之所以可靠，前提是前两节已经将足够细的事实写入日志。

## 4.4 回放和界面继续复用同一份事实

`replayTrace()` 读取同一批 `SessionEvent`，为每个事件生成页面要显示的标题和详情。**模型请求、回放与界面共享同一份事件事实。**它与 `buildRequest()` 面向不同用途，却没有维护另一份执行历史。新增一种展示或调试视图时，也能从日志派生，而不会改写模型输入。

<!-- fill {"index":4} -->

完整 DSH 会将 SessionEvent 写入 JSON Lines（JSONL，每行一条 JSON 记录）或 SQLite。Nano DSH 的日志保存在内存中，再把教学样本序列化为网站数据；两者共享的重点是请求、回放和展示都从同一条事件流获得依据。
