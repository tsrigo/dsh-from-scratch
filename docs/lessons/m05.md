# Agent 自己装一个工具

第四章的日志能恢复过去，但改变不了未来。如果任务进行到一半，发现当前工具不够用，Agent 能自己装一个吗？DSH 可以：Agent 先检查当前插件组成，确认能力缺口，再编写一个新的 Cordis 插件，挂载到当前 Context，并实际调用它提供的工具。这一章用一个最小实验走完这条路径：检查、定义、运行、验证、移除。

本章把路径浓缩为五个普通工具：`cordis_inspect` 查看当前插件组成，`cordis_define` 登记 Agent 编写的插件代码，`cordis_run` 挂载插件，`cordis_stop` 停止插件，`cordis_undefine` 停止插件并删除定义。Agent Loop 负责调用这些工具，Context 负责插件生命周期（第三章），Session Log 记录整个过程（第四章）。

## 5.1 先列出当前插件提供的能力

`cordis_inspect` 列出当前 Context 中已经挂载的 Plugin（插件），以及这些插件提供的 Tool、Prompt、Service 和依赖关系。Agent 根据这份结果判断现有工具能否完成任务，以及新插件需要提供什么。

实验开始时，过程日志和 Cordis 工具已经挂载，`word_count` 还不存在。第一张能力图是变化前的基线：插件列里没有 `dynamic:word_count`，工具列里也没有 `word_count`。后续每一步都对照这张图。

## 5.2 定义与挂载是两步

`cordis_define` 接收插件名称、用途和一段返回 Cordis Plugin 的 JavaScript 函数体。它先检查代码能否编译，再生成 `dyn-<n>` 形式的插件标识，把代码保存在定义表中。定义完成不会改变当前工具列表，模型还看不到任何新东西。

`cordis_run` 根据插件标识取出代码，在 Node.js 内置的 `node:vm` 代码执行环境中得到带有 `apply(context)` 的 Cordis Plugin，转换为 Nano DSH 的 Plugin 后，通过普通的 `context.mount()` 挂载。挂载时执行的注册沿用第三章的 effect 机制，返回的卸载函数保存在插件定义中，供停止或移除时使用。

挂载的效果从下一次模型请求开始出现：新请求会重新读取当前 Context。第二份请求的工具 Schema 从约 170 token 增加到约 214 token，新增的正是 `word_count` 的定义。Session Log 同时记录 `cordis_define`、`cordis_run` 和插件挂载事件，可以确定模型从哪次请求开始看到新能力。

## 5.4 调用新增工具，验证它真的可用

插件成功挂载只说明 `apply` 已经执行，不能证明新工具可以解决任务。Agent 还要调用插件提供的工具，根据 Tool Result 判断能力缺口是否已经补足。这个最小样本调用 `word_count`，参数是 `one two three`，返回 `words: 3`。

事件卡展示了这次验证：调用 `word_count` 的记录紧跟在插件挂载事件之后，结果 `{"words": 3}` 证明 Agent 刚刚定义的工具已经进入 Agent Loop 并正常执行。

## 5.5 实验结束，撤销并对照基线

`cordis_stop` 执行挂载时保存的卸载函数，移除插件提供的 Tool、Prompt 和其他内容，同时保留插件定义，之后可以再次运行。`cordis_undefine` 先停止仍在运行的插件，再从定义表中删除它。

第三张能力图重新使用同一份列表结构；与第一张图对照，`dynamic:word_count` 和 `word_count` 都已消失，插件和工具数量回到实验开始前的基线。一次完整的实验包含基线、处理、回滚三个状态。

## 5.6 一次完整的能力变化

这五个工具组成一次完整的能力变化：列出现有能力，编写插件，挂载插件，调用新增工具，再停止或移除插件。新增工具进入后续模型请求（第二章的投影），生命周期由第三章的机制管理，所有调用与事件写入第四章的日志。Agent 因此可以在执行中补齐自己的工具。
