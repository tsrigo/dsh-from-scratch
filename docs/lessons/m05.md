# 自进化不是任意改写，而是受控地更换运行时能力

“运行时自进化”很容易被理解成 Agent 可以随意下载代码、修改自身并永久保留。DSH 更可靠的起点要克制得多：Agent 能检查当前运行时，发现能力缺口，从受信任目录安装一个候选插件，用真实结果验证，再决定保留当前选择或撤回。

这不是模型参数的学习，也不是一条绕过权限的新路径。它是第三章插件生命周期对 Agent 开放后的结果：运行时原本就能安装和卸载能力，现在只是把这组操作做成了模型可调用、可记录的工具。

## 先取得基线，再谈改变

实验开始前，Agent 先调用 `inspect_runtime`。基线快照列出已经挂载的插件、工具、Prompt、Service 和依赖关系。没有这一步，后面即使多出一个工具，也无法判断它来自哪项安装，更无法验证卸载是否清理干净。

## 候选能力必须经过目录边界

`install_capability` 不接收任意代码或文件路径，只接受 Trusted Capability Catalog 中已经登记的名称。未知名称和重复安装会返回可读错误；命中目录后，能力仍通过普通的 `context.mount()` 进入运行时。安装工具自己还保存卸载函数，以便之后走同一条回滚路径。

<!-- evidence {"id":"m05-install-path","tab":"source","lines":[35,90],"label":"受信任目录与普通挂载","description":"检查目录约束、重复安装、插件挂载、卸载函数保存以及能力移除的完整路径。"} -->

安装完成后，变化不会神秘地注入正在进行的模型输出，而会体现在下一次请求中：工具 Schema 多出新动作；如果这个插件还贡献 Prompt，它也会进入系统规则。Session Log 同时记录插件挂载事件，于是“模型何时开始看见这项能力”有清楚的请求与时间边界。

## 验证的是结果，不是“安装成功”

挂载成功只说明代码进入了运行时，不说明它对当前任务有用。Agent 必须真正调用新工具，并用可观察结果判断能力缺口是否被填补。这个最小样本实际调用 `word_count`，得到 `words: 3`；这条 Tool Result 才是能力有效的证据。

<!-- evidence {"id":"m05-verified","tab":"events","eventType":"tool/result","eventOccurrence":1,"label":"实际调用与验证结果","description":"挂载事件之后真正调用 word_count，并记录 words: 3，而不是把安装成功当作验证。"} -->

若实验无效、任务结束或只是临时需要，就调用 `remove_capability`；插件带来的 Tool、Prompt 与其他贡献应当作为一组消失。卸载后的快照应当与基线对照，确认临时能力没有遗留在工具目录里。

<!-- evidence {"id":"m05-removed","tab":"graph","requestStep":3,"label":"卸载后的运行时基线","description":"对照最初快照，检查临时插件及其全部贡献是否已经从运行时消失。"} -->

所谓“持续”，指这条闭环可以在新的能力缺口出现时重复：检查现状，选择受信任候选，试装，实际使用，根据证据保留或回滚。每次变化都复用插件系统，都进入 Session Log，也都只从后续请求生效。

Nano DSH 演示的是这条最小、可解释的路径。生产系统还需要权限审批、代码签名、隔离环境和持久化策略；这些没有在本教程中实现。因此，本章证明的是受控的运行时适配，而不是无边界的自主学习。
