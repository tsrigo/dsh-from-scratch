# Agent 自己装一个工具

第四章的日志能够说明当前发生了什么，却不会自动增加能力。假设 Agent 需要统计一段文本中的单词数量，当前 Context 中没有 `word_count` 工具。继续猜测工具名或反复调用无关工具，只会消耗 Step，也不会缩小能力缺口。

DSH 将这类需要处理成受控的运行时变更：**先查看当前能力和接口，再挂载临时插件，调用新增工具验证结果，任务结束后释放插件。**它把前四章的机制放进一条完整路径：Agent Loop 负责发起动作，请求投影携带当前工具，插件生命周期管理进入和退出，Session Log 保存过程。

`runtime-tools.ts` 的骨架只定义两件事：动态插件保存哪些信息，以及 `runtimeToolsPlugin()` 怎样接入 Context。下面的实现会围绕同一张定义表展开，因此读者可以分清插件代码已被登记、插件正在运行、插件已经释放这三种状态。

## 5.1 先确认缺少什么，再决定补什么

`cordis_inspect` 返回当前 Context 中的插件、服务、工具、提示词和依赖关系。**先确认缺少什么，再决定补什么。**Agent 根据这份结果确认 `word_count` 缺失，再决定需要编写怎样的插件。能力图中的基线也很重要：它提供变更前的可比较状态，避免模型把已有能力误判为缺口。

Runtime Tools 自己也要维护生命周期。它用定义表保存动态插件，并在 Runtime Tools 退出时逆序停止仍在运行的插件、清空定义。与此同时，它注册检查工具和一段提示词，告诉 Agent 什么时候应该先检查、再定义和运行插件。这些准备让一次临时扩展拥有明确入口与收尾。

## 5.2 定义代码和挂载能力是两个时刻

检查确认缺口后，Agent 通过 `cordis_define` 提交插件名称、用途和 JavaScript 代码。**定义代码和挂载能力是两个时刻。**函数先编译代码，再将定义放进表中；此时工具列表没有变化。`cordis_run` 取回定义、实例化 Plugin，并调用第三章的 `context.mount()`，挂载成功后，新工具才进入当前 Context。

区分这两个时刻有实际用途。定义阶段可以报告代码是否可加载，挂载阶段可以报告插件是否真的改变了运行时；失败时也能准确指出发生在哪一步。官方 DSH 提供 `cordis_inspect`、`cordis_mount` 和 `cordis_unmount`，临时插件同样直接作用于当前进程，并在卸载或进程结束后消失。

## 5.3 结果验证和释放让变更形成闭环

插件挂载成功后，`dynamic:word_count` 出现在插件列表中，`word_count` 出现在工具列表中。**新工具从后续模型请求开始可见。**下一次模型请求重新读取 Context，因此 Tool Schema 增加新工具的名称和参数规则；已经发出的请求保持原样。

Agent 调用 `word_count` 并得到 `words: 3`，这才证明新能力已经穿过 Agent Loop 并完成任务。

<!-- evidence {"id":"m05-verified","tab":"events","eventType":"tool/result","eventOccurrence":4,"label":"调用结果验证新增能力","description":"查看 word_count 的工具结果，确认新增工具已经完成一次真实调用。"} -->

验证完成后，`cordis_stop` 执行挂载时取得的卸载函数并保留定义，方便稍后再次运行；`cordis_undefine` 则先停止仍在运行的插件，再删除定义。辅助函数负责编译、实例化和读取参数，让这些 Tool 的主体能集中表达状态转换。`node:vm` 仅用于可信教学样本的加载，实际部署仍需要明确权限与启用边界。
