# M05 · 创造模式的核心，不是任意改代码

固定组装已经可检查，但恢复审计还想验证一套透明的路由评分规则。我们不把它永久塞进 preset，也不开放 npm、Shell 或任意路径加载。

常驻 `runtime-tools` 只提供三个普通工具：检查当前运行时、按名字安装受信任能力、移除由它安装的能力。catalog 只有 `route_scoring` 和机制级示例 `word_count`。安装调用普通 `ctx.mount()`，卸载保存下来的同一个 disposer；Session Log 因而自然收到插件事件，下一 step 的 header 也自然捕获新 Prompt 和 `score_routes` schema。

贯穿 Trace 的变化是可验证的：安装前没有 `score_routes`；安装后的下一次请求出现工具与评分规则；调用后卸载；再下一次请求二者一起消失。`word_count` 的独立测试补足“安装前不可见—安装后调用—卸载后消失”的最小边界。

这对应创造模式最重要的内核：看清组装，受控试装，验证结果。完整 DSH 的创造模式还具备标准模式全部能力与 preset 创作指导，最终会把验证过的插件选择写成可发现、可加载的自定义 preset。Nano 到实验为止，不生成 preset 文件，也不把临时挂载冒充完整创作流程。
