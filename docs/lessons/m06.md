# 让任务跨过 Turn 继续

第五章可以在任务中补齐工具，当前模型停止调用工具时，一个 Turn 仍会结束。任务是否完成需要另一层判断。整理三条发布说明时，第一轮可能只收集到两条；模型暂时给出回复，目标依然处于进行中。

DSH 将长期目标放在 Agent Loop 外管理。**Goal 决定跨轮任务是否继续，Turn 和 Step 继续承担模型请求与工具执行。**Goal（目标）保存跨轮状态，Round（续行轮次）代表一次新的推进尝试。四层分别检查各自的停止条件，当前没有工具调用因而不会直接决定目标已经完成。

`long-task.ts` 先定义 Goal 状态、每轮输入和每轮结果，再给出 `LongTaskRunner` 的轮廓。它只持有目标、会话和 `runRound` 回调；具体 Agent、Context 与工作区由调用方在每轮中继续复用。这个边界让长程协调只做它需要做的事：决定是否再启动一次普通 Turn。

## 6.1 Goal 需要保存能跨轮检查的状态

构造 `LongTaskRunner` 时，代码固定目标文本、最大轮数、初始状态和下一轮将使用的定义。`run()` 开始时把 `goal/created` 写入 Session Log（会话日志），**Goal 从一开始就进入可回放的事实流。**这里没有请求模型；它在为多轮执行建立共同边界。

把状态集中在 `LongTaskState` 有两个作用。外层可以在每轮后读取统一的状态、原因和已开始轮数，页面和恢复逻辑也可以从日志查到目标何时创建。源码把初始化和创建事件放在一起，读者能看到状态对象与记录事实如何保持一致。

## 6.2 下一轮仍然调用普通 Agent Loop

Goal 处于 `active` 时，运行器先检查轮数上限和是否存在下一轮定义。通过检查后，它递增轮次、写入 `goal/round-started`，再调用 `runRound`。回调中可以把这一轮交给与前一轮相同的 Agent、Context、工作区和 Session Log；前几章写入的消息、工具结果和插件变化因此仍然可用。

这一层没有复制第一章的工具循环。**Goal 可以启动新的 Turn，却不重写 Agent Loop。**它只负责为下一次 Turn 划定轮次边界，普通 Agent Loop 继续处理模型请求、工具调用和反馈。将两层循环分开后，模型停止工具调用与 Goal 是否继续推进可以独立判断。

## 6.3 续行要依据可观察的结果

`runRound` 返回 `RoundResult`。`completed` 表示目标已经达成，`blockedReason` 说明无法继续，`progressed` 表示本轮产生了预期进展。运行器据此结束 Goal、标记受阻、处理轮数上限，或保留 `active` 状态进入下一轮。每个出口都写入 `goal/status-changed`，因此状态转换也能进入同一条会话记录。

代码中把这些分支和 `#finish()` 放在一起，是为了让结束状态总是同时更新内存状态和 Session Log。**只有本轮确实有进展、目标尚未完成且未到上限时，循环才会继续。**这个条件比单纯重复调用模型更接近 DSH 对长程任务的约束。

## 6.4 六章放回同一条 DSH 运行时主线

一次 Step 先在 Agent Loop 中完成模型与工具的往返；上下文层决定该 Step 能看到哪些信息；插件运行时决定当前有哪些能力；Session Log 将输入、动作和能力变化保存为共同事实；Runtime Tools 在任务中补齐能力；Goal 和 Round 则在一个 Turn 结束后判断任务是否需要继续。

这条关系也说明 DSH 的重点超过单次模型调用。它把执行、能力、记录和目标状态组织成可以检查、替换和续行的运行时。Nano DSH 保留其中最小的一组关系，完整 DSH 在此基础上增加配置层、持久化、权限、沙箱和更多运行时提供方。
