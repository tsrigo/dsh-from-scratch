# 插件统一管理运行时能力的生命周期

DSH 使用 Cordis 把插件和子插件组成一棵有层级关系的插件树，以此组装一个可以运行的 Agent。函数形式的插件通过 `apply(ctx)` 取得 Context。Context 是插件共享的注册入口，其中包含 Service、Tool、Prompt 和 Event Listener 等运行时对象：Service 是插件之间共享的具名能力，Tool 是模型可以请求的操作，Prompt 为模型补充系统规则，Event Listener 负责处理运行期间发出的类型化事件。

第三章所说的一切皆插件，是指 DSH 的运行能力都由插件提供，并随插件一起加载和卸载。一个插件可以同时提供服务、注册工具、贡献提示词和监听事件，这些内容共享同一段生命周期。

## Context 连接能力的提供方和使用方

完整 DSH 使用 `inject` 声明插件需要哪些 Service。Cordis 会在依赖就绪后调用插件的 `apply(ctx)`；服务提供方卸载后，依赖它的插件也会卸载，并在服务恢复后重新加载。应用启动时读取的 `cordis.yml` 负责选择插件树，插件之间的依赖关系决定实际加载时机。

Nano DSH 把这套关系浓缩为 `Plugin.setup(context)` 和 `Context.mount()`。插件通过 `provide()` 提供 Service，通过 `use()` 获取 Service。Context 会记录 provider（提供方）、consumer（使用方）和 Service 名称，页面据此展示当前插件之间的依赖关系。`registerTool()`、`contributePrompt()` 和 `on()` 则分别注册 Tool、Prompt 和 Event Listener，并记录提供这些内容的插件。

Agent Loop 每次发起模型请求前，都会从 Context 读取当前 Tool 和合并后的系统 Prompt。插件加载或卸载后，后续请求会使用更新后的工具列表和系统规则。

## Effect 让插件贡献可以随插件撤销

Cordis 把插件注册的内容视为 effect（随插件生命周期管理的操作）。`ctx.on()`、`ctx.plugin()`、服务注册和 `ctx.tools.register()` 等接口会把对应的 disposer（资源释放函数）绑定到当前插件。定时器、连接等由插件自行创建的资源，也可以通过 `ctx.effect()` 登记释放方法。插件卸载或热重载时，Cordis 会执行这些 disposer。热重载是指代码更新后卸载旧插件，再加载新插件。

Nano DSH 使用一段更短的代码表达同一条路径。插件在 `setup()` 期间注册每项内容时，Context 会把对应的清理函数加入当前插件的 effect 栈。`setup()` 成功后，`mount()` 返回一个只生效一次的卸载函数。调用这个函数时，Context 按相反顺序执行清理函数，同时移除该插件提供的 Service、Tool、Prompt 和 Event Listener。

如果 `setup()` 中途抛出错误，`mount()` 会沿同一个 effect 栈撤销已经完成的注册，使 Context 回到挂载前的状态。主动卸载和加载失败因此共用一套清理机制。

Context 提供统一的注册入口，插件说明一组能力来自哪里，effect 保存对应的撤销方法。DSH 因此可以通过插件树组装运行能力，并在配置变化、热重载和运行时调整时更新当前插件组合。第五章会把 Nano DSH 的插件检查、定义、运行和移除操作提供给 Agent。
