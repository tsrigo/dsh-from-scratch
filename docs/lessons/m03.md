# 插件统一管理运行时能力的生命周期

一个 Agent 的能力包含多种运行时对象。Tool 表示模型可以请求的操作，Service 提供共享服务，Prompt 提供行为规则，Listener 订阅运行事件，工具还可能依赖其他服务。如果这些对象分别使用全局变量注册，并由不同代码清理，运行时会积累难以检查和卸载的隐式状态。

DSH 让所有运行时能力通过 Plugin（插件）安装。第三章所说的一切皆插件，要求每项运行时贡献都记录来源插件，并提供在插件移除时撤销该项贡献的方法。普通对象无须改写成插件类。

## Context 提供统一注册入口

Plugin 在 `setup()` 中取得同一个 Context（运行时上下文），随后可以提供 Service、注册 Tool、贡献 Prompt 或订阅 Event。Context 在安装期间记录当前插件名称，为每项注册内容添加 owner（来源插件）。一个插件使用另一个插件的 Service 时，Context 还会记录 consumer（使用方）、service（服务）与 provider（提供方）的关系。这些记录用于检查依赖关系，不处理版本选择、拓扑排序和级联卸载。

Agent Loop 只从 Context 读取当前工具目录和合并后的系统 Prompt，不需要处理能力的安装过程。插件关系保持不变时，请求中的工具与规则也保持不变。卸载或重新挂载插件后，Context 会在下一次请求中提供更新后的能力列表。Nano DSH 没有实现原子替换操作。

## 注册能力时登记撤销动作

来源记录无法单独完成卸载。Context 在挂载开始时建立 effect 栈，即按顺序保存副作用清理函数的列表。每次注册能力时，对应的清理函数也会加入这个列表。`setup()` 全部成功后，Context 才确认挂载完成，并返回一个只生效一次的 disposer（卸载函数）。

如果 `setup()` 执行到一半抛出错误，Context 会按相反顺序执行已经登记的清理函数，使运行时恢复到安装前的状态。主动卸载使用同一组清理函数。反向执行可以让后注册且可能依赖前项的贡献先退出。

Nano DSH 假定 cleanup（清理函数）能够正常完成，也没有实现完整的依赖事务。生产实现还需要在 `finally` 代码块中清除挂载状态，并处理部分 cleanup 失败。本章实现仅覆盖插件生命周期所需的最小机制。

统一生命周期带来三个直接结果。owner 让运行时能够列出能力来源；disposer 让插件可以完整卸载后重新安装；同一组清理函数会同时移除 Tool、Prompt 和 Listener，避免只清理部分贡献。第五章会让 Agent 在受控范围内调用这里已经定义的安装与卸载操作。

Context 负责统一注册，owner 记录来源，disposer 撤销插件产生的全部影响。这三项机制让不同类型的运行时能力遵循同一套安装、检查和卸载流程。
