# 一切运行能力都由插件提供

第二章的请求里，Tool Schema 和系统规则是组装好的。谁提供这些内容？DSH 的答案只有一个：插件。而且这个答案没有例外：模型适配器、工具注册表、会话日志、Agent Loop 本身都是插件。DSH 的设计里不存在需要打补丁的特权内核，扩展 DSH 的方式是把插件挂载到其他插件旁边。这一章回答：插件如何组装运行能力，又如何安全地拆掉？

## 3.1 Context 连接能力的提供方和使用方

插件组成一棵有层级关系的插件树。每个插件在挂载时取得 Context（运行时上下文），这是插件共享的注册入口。Context 里的运行时对象有四种：Service 是插件之间共享的具名能力，Tool 是模型可以请求的操作，Prompt 为模型补充系统规则，Event Listener 负责处理运行期间发出的类型化事件。

插件通过 `provide()` 提供 Service，通过 `use()` 获取 Service。完整 DSH 用 `inject` 声明插件需要的 Service，服务就绪后才调用插件的 `apply(ctx)`；服务提供方卸载后，依赖它的插件也会卸载，并在服务恢复后重新加载。Nano DSH 把依赖关系压缩为 `provide()` 与 `use()`，Context 记录 provider（提供方）、consumer（使用方）和服务名称，不处理版本选择、拓扑排序和级联卸载。

能力图卡展示本章样本的归属关系：插件 `clock-core` 提供名为 `clock` 的服务，插件 `clock-tools` 注册工具 `get_time`、贡献提示词 `clock-rule`，并通过 `use()` 依赖 `clock`。Agent Loop 每次发起模型请求前，从 Context 读取当前工具列表和合并后的系统 Prompt；插件加载或卸载后，下一次请求就会使用更新后的内容。

## 3.2 注册是可逆的副作用

如果工具、提示词和监听器分别用全局变量注册，卸载时没有人知道该撤销什么。插件方案把注册和撤销绑在一起：插件在 `setup()` 期间注册每项内容时，Context 把对应的清理函数加入当前插件的 effect 栈。`setup()` 全部成功后，`mount()` 返回一个只生效一次的卸载函数。

调用卸载函数时，Context 按相反顺序执行清理函数，同时移除该插件提供的 Service、Tool、Prompt 和 Event Listener。如果 `setup()` 中途抛出错误，`mount()` 沿同一个 effect 栈撤销已经完成的注册，使 Context 回到挂载前的状态。主动卸载和加载失败因此共用一套清理机制。

反向顺序有一个实际理由：后注册的内容可能依赖先注册的内容，先撤销依赖方，再撤销被依赖方。Nano DSH 假定清理函数能够正常完成，没有实现完整的依赖事务；生产实现还需要确保部分清理失败时仍清除挂载状态。

## 3.3 统一生命周期带来的三个结果

owner（来源插件）记录让运行时能够列出能力来源；disposer（卸载函数）让插件可以完整卸载后重新安装；同一组清理函数会同时移除 Tool、Prompt 和 Listener，避免只清理部分贡献。三种运行时能力因此遵循同一套安装、检查和卸载流程。
