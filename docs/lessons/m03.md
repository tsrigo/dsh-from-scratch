# 一切运行能力都由插件提供

第一章的 `Agent` 直接拿到工具和系统规则，第二章把这些内容排进请求。这样的起点便于理解循环，能力一多，修改会集中到少数构造器和全局状态里：新增工具、替换模型适配器、改变工作区设置，都可能碰到同一片核心代码。

DSH 用 Cordis 组织这类变化。Cordis 是 DSH 使用的 TypeScript 插件运行时：**模型适配器、工具注册表、会话日志和 Agent Loop 都作为插件加入同一棵运行时树。**Profile（具名组装）、Bundle（插件组合包）和 Patch（配置覆盖）决定当前树包含哪些插件。Nano DSH 省略配置加载过程，保留最关键的运行时约束：**每项能力有来源，安装后能完整撤销。**

`runtime.ts` 先把这套约束写成插件契约、服务令牌和 `Context` 的内部状态。`Context` 保存当前插件、服务、工具、提示词、监听器与依赖关系；这些容器共同回答一个问题：当前 Agent 能用什么，以及这些能力从哪里来。

## 3.1 安装一项能力时，先确定它的生命周期

Plugin（插件）是一次安装和卸载的单位。它拿到 `Context`（运行时上下文）后，可以提供 Service（供其他插件调用的服务）、注册 Tool（模型可调用的操作）、补充 Prompt（系统规则片段），也可以监听运行时事件。能力图中的 `clock-core` 提供 `clock` 服务，`clock-tools` 取用该服务并注册 `get_time` 工具，归属和依赖因此可以沿图追溯。

安装时最容易遗漏的是中途失败的状态。一个插件可能已经注册服务，又在注册工具时抛出错误；如果此前的贡献留在 Context 中，之后的运行状态就无法可信。`mount()` 因此先建立安装记录，执行 `setup()`，并把每个清理动作收集到同一条 effect 栈。**安装失败和主动卸载沿同一条逆序清理路径处理。**

## 3.2 注册能力时，同时记录它如何退出

`effect()` 是这套生命周期的公共入口：它只在插件安装期间可调用，并将一次清理函数交给当前安装记录。`provide()` 保存服务及其来源插件，`use()` 读取服务并在安装期记录使用方和提供方之间的关系。**注册一项能力时，也同时登记它的清理动作和来源。**这样，工具看到的依赖不再只是一个对象引用，运行时还能说明它属于哪次安装。

这段实现处理的是插件之间的协作边界。`clock-tools` 在 setup 中通过 `use(clock)` 取得服务，随后注册工具；卸载时，后注册的清理动作先执行，相关工具和依赖记录会一并撤销。这里的顺序来自已登记的事实，无需为每类能力再写一套专门的退出流程。

## 3.3 同一条账目覆盖工具、提示词和监听器

工具、提示词和监听器的参数各不相同，运行时对它们采用相同的登记方式：写入带 owner（来源插件）的容器，再把删除动作交给 `effect()`。读取方法从这些容器派生出工具列表、编译后的提示词和 `inspect()` 的能力快照；`#requireMount()` 与 `#rollback()` 则守住安装期和清理期的边界。

源码的这一段把贡献登记、状态读取和回滚辅助集中在 `Context` 内。它让每个插件都沿同一套规则接入运行时，也让 `inspect()` 可以把当前插件、服务、工具、提示词和依赖关系交给模型或页面查看。

## 3.4 这正是 DSH 与常见 Harness 拉开距离的地方

工具循环和上下文投影在许多 Harness 中都很常见。**DSH 进一步把组成这些机制的能力也放进插件树。**配置描述当前组合，插件生命周期管理贡献的进入和退出，运行时检查工具可以追溯来源和依赖。这使模型、工具、会话和 Agent Loop 能按任务和环境重新组装。

Nano DSH 只展示服务关系、归属与可逆 effect。完整 DSH 还包含依赖注入、等待服务就绪、配置层叠和隔离作用域。保留的这一小段代码足以说明整套架构的中心关系：能力通过插件进入 Context，也通过同一条生命周期离开 Context。
