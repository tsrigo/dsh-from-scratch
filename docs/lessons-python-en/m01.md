# One Tool Round-Trip: Where the Agent Loop Starts

Consider one concrete task: the user asks for the current time in Beijing. The model understands the question, but it has no live data. It needs to call `get_time`, read the returned value, and then answer. That sequence puts the model, a tool, and the runtime on one execution path, which later DSH mechanisms rely on.

Many Agent Harnesses can complete one tool call. DSH becomes distinct in the way it organizes the surrounding runtime: tools, prompts, sessions, and the Agent Loop can be assembled as plugins, while execution facts enter one shared log. The Python teaching version starts with the minimum loop and adds these responsibilities in later chapters.

`agent.py` declares the `Llm` model protocol, the `Tool` data structure, an argument checker, and `Agent`. Keep one boundary in view before reading the implementation: **the model proposes the next step; the runtime prepares input, validates and executes tools, then saves feedback.**

## 1.1 Why One Answer Can Span Multiple Steps

On its first request, the model receives system rules, the parameter definition for `get_time`, the user question, and the current Step number. None of that reveals the current time, so it returns a Tool Call. The runtime executes the query and adds its result to message history. A second request includes that new fact. When the model returns ordinary text without a tool call, the Turn ends.

**A Step is one model request together with the tool execution it triggers; a Turn can contain several Steps.** `validate_arguments()` covers the small JSON Schema subset used in this tutorial, while `Agent.__init__()` fixes the model, tool table, and maximum Step count. Each iteration can then start from the same dependencies.

<!-- fill {"index":1} -->

Only after that setup does `run()` process the user objective. It writes the objective to `messages`, builds a request for every Step, calls the model, and writes model text back into history. When there are no `tool_calls`, the current reply is final. When calls exist, the loop enters its tool-execution phase. Request construction, the model reply, and the stop check share one control flow.

## 1.2 Tool Execution Needs One Feedback Path

The model can provide a tool name and arguments, but it cannot decide whether execution is valid or succeeds. The runtime must find the tool, check its arguments against a Schema, and await the tool function. A successful query, an unknown tool, invalid arguments, and a thrown exception all need to return through the same kind of tool-result message.

`run()` keeps this work in the loop over `tool_calls`. **Successes and failures both return as tool results in message history.** Unknown tools and invalid arguments create an `error` first. Exceptions from a normal call are wrapped as an `error` as well. Every outcome returns as a message with `role: "tool"`, so the next request reads a consistent feedback shape and can adjust parameters or choose another action.

## 1.3 Where This Loop Sits in DSH

This minimal implementation turns a tool round-trip into inspectable program flow, while still keeping the tool catalog and message history directly inside `Agent`. Longer tasks grow request input; runtime changes crowd the constructor; and history held only in memory cannot support replay after the process ends.

Full DSH preserves this execution boundary while assigning input projection, capability assembly, and session recording to dedicated runtime mechanisms. Understanding the Step and Turn in this chapter makes it possible to see which part of the loop each later mechanism supports.
