# Every Runtime Capability Comes from a Plugin

In Chapter 2, the Tool Schema and the system rules in the request are assembled content. Who provides them? DSH has a single answer: plugins. And the answer has no exceptions: the model adapters, the tool registry, the session log, and the Agent Loop itself are all plugins. There is no privileged kernel that needs patching in DSH's design; extending DSH means mounting a plugin next to other plugins. This chapter answers: how do plugins assemble runtime capabilities, and how are they removed safely?

## 3.1 Context Connects Capability Providers and Consumers

If tools, Services, and prompts were registered through separate global variables and cleaned up by unrelated code, the runtime would accumulate implicit state that is difficult to inspect and unload. The plugin approach brings every runtime capability into one registration flow. A Plugin receives a Context, the runtime context, when it mounts, and can then provide a Service, register a Tool, contribute a Prompt, or subscribe to Events.

The Context records the current plugin name during mounting and attaches an owner to every registered contribution. When one plugin uses another plugin's Service, the Context also records the consumer, the service, and the provider. These records support dependency inspection; they do not handle version selection, topological ordering, or cascading unloads.

The capability graph card shows the ownership in this chapter's sample: the plugin `clock-core` provides a Service named `clock`, the plugin `clock-tools` registers the `get_time` tool, contributes the `clock-rule` prompt, and depends on `clock`. Before each model request, the Agent Loop reads the current tool list and the merged system Prompt from the Context; after a plugin loads or unloads, the next request uses the updated content.

## 3.2 Registration Is a Reversible Side Effect

An owner record only answers where a capability comes from; unloading still needs a removal method. The Context builds an effect stack at the start of mounting, a list that stores side-effect cleanup functions in order. Each capability registration adds its cleanup function to this list. Only after `setup()` succeeds does the Context confirm the mount and return a disposer, an unload function whose cleanup runs at most once.

Calling the disposer executes the registered cleanup functions in reverse order and removes the Services, Tools, Prompts, and Listeners provided by the plugin. If `setup()` throws halfway through, the Context walks the same effect stack to roll back and restore the runtime to its pre-install state. Explicit unloads and failed loads share the same set of cleanup functions.

The reverse order has a practical reason: content registered later may depend on content registered earlier, so dependents are removed before their dependencies. Nano DSH assumes cleanup functions complete normally and does not implement full dependency transactions; production implementations also need to ensure the mount state is cleared when some cleanups fail.

## 3.3 Three Results of a Unified Lifecycle

The owner lets the runtime list where each capability comes from. The disposer lets a plugin unload completely and remount. The same set of cleanup functions removes Tools, Prompts, and Listeners together, so partial cleanup cannot leave stale contributions behind. Three kinds of runtime capabilities therefore follow one install, inspect, and unload flow.
