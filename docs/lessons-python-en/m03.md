# Plugins Provide Unified Lifecycle Management for Runtime Capabilities

An Agent's capabilities include several types of runtime objects. A Tool is an operation that the model can request. A Service provides a shared capability. A Prompt adds behavior rules. A Listener subscribes to runtime events. Tools may also depend on other Services. If these objects are registered through separate global variables and cleaned up by unrelated code, the runtime accumulates implicit state that is difficult to inspect and unload.

DSH installs every runtime capability through a Plugin. In Chapter 3, *everything is a plugin* means that each runtime contribution records the Plugin that provided it and supplies a way to reverse that contribution when the Plugin is removed. Regular objects do not need to be rewritten as Plugin classes.

## Context Provides One Registration Interface

A Plugin receives the same Context during `setup()`, then can provide a Service, register a Tool, contribute a Prompt, or subscribe to an Event. During installation, the Context records the current Plugin name and adds an owner to each registered contribution. When one Plugin uses a Service from another Plugin, the Context also records the consumer, Service, and provider relationship. These records support dependency inspection. They do not handle version selection, topological ordering, or cascading unloads.

The Agent Loop only reads the current tool catalog and combined system Prompt from the Context. It does not need to handle capability installation. While the Plugin composition remains unchanged, the tools and rules in the request also remain unchanged. After a Plugin is unloaded or mounted again, the Context provides the updated capability list in the next request. Nano DSH does not implement atomic replacement.

## Registering a Capability Also Records Its Cleanup

Source records alone cannot unload a Plugin. When mounting begins, the Context creates an effect stack, which stores a list of cleanup functions for side effects in registration order. Each registered capability adds its corresponding cleanup function to this list. The Context confirms the mount only after `setup()` completes successfully, then returns a disposer that takes effect only once.

If `setup()` throws an error before it finishes, the Context executes the cleanup functions already registered in reverse order and restores the runtime to its state before installation. An explicit unload uses the same cleanup functions. Reverse order lets later contributions, which may depend on earlier ones, exit first.

Nano DSH assumes that cleanup functions complete successfully and does not implement a complete dependency transaction. A production implementation must also clear the mount state when part of cleanup fails. This chapter implements only the minimum mechanism required for the Plugin lifecycle.

A unified lifecycle has three direct results. The owner lets the runtime list the source of each capability. The disposer lets a Plugin be completely unloaded and then installed again. The same cleanup functions remove Tools, Prompts, and Listeners together, which prevents contributions from being only partially removed. Chapter 5 lets the Agent call the installation and unload operations defined here within controlled limits.

The Context provides one registration interface, the owner records each source, and the disposer reverses every effect produced by a Plugin. These three mechanisms give different types of runtime capabilities the same installation, inspection, and unload process.
