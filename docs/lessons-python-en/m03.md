# Every Runtime Capability Comes from a Plugin

Chapter 1 gives `Agent` its tools directly, and Chapter 2 places those tools into a request. That starting point makes the loop easy to understand. As capabilities multiply, changes begin to gather in a few constructors and global states: adding a tool, replacing a model adapter, or changing workspace settings can touch the same core code.

Full DSH uses Cordis to organize this change. Cordis is the TypeScript plugin runtime used by DSH: **the model adapter, tool registry, Session Log, and Agent Loop all join one runtime tree as plugins.** The Python teaching version retains the shared lifecycle constraint: **every registered capability has an owner and can be withdrawn through a cleanup path.** It implements Tool and Prompt registration directly, while reserving `services` and `listeners` containers for future extensions.

`runtime.py` first defines the plugin protocol, `Contribution` records with an owner, and the state held by `Context`. This Python sample has no `provide()`, `use()`, or dependency-relation API, so the chapter focuses on a capability's source, installation, and complete removal.

## 3.1 Give a Capability a Lifecycle Before Installing It

A Plugin is one unit of installation and removal. With a `Context`, it can register a Tool or contribute a Prompt inside `setup()`. `Context` stores the value and owner for every contribution and creates a separate effect stack for the plugin currently being installed. The runtime can then answer which tools and prompts exist and which installation supplied them.

The difficult state appears when installation fails halfway through. A plugin can register a tool and then throw while contributing a prompt. Leaving its earlier contribution in `Context` makes later state unreliable. `mount()` creates an effect list, runs `setup()`, and collects every cleanup action there. **A failed installation and an intentional unload follow the same reverse cleanup path.**

## 3.2 Registering a Capability Also Records How It Leaves

`effect()` is the common lifecycle entry point. It can run only during plugin installation and adds one cleanup function to the current plugin's list. `register_tool()` writes a tool and its owner to the table, then registers an action that deletes the entry. `contribute_prompt()` does the same for a prompt. **Registering a capability also registers its cleanup action and source.**

The order has a practical purpose. Later cleanup actions run first during an intentional unload, so related contributions leave in reverse registration order. The `disposed` flag in `mount()` also makes the returned unload function effective only once. This Python version does not implement the full DSH Service-injection and cascading-dependency behavior, yet it retains the reversible installation boundary those mechanisms rely on.

## 3.3 One Record Covers Tools and Prompts in This Sample

Tools and prompts have different parameters, yet the runtime registers them in the same way: write a contribution with its owner, then give a removal action to `effect()`. `inspect()` derives a snapshot of current plugins, tools, and prompts from those containers. `_require_owner()` prevents a runtime mutation outside an installation.

This source segment keeps contribution registration, state reads, and rollback helpers inside `Context`. **Every plugin enters the current Python runtime through the same rule set.** Services, listeners, and dependency relationships should join the same owner-and-effect lifecycle if the implementation expands.

## 3.4 Where DSH Separates from Many Harnesses

Tool loops and context projection are common in many Harnesses. **DSH also puts the capabilities that compose those mechanisms into the plugin tree.** Configuration describes the current assembly, plugin lifecycles manage contributions entering and leaving, and runtime inspection can trace ownership and dependencies.

The Python teaching version shows the smaller Tool-and-Prompt lifecycle. Full DSH also includes dependency injection, waiting for services to become ready, layered configuration, and isolated scopes. The difference is one of implementation scope; the central relationship remains the same: capabilities enter the runtime through an inspectable installation and leave through the same lifecycle.
