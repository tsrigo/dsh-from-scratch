# Session Log Stores Events and Generates Other Views

A `messages` array can store conversation content, but it usually lacks the information needed to explain an Agent run, such as the system rules, tool catalog, and projection settings used for a particular Step. It is also difficult to determine when a plugin was installed, which call produced a Tool Result, or why the Agent stopped at a given point.

DSH records observations from a run as Events. User input, Step starts, request headers, model responses, Tool Calls, Tool Results, Context checkpoints, and runtime changes are all written to one Session Log, with an event type and an incrementing ID.

## Events Record Facts, While the Trace Presents Them

The log follows an append-only rule: new events can only be added at the end, and recorded events are never modified in place. This preserves the causal order of events. A Tool Result appears after its corresponding call and before the next request, which shows how it enters the subsequent Context.

The panel on the right selects the six events needed for one tool round trip. They show the order of the user message, first request, model Tool Call, Tool Result, and second request. The complete implementation also records Turns, Steps, Context checkpoints, and runtime events in the same Session Log.

## Any Step's Request Can Be Reconstructed from the Log

To reconstruct a Step, `build_request()` first finds its `request/header`. The Header event stores the system rules, Tool Schema, instructions for the Step, and projection settings in effect at that point. User, model, and tool events before the request header are restored as messages in their original order. Each Tool Result retains the name of the tool that produced it.

If the history contains a checkpoint, the request builder represents the older events covered by the checkpoint with a summary, then appends the newer events that follow it. The original Events remain in the Session Log. A checkpoint changes only the projection used for the current model request. This gives the separation between the complete record and the model input from Chapter 2 a reconstructable data structure.

The page also generates its Trace, or execution trace view, from Events. Event types become readable titles and descriptions, while the original payload remains available for inspection. Request inspection, the execution timeline, and capability changes therefore refer to the same record without maintaining separate copies that could become inconsistent.

This chapter reconstructs one semantically equivalent request. It does not guarantee a byte-for-byte match with the original request sent to the model provider. Replay converts the Events into a Trace again; it does not call the model or execute tools. Model streaming chunks, network retries, and provider request IDs are outside this minimal log.

Nano DSH currently keeps the Session Log in memory. This is enough to demonstrate recording, reconstruction, and replay, but the log cannot survive a process restart. Cross-process persistence could append the same Events to a JSON Lines file (JSONL, one JSON record per line) or a database. The storage medium does not change the event structure presented in this chapter.

DSH records observations as Events, preserves their order in the Session Log, and generates Requests and Traces from the same record. A checkpoint changes the model's view without deleting historical events. Together, these mechanisms explain how an Agent run can be recorded, stored, and inspected.
