# What the Model Sees Is What Gets Logged

The first three chapters produce several kinds of state: user messages and Tool Results make up model history, plugins change the available tools and prompts, and the page needs to show execution. If these details live separately in message arrays, debug output, and UI state, one run can quickly acquire conflicting versions of its own history.

**Full DSH writes runtime facts to one append-only Session Log first, then derives model history, replay, UI, and persisted data from that log.** This order establishes a checkable constraint: **anything visible to the model should be reconstructable from the record.** The Python teaching version implements the smallest form of that relationship: events append in order, and requests and Traces read from the same set of events.

`session.py` defines `Event` and `SessionLog`. Each Event contains only an increasing identifier, a type, and data. The caller explicitly decides when to append a user message, request header, or Tool Result. This reduction keeps the relationship between event order and request reconstruction visible.

## 4.1 Save Facts in the Order They Occur

One tool round-trip passes through a user message, request header, model response, external tool execution, and Tool Result. This Python minimum version asks its caller to append the user message, request header, model response, and Tool Result; it does not automatically create a separate Tool Call event. `SessionLog.append()` uses the current length to create an increasing identifier and then appends the new Event. The identifier lets the page point to a definite event. **Append order preserves causality: a Tool Result follows external execution and precedes the next request.**

`request_step_ids()` reads the identifiers of reconstructable Steps from `request/header` events. It does not copy history or infer an event's meaning; the index still points to the same append-only record. Keeping identifiers and this index in one small class prepares stable input for the reconstruction function that follows.

## 4.2 The Log Must Cover Model-Visible Facts

In full DSH, plugin mounts and unloads change tools and prompts. Those changes need to enter the same record so that a later reader can explain why a Step saw a particular tool. The TypeScript implementation's `sessionPlugin()` listens for runtime changes and appends events.

The Python teaching version keeps a clearer boundary here: `SessionLog` does not attach to `Context` automatically, so its caller invokes `append()` when a fact occurs. **This code demonstrates a shared event source; it does not yet record plugin changes or execution stop reasons automatically.** When runtime listeners are added, their new events should join this same log instead of creating another history.

## 4.3 A Request Header Marks the Boundary at That Time

Message history alone cannot describe a complete request. System rules, tool definitions, and Step instructions can all change over time. `build_request()` first locates the target `request/header` through `step_id` and reads only events before that header. **The request header stores the input boundary of a Step at the time it ran.**

The code then finds the newest `context/checkpoint`. When one exists, its summary becomes a system message and events after it continue to become messages one by one. `_message_from()` handles only user, assistant, and Tool Result events, preserving the tool name for a tool message. The Python minimum version does not record separate Tool Calls or apply Chapter 2's clipping again here; it shows the basic method for restoring the current request from event order.

## 4.4 Trace and Requests Reuse the Same Facts

`trace()` iterates through the same Events and creates display objects with an `event_id`, type, and data. **Request reconstruction and Trace share one event-based source of facts.** They serve different purposes without maintaining a second execution history.

Full DSH writes SessionEvents to JSON Lines, or JSONL, where each line is one JSON record, or to SQLite, and connects the Session Log to its plugin runtime. The Python teaching version currently keeps facts in memory and lets the tutorial generator serialize samples. Both emphasize that requests and display views need the same event stream as evidence.
