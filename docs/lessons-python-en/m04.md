# What the Model Sees Is What Gets Logged

At the end of Chapter 3, plugin mounts, tool calls, and model responses exist only in memory. When the process exits, all of it disappears: the conversation cannot be resumed, the run cannot be inspected, and what happened can only be recalled from memory. Recovery, auditing, and replay all point to the same need: record the facts of a run in order. This chapter answers: how does DSH record a run, and how does it rebuild requests from the record?

## 4.1 The Log Appends Events in Occurrence Order

A `messages` array can store conversation content, but it usually lacks the information needed to explain an Agent run: the system rules, tool catalog, and projection settings of one Step, when a plugin was installed, which call produced a Tool Result, and why the Agent stopped at a given point. DSH records everything observed during a run as Events: user input, Step start, request header, model response, Tool Call, Tool Result, and runtime changes are all written to one Session Log with an event type and an incrementing ID.

The log is append-only: new events can only be added at the end, and recorded events are never modified in place. This constraint preserves causal order: a Tool Result sits after its Tool Call and before the next model request, which explains how the result enters the following context.

The events card shows the six events of one tool round-trip: user message, first request header, model response, Tool Call, Tool Result, and second request header. Reading them by ID reveals the order of request, execution, and feedback.

## 4.2 What the Model Sees Is What Gets Logged

The log is not just a running account; it is the only source of model requests. Full DSH maintains a runtime invariant: what the model sees is what gets logged. Everything that reaches a model request must be rebuildable from the log. Adding one model-visible input therefore requires adding one SessionEvent type.

Here is the rebuild path. A `request/header` stores the system rules, Tool Schema, step instructions, and projection settings of one Step. `build_request()` locates the target Step's header, then restores the preceding user, model, and tool events into messages in their original order, keeping the tool name that produced each Tool Result. When a checkpoint exists in the history, the builder represents the covered old events with a summary and appends the events after the checkpoint; the original events stay in the log.

Nano DSH records a complete `request/header` for every Step, so requests can be rebuilt. The request comparison, the Trace (execution view), and the events card on the page all come from the same log; maintaining separate copies would let them drift apart.

## 4.3 Persistence Is the Full Version's Choice

An in-memory log demonstrates recording and rebuilding, but it is still lost on process restart. Full DSH appends the same Events to a JSON Lines (JSONL, one JSON record per line) file or a database, and reloading a session restores the log from the persisted records. The storage medium does not change this chapter's event structure.

Nano DSH keeps the events in an in-memory `SessionLog` for one run. The tutorial generator writes these events into the `tutorial-python.json` used by the website, and the page rebuilds requests and replays the Trace from this static record. This minimal implementation keeps the relationship of one data source feeding event recording, request projection, and replay.

One boundary needs stating: this chapter rebuilds semantically identical unified requests, not byte-identical copies of the model provider's original request. Replay never calls the model or executes tools again; streamed chunks, network retries, and provider request IDs do not enter this minimal log.
