# Keep the Shared Prefix as Long as Possible

Each Step in the first chapter carries more messages into the next request. That is easy to follow in a short task. A long tool result can quickly fill the model's context window. At that point, the runtime needs to retain two forms of data: **complete facts for review and recovery, and a model view for the current inference.**

DSH's context design first makes input controllable, then uses a stable request order to encourage prefix-cache reuse. **Control the input first; then keep the stable prefix as long as possible.** The Python teaching version reduces that design to message projection and comparison of four top-level request components. The model service remains the source of truth for actual cache hits.

`context.py` defines the projection, request-building, and prefix-comparison functions. Together, they set the shared rules for later code: which tool results need clipping, how request components are ordered, and where two requests first differ.

## 2.1 The Model View Can Shrink; Complete Facts Must Remain

When an Agent answers a question about a memo, `read_note` may return a long text. Carrying the full value through every Step steadily increases input length. Overwriting it would make later review lose its evidence. The Python version therefore creates a projection while building a request. It changes only the Tool Results the model reads on that request and leaves the original `messages` list intact.

`project_tool_result()` clips only strings over its limit. Short results remain unchanged. A long result retains the beginning, end, and the number of omitted characters. The beginning helps the model identify the source; the end often contains a conclusion, status, or error; the marker makes clear that the middle is absent from this view.

This implementation restricts clipping to the model view: **the current request can become shorter while the caller's complete messages stay unchanged.** Full DSH writes the original facts to a Session Log for later reconstruction, replay, and recovery.

## 2.2 Request Order Determines Where Change Appears

Clipping bounds the size of one result. The order of request components determines where new content changes an otherwise shared request. Python's `build_request()` places system rules and tool definitions first, then the projected message history in time order, and finally the `dynamicContext` that changes on every Step. Comparing adjacent requests from the beginning leaves a longer shared prefix for slowly changing content.

**Slow-changing content comes first; new content is appended near the end.** This function does not call a model service or manage a cache. It arranges current state into a unified request, so callers and the comparison function use the same order to understand one model call. When a tool round-trip adds messages, the new content naturally lands at the end of history.

## 2.3 Check Structural Stability with a Repeatable Comparison

The page can describe how much of two requests starts the same way, but it cannot know a model service's actual cache hit. `approximate_tokens()` gives a character-based teaching estimate. `shared_prefix()` checks `system`, `tools`, `messages`, and `dynamicContext` in a fixed order and finds the first different component. Neither helper contacts a service or changes a request.

This comparison is smaller than the TypeScript version: it checks four top-level components instead of normalizing every segment. **It still gives a stable explanation of which request component changes first.** When tools, prompts, or the model adapter change at runtime, the stable portion changes too; full DSH uses finer request descriptions and log reconstruction for those cases.
