# Context Management Preserves Complete Records and Model Inputs Separately

The model can only read the current request and does not retain content from the previous Step automatically. As an Agent continues running, user messages, model responses, and Tool Results accumulate. If every request includes the complete original content, it will eventually exceed the number of tokens that the model context can hold. A token is the unit a model uses to process text. DSH preserves a record with the complete content and derives the model view required for each request from it. Chapter 2 temporarily stores the original content in Agent memory. Chapter 4 moves the complete record into the Session Log.

## Projection Affects Only the Current Model Request

A Tool Result can grow suddenly. Test logs, search results, or file contents may be longer than the rest of the history combined. Nano DSH preserves the beginning, the end, and an explicit omission marker for long results. The beginning helps identify the result, the end often contains conclusions or errors, and the marker records how many characters were removed from the middle.

The fixed character count is only the projection setting used by this example. The complete tool output remains in the original record, which is Agent memory in this chapter and the Session Log in Chapter 4. Truncation occurs only when the model request is built. If further compression is necessary, DSH can generate a new history projection while preserving the original record of what happened.

## Request Content Is Ordered by How Often It Changes

The fixed section comes first and contains the system rules and Tool Schema, which defines the tools and their argument rules. The accumulated section follows, with user messages, model responses, and Tool Results appended in chronological order. The step-specific section comes last and contains only the dynamic instructions for the current Step. These three sections change at different rates.

This order preserves a longer stable prefix. Most model services reuse the Prompt Cache for consecutive identical tokens at the beginning of adjacent requests. The cache compares the actual content and its order. Semantically similar content with different text cannot be reused directly. Placing frequently changing step-specific instructions at the end and appending new messages without reordering earlier content keeps the first change later in the request.

## Different Changes Invalidate the Cache at Different Positions

When the system rules change, the prefix changes from the first section. When plugin installation changes the tool catalog, the change begins in the Tool Schema. A regular new message usually affects only the end of the history. History compaction occurs earlier in the request: a summary can shorten the request, and it also changes the subsequent prefix from the point where the summary is inserted. Context length and cache reuse rate therefore require separate evaluation.

This tutorial shows the cache reuse opportunities provided by the request structure. It does not represent the actual server-side hit rate. Whether a model provider enables caching and how it bills cache usage depend on that provider. DSH can control deterministic serialization, the placement of fixed content, the append order of history, and can record the earliest position where each request changes.

Chapter 2 projects the complete record into the current model request. It extends the stable prefix by placing fixed content first, appending history, and placing dynamic instructions last. Truncation and summaries control request length. Content order and stability affect cache reuse.
