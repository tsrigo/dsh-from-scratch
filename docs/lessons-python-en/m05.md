# The Agent Installs Its Own Tool

Chapter 4's log can explain what happened, yet it does not add a capability. Suppose a task needs to count the words in a piece of text and the current `Context` has no `word_count` tool. Guessing tool names or repeatedly calling unrelated tools consumes Steps without closing that capability gap.

DSH treats this situation as a controlled runtime change: **inspect the current capabilities and interfaces, mount a temporary plugin, call its new tool to verify the result, and release the plugin when the task ends.** The Python teaching version retains the same path and loads dynamic Python code with `compile()` and `exec()`. That path is appropriate only for trusted teaching samples; the code itself provides no security sandbox.

`runtime_tools.py` begins with the common tool wrapper and the entry point for `runtime_tools_plugin()`. The following implementation works from one definition table, making three states easy to distinguish: plugin code is registered, the plugin is running, or the plugin has been released.

## 5.1 Confirm the Gap Before Deciding What to Add

`cordis_inspect` returns a snapshot of the plugins, tools, and prompts currently held by `Context`. **Confirm what is missing before deciding what to add.** The caller uses the result to establish that `word_count` is absent, then decides what the new plugin must provide. The baseline capability graph matters too: it gives a comparable state from before the change, so an existing capability is not mistaken for a gap.

Runtime Tools also needs its own lifecycle. It keeps dynamic plugins in a definition table and, when removed, stops still-running plugins in reverse order before clearing their definitions. It also registers the inspection interface and a Prompt that explains when to inspect, define, and run a plugin. These preparations give a temporary extension a definite entry and exit.

## 5.2 Defining Code and Mounting a Capability Are Different Moments

After inspection confirms the gap, the caller submits a plugin name, purpose, and Python code through `cordis_define`. The code must define `plugin_factory()` and return an object with `name` and `setup(context)`. **Defining code and mounting a capability happen at different moments.** The function checks code with `compile()` and saves the definition in its table, leaving the tool catalog unchanged. `cordis_run` retrieves the definition, executes the code to obtain a Plugin, and calls Chapter 3's `context.mount()`. The new tool joins the current Context only after mounting succeeds.

The distinction has practical value. Definition reports whether code can load; mounting reports whether the plugin really changed the runtime. A failure therefore has a precise location. `instantiate_plugin()` runs code in a new namespace, then checks the factory function and returned object's required shape. This path has no permission isolation, so deployment needs a constrained execution environment rather than this teaching loader.

## 5.3 Verification and Release Close the Change Loop

Once mounting succeeds, `word_count` appears in the tool table. **It is now available for an outer layer to rebuild a later Agent request.** The Python `Agent` keeps its own tool table from construction and does not automatically subscribe to `Context`. The caller must read `context.tools` and create or update the Agent's tool definitions. A request already sent remains unchanged.

The outer layer retrieves `word_count` from `Context` and receives `words: 3`. That result proves that the new capability mounted and completed one call.

<!-- evidence {"id":"m05-verified","tab":"events","eventType":"tool/result","eventOccurrence":4,"label":"A tool result verifies the new capability","description":"Inspect word_count in the teaching call sequence to confirm that the new tool completed one real call."} -->

After verification, `cordis_stop` invokes the unload function captured during mounting while retaining the definition for a later rerun. `cordis_undefine` stops a running plugin first and then removes its definition. The five `cordis_*` tools share one wrapper, while helpers read arguments and instantiate plugins so the main functions can focus on state transitions. This Python minimum version does not automatically write definition, mounting, or release events to SessionLog; full DSH should add those changes to the common record.
