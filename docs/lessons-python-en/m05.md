# The Agent Writes and Mounts a New Plugin

In this tutorial, runtime self-evolution means that an Agent acquires new plugins and tools while executing a task. The Agent first inspects the current set of plugins and identifies a missing capability. It then writes a new plugin, mounts it into the current Context, and calls the tool provided by the plugin.

This chapter reduces the process to five regular tools: `cordis_inspect` examines the current set of plugins, `cordis_define` registers plugin code written by the Agent, `cordis_run` mounts a plugin, `cordis_stop` stops it, and `cordis_undefine` stops it and deletes its definition. The Agent Loop calls these tools, the Context manages the plugin lifecycle, and the Session Log records definition, mounting, invocation, and removal.

The code on the right uses the `definitions` dictionary to store each plugin's ID, name, purpose, code, and unmount function. Each definition is first stored in the dictionary. It becomes a running plugin in the current Context only after `cordis_run` is called.

## List the Capabilities Provided by Current Plugins

`cordis_inspect` lists the Plugins currently mounted in the Context, along with the Tools, Prompts, and dependencies they provide. The Agent uses this information to determine whether the available tools can complete the task and what a new plugin needs to provide.

At the start of the experiment, the process log and Cordis tools are already mounted, while `word_count` does not yet exist. The Agent first calls `cordis_inspect` to save the current list. It can later compare the capabilities before and after the plugin runs, and verify that the plugin's contributions are removed after it stops. The diagram below provides the baseline for three comparisons: neither `dynamic:word_count` in the plugin list nor `word_count` in the tool list is present.

## The Agent Defines and Runs a New Plugin

`cordis_define` accepts a plugin name, its purpose, and a piece of Python code. The code must define a `plugin_factory()` function that returns a plugin object with a `name` attribute and a `setup(context)` method. `cordis_define` first uses the built-in `compile()` function to check the code's syntax. It then generates a plugin ID in the form `dyn-<n>` and stores the code in the definition table. Creating the definition does not change the current tool list.

`cordis_run` retrieves the code by plugin ID, executes it with `exec()` in a restricted namespace, and calls `plugin_factory()` to obtain the plugin object. It then mounts the plugin through the standard `context.mount()`. `setup` can register Tools, Prompts, and other Context entries. The unmount function returned by `context.mount()` is stored in the plugin definition for use when the plugin is stopped or removed. This teaching implementation executes dynamic code with the built-in `exec()` function and does not provide a security sandbox.

After the plugin starts, its Tools and Prompts appear from the next model request onward because every new request reads the current Context again. The Session Log also records `cordis_define`, `cordis_run`, and the plugin mount event, which identifies the first request where the model can see the new capability. ## Call the New Tool Before Deciding Whether It Works

A successfully mounted plugin only confirms that `setup` has executed. The Agent must also call the tool provided by the plugin and use its Tool Result to determine whether the missing capability has been supplied. In this minimal example, calling `word_count` returns `words: 3`. This confirms that the tool just defined by the Agent has entered the Agent Loop and executes correctly.

<!-- evidence {"id":"m05-verified","tab":"events","eventType":"tool/result","eventOccurrence":4,"label":"Actual invocation and verification result","description":"After the dynamic plugin starts, call word_count and verify the new capability from the result words: 3."} -->

After the experiment, `cordis_stop` runs the unmount function saved during mounting. This removes the Tool, Prompt, and other entries provided by the plugin while retaining its definition so it can be run again. `cordis_undefine` first stops the plugin if it is still running, then deletes it from the definition table. The final diagram uses the same list structure again. Compared with the first diagram, both `dynamic:word_count` and `word_count` are gone, confirming that the plugin's contributions have been removed.

<!-- evidence {"id":"m05-removed","tab":"graph","requestStep":3,"label":"word_count has been removed from the current Context","description":"The plugin and its tool have been removed, returning the number of capabilities in the current Context to the baseline."} -->

These five tools form a complete capability change: list existing capabilities, write a plugin, mount it, call the new tool, and then stop or remove the plugin. The new tool enters subsequent model requests, while all calls and lifecycle events enter the Session Log. The Agent can then continue the task with the plugin it has just written.
