# Let the Task Continue Past a Turn

The Chapter 1 Turn ends when the model stops calling tools. At the end of Chapter 5, the Agent has just installed a tool and removed it again, and the Turn stops. But the task may not be finished: organizing three release notes, the first round collected two of them, and one is still missing. The end of a Turn does not mean the task is done. Who decides that another round starts? This chapter answers: how does a Goal hold the task state, and who decides to continue or stop?

## 6.1 The Goal Holds State; the Driver Makes Decisions

DSH adds a continuation function outside the Agent Loop and uses Goals and Rounds to hold cross-Turn state. The Goal holds the whole task's objective, its current status, and its round limit. A Round represents one stage, such as collecting existing information or completing delivery. One Round starts one ordinary Agent Turn, and one Turn contains several Steps. Goal, Round, Turn, and Step answer, respectively: what is the whole task, which stage is advancing now, what will this Agent start do, and what did the model do in this step.

Nano DSH compresses this relationship into `run_long_task`. The `Goal` holds the objective, the status, the rounds started, the maximum rounds, and the reason for the latest status change; at the start of each round it takes the current task from the predefined stage instructions and passes the same long-term goal together with the stage instruction to `run_round`. Each Round is one ordinary Turn plus one appended goal message, and the mechanisms of the first five chapters are reused as-is.

## 6.2 The Next Round Reuses the Same Session

`run_long_task` never requests the model or executes tools itself. It receives an externally supplied `run_round` function and calls it at the start of each round; the caller starts an ordinary Agent Turn with the same Agent, Context, and Session Log, so the plugins, messages, and Tool Results of the previous round remain, and the long-term goal in the Goal is never replaced by one round's stage instruction.

The request comparison card shows the difference between the two rounds' requests. The second request totals about 50 tokens; its first about 19 tokens match the first request, holding the long-term goal and the previous round's progress, and the second round's task is appended after that. The second round therefore continues from existing progress instead of rebuilding a conversation history.

## 6.3 After Each Round, Check Whether to Continue

In this Python minimal implementation, `run_round` returns a result text. When the text contains `accepted`, the Goal status becomes `completed`; when it contains `blocked`, the status becomes `blocked`; when neither appears, the next round starts. If the Goal is still unfinished but the round boundary is reached, the status becomes `limit_reached`. `accepted` is an acceptance signal in this round's result, not a Goal status name.

The events card shows the full process of this minimal sample: Goal creation, first round start, second round start, and the `completed` status. Compared with the TypeScript version, this implementation has no separate `progressed` field, so it cannot distinguish still-needs-continuation from no-progress-this-round; production implementations need this check to avoid repeating rounds that produce no effect.

## 6.4 The Six Chapters Together

Stack the six chapters: the Agent Loop manages one tool round-trip (Chapter 1), projection controls each request's length and order (Chapter 2), plugins assemble and remove runtime capabilities (Chapter 3), the Session Log records and rebuilds everything (Chapter 4), the Agent fills capability gaps during execution (Chapter 5), and Goals with Rounds let the task continue past a Turn (Chapter 6). Input, capabilities, records, and continuation all serve the same loop.

What Chapter 6 adds is the task coordination layer outside the Agent Loop: the Goal holds the cross-Turn task state, a Round is one continuation, and the driver decides after each round whether to start another Turn. The current Nano DSH executes multiple Rounds in one process only; it does not implement Goal recovery after a process restart, scheduled wakeups, background Jobs, or Subagents. At this point, the six chapters cover one complete thread of DSH's runtime mechanisms: from a single model call to a reliable long-running execution.
