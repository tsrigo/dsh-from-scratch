# Every Runtime Capability Comes from a Plugin

Chapter 1 gives `Agent` its tools and system rules directly, and Chapter 2 arranges them into a request. That starting point makes the loop easy to understand. Once capabilities multiply, changes begin to gather in a few constructors and global states: adding a tool, replacing a model adapter, or changing workspace settings can touch the same core code.

DSH uses Cordis to organize this change. Cordis is the TypeScript plugin runtime used by DSH: **the model adapter, tool registry, Session Log, and Agent Loop all join one runtime tree as plugins.** Profiles, named assemblies; Bundles, packages of plugins; and Patches, configuration overrides, decide which plugins the current tree contains. Nano DSH omits configuration loading and retains the central runtime constraint: **each capability has a source and can be fully withdrawn after installation.**

`runtime.ts` first expresses that constraint through the plugin contract, service tokens, and the internal state of `Context`. `Context` keeps the current plugins, services, tools, prompts, listeners, and dependency relationships. Together, these containers answer two questions: what can the Agent use now, and where did each capability come from?

## 3.1 Give a Capability a Lifecycle Before Installing It

A Plugin is one unit of installation and removal. With a `Context`, it can provide a Service for other plugins, register a Tool the model can call, add a Prompt fragment to system rules, or listen for runtime events. In the capability graph, `clock-core` provides the `clock` service; `clock-tools` uses that service and registers `get_time`. Ownership and dependency can therefore be traced through the graph.

The difficult state appears when installation fails halfway through. A plugin can register a service and then throw while registering a tool. Leaving its earlier contributions in `Context` makes later runtime state unreliable. `mount()` creates an installation record, runs `setup()`, and gathers every cleanup action in one effect stack. **A failed installation and an intentional unload follow the same reverse cleanup path.**

## 3.2 Registering a Capability Also Records How It Leaves

`effect()` is the common lifecycle entry point. It can run only during plugin installation and adds one cleanup function to the current installation record. `provide()` stores a service and its source plugin. `use()` reads the service and records the relationship between its consumer and provider during installation. **Registering a capability also registers its cleanup action and source.** A tool's dependency is then more than an object reference: the runtime can say which installation supplied it.

This implementation handles the collaboration boundary between plugins. During setup, `clock-tools` retrieves `clock` through `use()` and then registers its tool. On unloading, later cleanup actions run first, so the related tool and dependency records leave together. The order comes from recorded facts; each capability type does not need its own exit procedure.

## 3.3 One Record Covers Tools, Prompts, and Listeners

Tools, prompts, and listeners have different parameters, yet the runtime registers them in the same way: write an entry with its owner, then pass a removal action to `effect()`. Read methods derive the current tool list, compiled prompt, and capability snapshot from these containers. `#requireMount()` and `#rollback()` protect the installation and cleanup boundaries.

This source segment keeps contribution registration, state reads, and rollback helpers inside `Context`. Every plugin can enter the runtime through one rule set, and `inspect()` can expose the current plugins, services, tools, prompts, listeners, and dependencies to the model or the page.

## 3.4 Where DSH Separates from Many Harnesses

Tool loops and context projection are common in many Harnesses. **DSH also puts the capabilities that compose those mechanisms into the plugin tree.** Configuration describes the current assembly, plugin lifecycles manage every contribution entering and leaving, and runtime inspection can trace ownership and dependencies. Model adapters, tools, sessions, and the Agent Loop can then be assembled again for a task or environment.

Nano DSH shows service relationships, ownership, and reversible effects. Full DSH also includes dependency injection, waiting for services to become ready, layered configuration, and isolated scopes. The small implementation still demonstrates the architecture's central relationship: capabilities enter `Context` through plugins and leave through the same lifecycle.
