# Plugins Provide Unified Lifecycle Management for Runtime Capabilities

DSH uses Cordis to organize plugins and child plugins into a hierarchical plugin tree, which it uses to assemble a runnable Agent. A function-form plugin receives a Context through `apply(ctx)`. The Context is the shared registration interface for plugins. It contains runtime objects such as Services, Tools, Prompts, and Event Listeners. A Service is a named capability shared between plugins. A Tool is an operation that the model can request. A Prompt adds system rules for the model. An Event Listener handles typed events emitted during a run.

In Chapter 3, the phrase *everything is a plugin* means that plugins provide DSH's runtime capabilities, and those capabilities are loaded and unloaded with their plugins. A single plugin can provide a Service, register a Tool, contribute a Prompt, and listen for events. All of these contributions share the same lifecycle.

## Context Connects Capability Providers and Consumers

Full DSH uses `inject` to declare the Services that a plugin requires. Cordis calls the plugin's `apply(ctx)` after its dependencies are ready. When a Service provider is unloaded, plugins that depend on it are also unloaded, then loaded again after the Service becomes available. The `cordis.yml` file read at application startup selects the plugin tree. Dependencies between plugins determine when each plugin is actually loaded.

Nano DSH condenses these relationships into `Plugin.setup(context)` and `Context.mount()`. A plugin provides a Service through `provide()` and obtains one through `use()`. The Context records the provider, consumer, and Service name, which the page uses to display the current dependencies between plugins. The `registerTool()`, `contributePrompt()`, and `on()` methods register a Tool, Prompt, and Event Listener, respectively, and record which plugin provided each contribution.

Before each model request, the Agent Loop reads the current Tools and the combined system Prompt from the Context. After a plugin is loaded or unloaded, subsequent requests use the updated tool list and system rules.

## Effects Let Plugin Contributions Be Reversed with the Plugin

Cordis treats content registered by a plugin as effects, meaning operations managed within the plugin lifecycle. Interfaces such as `ctx.on()`, `ctx.plugin()`, Service registration, and `ctx.tools.register()` bind the corresponding disposer, a resource cleanup function, to the current plugin. Resources that a plugin creates itself, such as timers and connections, can also register cleanup methods through `ctx.effect()`. Cordis executes these disposers when a plugin is unloaded or hot-reloaded. A hot reload unloads the old plugin after its code changes, then loads the new plugin.

Nano DSH expresses the same path with less code. When a plugin registers each contribution during `setup()`, the Context adds its cleanup function to the current plugin's effect stack. After `setup()` succeeds, `mount()` returns an unload function whose cleanup runs at most once. Calling this function executes the cleanup functions in reverse order and removes the Services, Tools, Prompts, and Event Listeners provided by the plugin.

If `setup()` throws an error before it finishes, `mount()` uses the same effect stack to reverse the completed registrations and return the Context to its state before mounting. Explicit unloads and failed loads therefore share the same cleanup mechanism.

The Context provides one registration interface, each plugin identifies the source of a group of capabilities, and its effects store the corresponding cleanup methods. DSH can therefore assemble runtime capabilities through a plugin tree and update the current plugin composition when configuration changes, hot reloads, or runtime adjustments occur. Chapter 5 will expose Nano DSH's plugin inspection, definition, execution, and removal operations to the Agent.
