# Every Runtime Capability Comes from a Plugin

In Chapter 2, the Tool Schema and the system rules in the request are assembled content. Who provides them? DSH has a single answer: plugins. And the answer has no exceptions: the model adapters, the tool registry, the session log, and the Agent Loop itself are all plugins. There is no privileged kernel that needs patching in DSH's design; extending DSH means mounting a plugin next to other plugins. This chapter answers: how do plugins assemble runtime capabilities, and how are they removed safely?

## 3.1 Context Connects Capability Providers and Consumers

Plugins form a hierarchical plugin tree. Each plugin receives a Context, the shared registration interface, when it mounts. The Context holds four kinds of runtime objects: a Service is a named capability shared between plugins, a Tool is an operation the model can request, a Prompt adds system rules for the model, and an Event Listener handles typed events emitted during a run.

A plugin provides a Service through `provide()` and obtains one through `use()`. Full DSH declares the Services a plugin requires with `inject`; Cordis calls the plugin's `apply(ctx)` after its dependencies are ready. When a Service provider unloads, plugins that depend on it unload too and reload once the Service returns. Nano DSH compresses the dependency relationship into `provide()` and `use()`; the Context records the provider, the consumer, and the Service name, without version selection, topological ordering, or cascading unloads.

The capability graph card shows the ownership in this chapter's sample: the plugin `clock-core` provides a Service named `clock`, the plugin `clock-tools` registers the `get_time` tool, contributes the `clock-rule` prompt, and depends on `clock` through `use()`. Before each model request, the Agent Loop reads the current tool list and the merged system Prompt from the Context; after a plugin loads or unloads, the next request uses the updated content.

## 3.2 Registration Is a Reversible Side Effect

If tools, prompts, and listeners were registered with global variables, nothing would know what to undo on unload. The plugin approach binds registration and removal together: when a plugin registers each contribution during `setup()`, the Context pushes its cleanup function onto the current plugin's effect stack. After `setup()` succeeds, `mount()` returns an unload function whose cleanup runs at most once.

Calling the unload function executes the cleanup functions in reverse order and removes the Services, Tools, Prompts, and Event Listeners provided by the plugin. If `setup()` throws before finishing, `mount()` walks the same effect stack to reverse the completed registrations and return the Context to its pre-mount state. Explicit unloads and failed loads therefore share one cleanup mechanism.

The reverse order has a practical reason: content registered later may depend on content registered earlier, so dependents are removed before their dependencies. Nano DSH assumes cleanup functions complete normally and does not implement full dependency transactions; production implementations also need to ensure the mount state is cleared when some cleanups fail.

## 3.3 Three Results of a Unified Lifecycle

The owner record lets the runtime list where each capability comes from. The disposer lets a plugin unload completely and remount. The same set of cleanup functions removes Tools, Prompts, and Listeners together, so partial cleanup cannot leave stale contributions behind. Three kinds of runtime capabilities therefore follow one install, inspect, and unload flow.
