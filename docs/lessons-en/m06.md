# Let the Task Continue Past a Turn

Chapter 5 can add a tool during a task. A Turn still ends when the current model stops calling tools. The task may remain incomplete: after one round of organizing three release notes, the Agent may have collected only two. A different layer has to decide whether work should continue.

DSH manages long-term objectives outside the Agent Loop. **A Goal decides whether cross-Turn work continues; Turns and Steps continue to handle model requests and tool execution.** A Goal holds state that spans rounds, while a Round is one new attempt to advance it. These four layers check their own stop conditions. A lack of Tool Calls therefore does not directly mean the Goal is complete.

`long-task.ts` defines Goal state, the input and result of each Round, and the outline of `LongTaskRunner`. It holds only an objective, session, and `runRound` callback. The caller keeps reusing the specific Agent, Context, and workspace on each Round. This boundary lets long-task coordination do just what it needs to do: decide whether to start another ordinary Turn.

## 6.1 A Goal Needs State That Can Be Checked Across Rounds

The `LongTaskRunner` constructor fixes the objective, maximum Round count, initial status, and the definitions for later Rounds. At the start of `run()`, it writes `goal/created` to the Session Log. **The Goal enters the replayable flow of facts from the beginning.** No model request happens here; the code is establishing the shared boundary for work that spans several Rounds.

Keeping this state in `LongTaskState` has two benefits. The outer layer can read a consistent status, reason, and number of started Rounds after each attempt. The page and recovery logic can also find the moment the Goal was created in the log. The source keeps initialization and the creation event together so the state object and recorded fact remain aligned.

## 6.2 The Next Round Still Calls the Ordinary Agent Loop

While the Goal is `active`, the runner checks the Round limit and whether another Round definition exists. If both checks pass, it increments the Round count, writes `goal/round-started`, and calls `runRound`. The callback can reuse the Agent, Context, workspace, and Session Log from earlier Rounds. Messages, Tool Results, and plugin changes recorded in previous chapters are therefore still available.

This layer does not duplicate Chapter 1's tool loop. **A Goal can start a new Turn without rewriting the Agent Loop.** It draws a Round boundary for the next Turn; the ordinary Agent Loop continues to handle model requests, Tool Calls, and feedback. Separating the loops lets the model's decision to stop calling tools and the Goal's decision to continue progress be evaluated independently.

## 6.3 Continuation Must Use Observable Results

`runRound` returns a `RoundResult`. `completed` reports that the Goal is achieved, `blockedReason` says why it cannot continue, and `progressed` reports whether the Round made the intended progress. The runner uses these values to finish the Goal, mark it blocked, enforce its Round limit, or retain `active` and begin another Round. Every exit writes `goal/status-changed`, so state transitions enter the same session record.

The source keeps these branches with `#finish()` so that ending a Goal always updates in-memory state and the Session Log together. **The loop continues only when the current Round made progress, the Goal remains incomplete, and the limit has not been reached.** That condition imposes a more useful constraint on long-running work than simply calling the model again.

## 6.4 The Six Chapters on One DSH Runtime Path

One Step completes a model-and-tool round-trip in the Agent Loop. The context layer decides which information that Step sees. The plugin runtime decides what capabilities currently exist. The Session Log saves inputs, actions, and capability changes as shared facts. Runtime Tools add a needed capability during work. Goals and Rounds decide whether work needs another Turn after the current one ends.

This relationship shows that DSH reaches beyond a single model call. It organizes execution, capabilities, records, and Goal state into a runtime that can be inspected, replaced, and continued. Nano DSH retains the smallest set of these relationships; full DSH adds configuration layers, persistence, permissions, sandboxes, and more runtime providers.
