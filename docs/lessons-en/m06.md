# Let the Task Continue Past a Turn

The Chapter 1 Turn ends when the model stops calling tools. At the end of Chapter 5, the Agent has just installed a tool and removed it again, and the Turn stops. But the task may not be finished: organizing three release notes, the first round collected two of them, and one is still missing. The end of a Turn does not mean the task is done. Who decides that another round starts? This chapter answers: how does a Goal hold the task state, and who decides to continue or stop?

## 6.1 The Goal Holds State; the Driver Makes Decisions

DSH treats the Goal as state that can survive within the same Session. The Goal records the objective, the phase, how many Goal Rounds have already started, and the round limit. The Goal Round Driver checks the Goal while the Agent is idle: when the phase is `active`, continuation is enabled, and rounds remain, it appends a message carrying the goal and the round number to the same Session, then starts an ordinary Turn.

Nano DSH compresses this relationship into `LongTaskRunner`. `LongTaskState` holds the objective, the status, the rounds started, the maximum rounds, and the reason for the latest status change; two `RoundDefinition`s hold each round's name and input; `runRound` starts the ordinary Agent Turn from Chapter 1. Each Round is one ordinary Turn plus one appended goal message, and the mechanisms of the first five chapters are reused as-is.

## 6.2 The Next Round Reuses the Same Session

`LongTaskRunner` never requests the model or executes tools itself. At the start of each round it calls an externally supplied `runRound` function; in this tutorial, `runRound` starts a new Agent Turn with the same Agent, Context, and Session Log, so the plugins, messages, Tool Results, and workspace changes of the previous round all remain.

The request comparison card shows the difference between the two rounds' requests. The second request totals about 50 tokens; its first about 19 tokens match the first request, holding the long-term goal and the previous round's progress, and the second round's task is appended after that. The second round therefore continues from existing progress instead of rebuilding a conversation history.

## 6.3 After Each Round, Check Whether to Continue

After each round, `runRound` returns a `RoundResult`: `progressed` says whether the round produced the expected progress, `completed` says whether the whole Goal is done, and `blockedReason` records why it cannot continue. Nano DSH updates the status from these three fields to `completed`, `blocked`, or `max-rounds`; when progress was made but the Goal is not done, the status stays `active` and the next round starts.

The events card shows the full process of this minimal sample: Goal creation, first round start, second round start, and the `completed` status with the stop reason that all three items were written to the deliverable. Full DSH also has a `paused` phase; the model reports completion or blockage through `update_goal`, and every status change is saved to the Session Log.

## 6.4 The Six Chapters Together

Stack the six chapters: the Agent Loop manages one tool round-trip (Chapter 1), projection controls each request's length and order (Chapter 2), plugins assemble and remove runtime capabilities (Chapter 3), the Session Log records and rebuilds everything (Chapter 4), the Agent fills capability gaps during execution (Chapter 5), and Goals with Rounds let the task continue past a Turn (Chapter 6). Input, capabilities, records, and continuation all serve the same loop.

What Chapter 6 adds is the continuation mechanism outside the Agent Loop: the Goal holds the cross-Turn task state, a Round is one continuation, and the driver decides after each round whether to start another Turn. At this point, the six chapters cover one complete thread of DSH's runtime mechanisms: from a single model call to a reliable long-running execution.
