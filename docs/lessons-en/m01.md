# One Tool Round-Trip: Where the Agent Loop Starts

Consider one concrete task: the user asks for the current time in Beijing. The model understands the question, but it has no live data. It needs to call `get_time`, read the returned value, and then answer. That sequence puts the model, a tool, and the runtime on one execution path, which every later DSH mechanism relies on.

Many Agent Harnesses can complete one tool call. DSH becomes distinct in the way it organizes the surrounding runtime: tools, prompts, sessions, and the Agent Loop can all be assembled as plugins, while execution facts enter one shared log. This chapter first establishes the smallest loop so that the later mechanisms have a clear place to attach.

`agent.ts` declares the model adapter, tool definitions, the result of one Turn, and the state held by `Agent`. Keep one boundary in view before reading the implementation: **the model proposes the next step; the runtime prepares input, executes actions, and saves feedback.**

## 1.1 Why One Answer Can Span Multiple Steps

On its first request, the model receives system rules, the parameter definition for `get_time`, the user question, and an instruction for the current Step. None of that reveals the current time, so it returns a Tool Call. The runtime executes the query and adds the result to message history. A second request includes that new fact. When the model then returns ordinary text, the Turn ends.

**A Step is one model request together with the tool execution it triggers; a Turn can contain several Steps.** To keep every Step within the same boundary, the `Agent` constructor fixes the model adapter, tool table, argument validator, system rules, and maximum Step count. The loop can then start without rediscovering those dependencies on every request.

<!-- fill {"index":1} -->

Only after that setup does `runTurn()` process user input. It writes the input into history, builds an independent request for each Step, calls the model, and writes the reply back into history. A Tool Call keeps the loop moving; a reply without one becomes the final answer. Request construction, the model reply, and the tool round-trip sit in one control flow, so one complete Turn can be read in order.

## 1.2 Tool Execution Needs One Feedback Path

The model can supply a tool name and arguments, but it cannot decide whether the action is valid or succeeds. The runtime has to find the registered tool, check that the arguments follow its Schema, and execute the function. A successful query, an unknown tool, invalid arguments, and a thrown exception all need to return through the same kind of tool-result message.

`runTurn()` therefore keeps validation details out of the loop body and calls `#executeTool()`. **Successful values and failures both return as the same structured feedback.** The helper converts the three failure cases into results with `ok: false` and preserves a successful value. The next request can read one consistent message shape, allowing the model to adjust its arguments or choose another action.

## 1.3 Where This Loop Sits in DSH

This minimal implementation turns a tool round-trip into an inspectable program flow, while still keeping the tool catalog, system rules, and message history directly inside `Agent`. Longer tasks make request input grow; runtime changes crowd the constructor; and history held only in memory cannot support replay after the process ends.

Full DSH preserves this execution boundary while assigning input projection, capability assembly, and session recording to dedicated runtime mechanisms. Understanding the Step and Turn in this chapter makes it possible to see which part of the loop each later mechanism supports.
