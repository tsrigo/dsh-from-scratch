# One Tool Round-Trip: Where the Agent Loop Starts

Ask the Agent: find the current time in Beijing. The model does not know the time, so it must first call the `get_time` tool and then answer with the result. One answer needs two model requests, and the runtime handles the connection between them. This chapter answers: how does one tool round-trip complete?

## 1.1 The Loop: Request, Execute, Request Again

The first request holds the system rules, the tool definitions, the user question, and a short step instruction: about 62 tokens in total. The model cannot read the time from these contents, so it returns a Tool Call: call `get_time` with the argument Beijing.

The Harness receives the Tool Call, looks up the tool, validates the arguments, and executes it. It appends the result and its call ID to the history, then starts the next Step and requests the model again. The second request keeps everything from the first and appends the model's Tool Call and the tool's returned result at the end: about 119 tokens in total. The model reads the result and answers directly, closing the Turn.

The request comparison card shows exactly this one change. Compare the beginnings of the two requests first: the system rules, the tool definitions, and the user question are identical. Then look at the end: the second request adds the assistant message and the tool result. This single change is the minimal Agent Loop closure: the model proposes an action, the runtime executes it, the result enters the next request, and the model chooses the next step from that result.

## 1.2 The Model Chooses Actions; the Harness Validates and Executes Them

Splitting the round-trip above reveals two responsibilities. The model chooses the action: which tool to call and with what arguments. The Harness decides whether the action can run: it looks up the tool, validates the arguments, executes, and catches exceptions. The tool interface is the boundary between the two.

The execution path works step by step: the Harness looks up the tool by name in the registry, validates the arguments against the argument rules, invokes the tool, and finally catches execution exceptions. Any failure in these four steps produces a structured result.

An unknown tool returns `Unknown tool`, arguments that do not match the rules return `Invalid tool arguments` with a list of issues, and an execution error returns the exception message. These results are appended to the history like any normal result, ready for the model to read in the next step.

After reading the failure reason, the model adjusts the arguments or switches to another tool. A failed call therefore also enters the next request; the loop corrects itself through this feedback.

## 1.3 Steps, Turns, and Stop Conditions

One model request together with the tool execution it triggers forms a Step. A Turn is the container for these Steps: it opens when a user message arrives and closes when the model stops calling tools. Nano DSH's `runTurn()` accepts one user message and executes multiple Steps within the same Turn.

A Turn has two stop conditions. The normal one: the model returns a reply without Tool Calls, and the current Turn ends. The defensive one: the Step count reaches its limit, and the Harness terminates the run explicitly. Tool failures do not trigger a stop condition; they return to the model as results, and the model decides what to do next.

Full DSH draws a wider boundary. It checks at the end of each Step whether the current Turn still has pending tool results or new inputs. The Provider, the model-service adapter, converts the unified request into the format a specific model interface requires and handles streamed responses. The Agent Loop advances Turns and Steps; the next five chapters manage the inputs, capabilities, records, runtime changes, and cross-Turn coordination of this loop.
