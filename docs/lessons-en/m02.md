# Keep the Shared Prefix as Long as Possible

Every step of the Chapter 1 loop adds more history to the request: the second request already carries 57 more tokens than the first. The longer the task, the faster the growth, and the request eventually exceeds the model's Context window. Model services reuse the KV Cache (Key-Value Cache) by prefix: identical content at the beginning of two requests is computed only once. The longer the prefix, the lower the cost. This chapter answers: how can the shared prefix stay as long as possible?

## 2.1 Clip Long Results Before They Enter the Request

Ask the Agent: what does the memo say? `read_note` returns a very long memo. The second request totals about 264 tokens, and this Tool Result alone is about 172 tokens, while everything else combined is about 92 tokens. Putting such a full text directly into the request would fill the Context window within a few Steps.

Nano DSH clips overly long Tool Results when building the request, keeping the beginning, the end, and an explicit omission marker. With the default settings, a result longer than 720 characters keeps the first 430 characters and the last 170, and the marker states how many characters were removed. Clipping happens only when the request is built; the complete result stays in the record.

The cost of clipping is that the model never sees the middle content. The head and tail are kept because the beginning identifies the result and the end usually holds the conclusion or the error. Full DSH clips long Tool Results after token pressure reaches a threshold; if the request is still too long, it replaces an earlier model view with a summary. Nano DSH shows the same path with a fixed threshold.

## 2.2 Ordering Decides Where the Prefix Starts to Change

The request is divided into three sections by how often they change. The fixed section comes first and holds the system rules and the Tool Schema, which defines the tools and their argument rules; it changes only with configuration. The middle is the accumulated section: user messages, model responses, and Tool Results are appended in chronological order and never rewritten. The step-specific section comes last and holds only the dynamic instructions for the current Step; it changes with every request.

This order puts content that changes every time at the end and content that rarely changes at the front, so the shared prefix stays as long as possible. Cache reuse compares the actual content and its order; semantically similar content with different text produces a different cache key.

The request comparison card shows the difference between the second request and the first: the shared prefix is about 57 tokens, exactly the fixed section plus the user message; the first change happens at the assistant message, followed by the Tool Result of about 172 tokens.

## 2.3 What Invalidates the Prefix Early

Where the prefix breaks depends on which section the change lands in. When the system rules change, the prefix changes from the first section. When plugin installation changes the tool catalog, the change lands in the Tool Schema. A regular new message only affects the end of the history.

History compaction sits further forward: a summary shortens the request, but it also changes the following prefix from its insertion point. Context length and cache reuse rate must be evaluated separately. What the page shows is a teaching estimate; actual cache hits and billing follow the data returned by the specific model service.

Full DSH keeps a reusable prefix by holding system prompts and tool definitions in a stable order and appending history chronologically. The Nano DSH page also marks the earliest point where adjacent requests differ.
