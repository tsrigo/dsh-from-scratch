# Context Management Preserves Complete Records and Model Inputs Separately

The model generates each response from the current request. As an Agent continues running, user messages, model responses, and Tool Results accumulate. If every request includes the complete original content, it will eventually exceed the model's Context limit. A token is the unit a model uses to process text. DSH derives the model view required for each request from the complete Session Log. In Chapter 2, Nano DSH first represents the complete record with messages in Agent memory. Chapter 4 will express the same relationship through the Session Log.

## Projection Affects Only the Current Model Request

A Tool Result can grow suddenly. Test logs, search results, or file contents may be longer than the rest of the history combined. Nano DSH starts truncation at a fixed character count. For long results, it preserves the beginning, the end, and an explicit omission marker. The beginning helps identify the result, the end often contains conclusions or errors, and the marker records how many characters were removed from the middle.

The fixed character count is the projection setting used by this minimal example. The complete tool output remains in Agent memory, while truncation occurs when the model request is built. Full DSH prunes long Tool Results after token pressure reaches a threshold. If the request remains too long, it replaces an earlier model view with a summary. The original events remain in the Session Log. Nano DSH uses fixed-threshold head-and-tail truncation to show the separate roles of the complete record and the model view.

## Request Content Is Ordered by How Often It Changes

The fixed section comes first and contains the system rules and Tool Schema, which defines the tools and their argument rules. The accumulated section follows, with user messages, model responses, and Tool Results appended in chronological order. The step-specific section comes last and contains only the dynamic instructions for the current Step. These three sections change at different rates.

This order preserves a longer stable prefix. Cache reuse here means that the model service reuses the Key-Value Cache (KV Cache) for identical request prefixes. The cache compares the actual content and its order. Semantically similar content with different text produces a different cache key. Placing frequently changing step-specific instructions at the end and appending new messages in order keeps the first change later in the request.

## Different Changes Invalidate the Prefix at Different Positions

When the system rules change, the prefix changes from the first section. When plugin installation changes the tool catalog, the change begins in the Tool Schema. A regular new message usually affects only the end of the history. History compaction occurs earlier in the request: a summary can shorten the request, and it also changes the subsequent prefix from the point where the summary is inserted. Context length and cache reuse rate therefore require separate evaluation.

The page compares the longest identical prefix between adjacent requests and estimates the corresponding token count from the number of characters. Actual cache hits and billing are determined from data returned by the specific model service. Full DSH preserves reusable prefixes by keeping system prompts and tool definitions in a stable order and appending history chronologically. The Nano DSH page also marks the earliest point where adjacent requests differ.

Chapter 2 projects the complete record into the current model request. It extends the stable prefix by placing fixed content first, appending history, and placing dynamic instructions last. The head-and-tail truncation in this chapter and the summaries in Chapter 4 control request length. Content order and stability affect cache reuse.
