# Keep the Shared Prefix as Long as Possible

Each Step in the first chapter carries more messages into the next request. That is easy to follow in a short task. A long tool result can quickly fill the model's context window. At that point, the runtime needs to retain two forms of data: **complete facts for review and recovery, and a model view for the current inference.**

DSH's context design first makes input controllable, then uses a stable request order to encourage prefix-cache reuse. **Control the input first; then keep the stable prefix as long as possible.** Caching is not an isolated optimization. It depends on which request content stays fixed and which content is appended at the end. Follow the division between complete facts and the model view before looking at the code that preserves it.

`context.ts` opens with projection rules, request components, and comparison results. These give later functions a common vocabulary: which tool results need clipping, which parts compose a request, and where two requests first differ.

## 2.1 The Model View Can Shrink; Complete Facts Must Remain

When an Agent answers a question about a memo, `read_note` may return a long text. Carrying the full value through every Step steadily increases input length. Overwriting that value would make later replay lose its evidence. Nano DSH therefore creates a projection before sending a request: it changes only the messages the model reads for this request and leaves the original messages intact.

The projection function copies messages one by one and calls its clipping helper only for Tool Results. Short results remain unchanged. A long result keeps its beginning, end, and an omission count. The beginning helps the model identify the source; the end often contains a conclusion, status, or error; the marker makes clear that the middle is absent from this view.

The code intentionally keeps copying and clipping together: **clipping happens while the request view is generated, so the complete facts are never overwritten.** Full DSH stores those original facts in the Session Log for later reconstruction, replay, and recovery.

## 2.2 Request Order Determines Where Change Appears

Clipping bounds the size of one result. The order of request components determines where new content changes an otherwise shared request. Nano DSH places system rules and the Tool Schema, the names and argument rules of available tools, first. It then appends message history in time order and places instructions that change on every Step at the end. Comparing adjacent requests from the start leaves a longer shared prefix for content that changes slowly.

`describeRequest()` makes that order an explicit array. **Slow-changing content comes first; new content is appended near the end.** The function does not call a model service or manage a cache. It separates a request into observable components, so the page and the comparison function use the same order to understand one model call. When a tool round-trip adds messages, the new part naturally lands at the tail of history.

## 2.3 Check Structural Stability with a Repeatable Comparison

The page can describe how much of two requests starts the same way, but it cannot know a model service's actual cache hit. `compareRequestPrefix()` therefore performs a deterministic structural check. It normalizes components, compares them from the beginning, and records the count of shared components, an estimated text size, and the first changed position. Actual cache hits and billing remain the model service's own result.

The comparison also estimates tokens, the units a model uses to process text, and sorts object fields consistently. These helpers do not alter request content. They make a local comparison of the same structure produce the same conclusion, so readers do not mistake a display estimate for the model service's cache implementation.

When tools, prompts, or the model adapter change during a run, the stable part of a request changes with them. DSH organizes those capabilities in the runtime; the context module continues to arrange the currently effective capabilities and history into model input.
