# The Agent Installs Its Own Tool

The Chapter 4 log can restore the past, but it cannot change the future. What if the task is halfway through and the current tools are not enough? Can the Agent install its own? DSH can: the Agent first inspects the current set of plugins and identifies the missing capability, then writes a new Cordis plugin, mounts it into the current Context, and actually calls the tool the plugin provides. This chapter walks that path with one minimal experiment: inspect, define, run, verify, remove.

The path is compressed into five ordinary tools: `cordis_inspect` lists the current plugin composition, `cordis_define` registers the plugin code the Agent writes, `cordis_run` mounts the plugin, `cordis_stop` stops it, and `cordis_undefine` stops it and deletes the definition. The Agent Loop calls these tools, the Context manages the plugin lifecycle (Chapter 3), and the Session Log records the whole process (Chapter 4).

## 5.1 First, List the Capabilities the Current Plugins Provide

`cordis_inspect` lists the Plugins currently mounted in the Context, along with the Tools, Prompts, Services, and dependencies they provide. The Agent uses this list to judge whether the existing tools can finish the task and what the new plugin needs to provide.

At the start of the experiment, the session log and the Cordis tools are already mounted, and `word_count` does not exist. The first capability graph is the baseline before the change: the plugin list has no `dynamic:word_count`, and the tool list has no `word_count`. Every following step is compared against this graph.

## 5.2 Defining and Mounting Are Two Steps

`cordis_define` receives a plugin name, a purpose, and a JavaScript function body that returns a Cordis Plugin. It first checks whether the code compiles, then generates a plugin ID of the form `dyn-<n>` and stores the code in the definition table. Defining does not change the current tool list; the model sees nothing new yet.

`cordis_run` takes the code by plugin ID, evaluates it in the Node.js built-in `node:vm` code-execution environment to obtain a Cordis Plugin with `apply(context)`, converts it into a Nano DSH Plugin, and mounts it through the ordinary `context.mount()`. The registrations performed during mounting follow Chapter 3's effect mechanism; the returned unload function is stored in the plugin definition for stopping or removal.

The effect of mounting appears from the next model request, because a new request re-reads the current Context. The second request's Tool Schema grows from about 170 tokens to about 214 tokens, and the addition is exactly the `word_count` definition. The Session Log records `cordis_define`, `cordis_run`, and the plugin mount event, so it can determine from which request the model started seeing the new capability.

## 5.4 Call the New Tool to Verify It Works

A successful mount only means `apply` has run; it does not prove the new tool can solve the task. The Agent must also call the tool provided by the plugin and judge from the Tool Result whether the capability gap is closed. This minimal sample calls `word_count` with the argument `one two three` and receives `words: 3`.

The events card shows this verification: the `word_count` call is recorded right after the plugin mount event, and the result `{"words": 3}` proves that the tool the Agent just defined has entered the Agent Loop and executes normally.

## 5.5 When the Experiment Ends, Undo and Compare with the Baseline

`cordis_stop` executes the unload function saved at mount time, removing the Tools, Prompts, and other content the plugin provided, while keeping the plugin definition so it can run again later. `cordis_undefine` first stops a still-running plugin and then deletes it from the definition table.

The third capability graph reuses the same list structure; compared with the first graph, both `dynamic:word_count` and `word_count` are gone, and the plugin and tool counts are back at the pre-experiment baseline. A complete experiment has three states: baseline, treatment, and rollback.

## 5.6 One Complete Capability Change

These five tools form one complete capability change: list the existing capabilities, write a plugin, mount it, call the new tool, then stop or remove the plugin. The new tool enters subsequent model requests (Chapter 2's projection), its lifecycle is managed by Chapter 3's mechanisms, and every call and event is written to Chapter 4's log. The Agent can therefore supply its own tools during execution.
