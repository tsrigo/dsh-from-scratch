# What the Model Sees Is What Gets Logged

The first three chapters produce several kinds of state: user messages and Tool Results make up model history, plugins change the available tools and system rules, and the page needs to show the execution. If these details live separately in message arrays, debug output, and UI state, one run can quickly acquire conflicting versions of its own history.

**DSH writes runtime facts to one append-only Session Log first, then derives model history, replay, UI, and persisted data from that log.** This order establishes a checkable constraint: **anything visible to the model must be reconstructable from the record.** This chapter joins Chapter 2's model view and Chapter 3's runtime changes to one source of facts.

`session.ts` begins by listing the `SessionEvent` values a run can produce and defining `SessionLog` state. The event types are more precise than a generic log table: request headers, Tool Calls, Tool Results, plugin changes, and Goal status each carry the data reconstruction needs.

## 4.1 Save Facts in the Order They Occur

One tool round-trip contains at least a user message, a request header, a model reply, a Tool Call, and a Tool Result. `SessionLog.append()` copies the incoming event, assigns a growing identifier, and appends it at the end. The identifier lets the page point at a definite event. **Append order preserves causality: a Tool Result follows its Tool Call and precedes the next request.**

A context checkpoint is also an event. It records a summary and the last event identifier the summary covers, while original events remain in the log. Later requests can build a shorter view from the summary and newer events; review and replay still return to the complete facts. Keeping identifiers, appending, and checkpoints in one small class prepares dependable input for the reconstruction functions that follow.

## 4.2 The Log Must Follow Runtime Capability Changes

Recording messages alone is insufficient. Plugin mounting and unloading from Chapter 3 change the tool list and prompts. Without those changes in the same record, a later reader cannot explain why a particular Step saw a particular tool. `sessionPlugin()` provides the Session Log through `Context`, listens to plugin mount and unload events, and appends them as session facts.

This layer connects the plugin runtime and the session record. It does not build model requests or execute tools. Its job is to keep capability changes on the same timeline as messages and Tool Results.

## 4.3 A Request Header Marks the Boundary at That Time

Message history alone cannot describe a complete request. System rules, the Tool Schema, model configuration, Step instructions, and projection settings can change over time. **A `request/header` stores the full input boundary for one Step at the time it ran.** Nano DSH records one for each Step. Reconstruction first locates that header by `stepId` and then reads only the events before it.

`buildRequest()` then finds the newest context checkpoint to determine which older events its summary already covers. It projects remaining user messages, model replies, and Tool Results into model messages. Tool Calls are recorded separately and later attached to the reply that issued them. Finally, it calls Chapter 2's `projectMessages()` to create the current model view. This array work remains dependable because the first two sections recorded facts at a sufficiently fine granularity.

## 4.4 Replay and the UI Reuse the Same Facts

`replayTrace()` reads the same `SessionEvent` values and creates the titles and details shown by the page. **Model requests, replay, and the UI share one event-based source of facts.** `replayTrace()` and `buildRequest()` serve different purposes without maintaining a second execution history. New display or debugging views can likewise derive from the log without rewriting model input.

Full DSH writes SessionEvents to JSON Lines, or JSONL, where each line is one JSON record, or to SQLite. Nano DSH keeps the log in memory and serializes teaching samples for the site. Both retain the important relationship: requests, replay, and display all derive from one event stream.
