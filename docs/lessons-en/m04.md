# Session Log Stores Events and Generates Other Views

DSH stores the complete interaction history of an Agent as a Session Log. Each entry in the log is a SessionEvent, such as `turn/start` for the start of a Turn and `step/start` for the start of a Step, along with user messages, model responses, Tool Calls, and Tool Results. Every SessionEvent contains an event type, a sequential ID, a timestamp, and the corresponding data.

Here, a SessionEvent represents a fact that must be written to the session history. The Cordis Event introduced in Chapter 3 supports runtime communication between plugins. When information needs to persist, an event handler appends it as a SessionEvent. DSH plugins can also extend the SessionEvent types, for example by adding Context compaction records.

## Session Log Appends Events in Order

The Session Log uses an append-only structure. New events are written at the end of the log, while existing events remain unchanged. The IDs therefore show the exact order of Turns, Steps, model responses, and tool execution. A Tool Result appears after its corresponding Tool Call and before the next model request, showing how the result enters the subsequent Context.

Nano DSH's `SessionLog.append()` copies an event, assigns an incrementing `id`, and adds it to the array. `sessionPlugin()` also listens for plugin mount and unmount notifications and writes changes in runtime capabilities to the same log. ## The Same Events Generate Model Requests and Execution Traces

The full DSH derives model messages from the Session Log. Events such as `user/message`, `assistant/message`, and `tool/result` form the message history visible to the model. `request/header` stores the model configuration, rendered system prompt, and Tool Schema. When a request header changes, DSH appends a complete snapshot. A model request can be reconstructed by reading the latest request header before the target position and combining it with the message history available at that point.

Nano DSH records a complete `request/header` for every Step. It includes the Provider, model, system prompt, Tool Schema, dynamic instructions, and projection settings. `buildRequest()` first finds the request header for the target Step, then restores all earlier user messages, model responses, and Tool Results in order. Tool Calls are reattached to the model response that initiated them, while Tool Results retain their original call IDs.

Nano DSH uses `context/checkpoint` for a summary of older history. When reconstructing a request, `buildRequest()` adds the summary first, followed by events after the checkpoint. Context compaction in the full DSH also appends a new SessionEvent so that a summary replaces part of the old message history currently visible to the model. The original summarized events remain in the Session Log.

Nano DSH's `replayTrace()` reads the same set of SessionEvents and generates a title and description for each event. The website calls this output the Trace, or execution trace view. Trace replay reads only recorded events, so model request reconstruction and execution trace rendering use the same data.

## Persisting the Session Log

The full DSH appends SessionEvents in memory and notifies the persistence plugin through `session/event`. The persistence plugin copies the events in batches and writes them to storage through the common `SessionPersistence` service. DSH provides two implementations: JSON Lines (JSONL, one JSON record per line) and SQLite. When a session is reloaded, its Session Log is restored from the persisted records. An explicit flush waits until the current batch has been written.

Nano DSH keeps events in a `SessionLog` array during a run. The tutorial generator writes these events to the `tutorial.json` used by the website. The page can then reconstruct model requests and replay the Trace from this static record. This minimal implementation preserves the relationship in which event recording, request projection, and replay all use the same data source.

DSH records runtime facts as SessionEvents, preserves their order in the Session Log, and writes them to JSONL or SQLite through the persistence service. Model requests, text records, and replay views are all derived from this log, so the stored events remain available for restoring and inspecting Agent execution.
