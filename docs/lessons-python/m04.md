# 模型可见即已记录

前三章已经产生多种状态：用户消息和工具结果构成模型历史，插件改变可用工具和提示词，页面还要展示执行过程。若这些信息分别停留在消息数组、调试输出和界面状态中，同一次运行很容易出现几份互相对不上的版本。

**完整 DSH 先把运行事实写入一条仅追加的 Session Log（会话日志），再从这条日志派生模型历史、回放、界面和持久化数据。**这个顺序建立了一条可检查的约束：**模型能够看到的内容，应当能从记录中重建。**Python 教学版先实现这条关系的最小骨架：事件按顺序追加，请求和 Trace（执行时间线）从同一组事件读取。

`session.py` 定义 `Event` 和 `SessionLog`。每个 Event 只有递增编号、类型和数据，调用方明确决定何时追加用户消息、请求头或工具结果。这份简化让事件顺序和请求重建的关系保持可见。

## 4.1 先按发生顺序保存事实

一次工具往返会经过用户消息、请求头、模型回复、外层执行工具和工具结果。这个 Python 最小版由调用方追加用户消息、请求头、模型回复和工具结果，并未自动建立独立的 Tool Call 事件。`SessionLog.append()` 使用当前长度生成递增编号，再把新 Event 追加到末尾。编号让页面能指向确定事件，**追加顺序保留了因果关系：工具结果位于外层执行之后、下一次请求之前。**

`request_step_ids()` 从 `request/header` 事件中取出可以重建的 Step 标识。它没有复制历史，也不猜测事件的语义；索引仍指向同一份追加记录。编号和索引放在一个小类中，正是在为后面的重建函数准备稳定输入。

## 4.2 日志必须覆盖模型可见的事实

完整 DSH 中，插件挂载和卸载会改变工具列表与提示词；这些变化也需要进入同一份记录，之后才能解释某个 Step 当时为什么看到了某个工具。TypeScript 版的 `sessionPlugin()` 会监听运行时变化并追加事件。

Python 教学版在这里保留了更明确的边界：`SessionLog` 不会自动挂接 `Context`，调用方负责在发生事实时调用 `append()`。**这段代码演示共同事件来源的结构，尚未自动记录插件变化或执行结束原因。**将来补上运行时监听器时，新增事件仍应写入同一条日志，而不应另建一份历史。

## 4.3 请求头给重建过程划出当时的边界

消息历史本身无法描述一份完整请求。系统规则、工具定义、本步说明都可能随时间变化。`build_request()` 先按 `step_id` 找到目标 `request/header`，只读取这条头部之前的事件。**请求头保存一个 Step 当时的输入边界。**

随后代码寻找最近的 `context/checkpoint`。检查点存在时，摘要作为系统消息进入模型视图，检查点之后的事件继续逐条转换为消息。`_message_from()` 只处理用户、助手和工具结果事件，并为工具消息保留工具名称。Python 最小版不记录独立的 Tool Call，也没有在这里再次套用第二章的裁剪；它展示的是从事件顺序恢复当前请求的基本方法。

## 4.4 Trace 和请求继续复用同一份事实

`trace()` 遍历同一批 Event，为每一项生成带 `event_id`、类型和数据的展示对象。**请求重建和 Trace 共享同一份事件事实。**它们面向不同用途，却没有维护另一份执行历史。

完整 DSH 会将 SessionEvent 写入 JSON Lines（JSONL，每行一条 JSON 记录）或 SQLite，并将 Session Log 接入插件运行时。Python 教学版目前保存在内存中，再由教程生成器序列化样本；两者共同强调的是请求与展示要从同一事件流获得依据。
