# Session Log 保存事件并生成其他视图

一个 `messages` 数组可以保存对话内容，但通常缺少解释 Agent 运行所需的信息，例如某个 Step 当时使用的系统规则、工具目录和投影设置。它也难以确定插件的安装时间、工具结果对应的调用，以及 Agent 在某处停止的原因。

DSH 把运行中观察到的内容记录为 Event（事件）。用户输入、Step 开始、请求头、模型回复、工具调用、工具结果、上下文检查点和运行时变化，都写入同一条 Session Log（会话日志），并获得事件类型和递增编号。

## Event 负责记录，Trace 负责展示

日志采用 append-only（只追加）约束：新事件只能加入末尾，已经记录的事件不会就地修改。这项约束保留事件的因果顺序。工具结果位于对应调用之后、下一次请求之前，因此可以确定它如何进入后续上下文。

右侧截取一次工具往返所需的六条事件，用于展示用户消息、第一份请求、模型工具调用、工具结果和第二份请求的顺序。完整实现还记录 Turn、Step、checkpoint（上下文检查点）与运行时事件，全部使用同一条 Session Log。

## 任意一步的请求都能从日志重建

为了还原某个 Step，`build_request()` 先找到对应的 `request/header`。Header（请求头事件）保存当时的系统规则、Tool Schema、本步说明与投影配置。请求头之前的用户、模型和工具事件会按原顺序还原成消息，工具结果继续保留产生它的工具名称。

历史中存在 checkpoint 时，请求构建器用摘要表示检查点覆盖的旧事件，再追加检查点之后的新事件。原始 Event 仍保留在 Session Log 中，checkpoint 只改变当前模型请求的投影。第二章提出的完整记录与模型输入分离由此获得可重建的数据结构。

页面上的 Trace（执行过程视图）也由 Event 生成：事件类型转换为可读标题和说明，原始 payload（事件数据）仍可展开。请求检查、执行时间线和能力变化因此引用同一份记录，无须分别维护可能不一致的副本。

本章重建的是语义一致的统一请求，不保证与模型服务商的原始请求逐字节相同。回放会把 Event 再次转换为 Trace，不会重新调用模型或执行工具。模型的流式分片、网络重试和服务商请求编号没有进入这份最小日志。

当前 Nano DSH 把 Session Log 保存在内存中，可以演示记录、重建和回放，但进程重启后无法恢复。跨进程保存可以把同一组 Event 追加写入 JSON Lines（JSONL，每行一条 JSON 记录）文件或数据库。存储介质的选择不会改变本章的事件结构。

DSH 通过 Event 记录观察结果，由 Session Log 保存顺序，再从同一份记录生成 Request 和 Trace。checkpoint 只改变模型视图，不删除历史事件。这些机制共同回答运行过程如何记录、保存和检查。
