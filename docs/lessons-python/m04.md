# 模型可见即已记录

第三章结束时，插件挂载、工具调用、模型回复都只存在内存里。进程退出后，这些过程全部消失：对话无法恢复，执行过程无法检查，之前发生了什么只能靠记忆。要恢复、要审计、要回放，三个需求指向同一件事：把运行中发生的事实按顺序记下来。这一章回答：DSH 怎样记录一次运行，又怎样从记录里重建请求？

## 4.1 日志按发生顺序追加事件

一个 `messages` 数组可以保存对话内容，但缺少解释 Agent 运行所需的信息：某个 Step 当时使用的系统规则、工具目录和投影设置，插件的安装时间，工具结果对应的调用，Agent 在某处停止的原因。DSH 把运行中观察到的内容记录为 Event（事件）：用户输入、Step 开始、请求头、模型回复、工具调用、工具结果和运行时变化，都写入同一条 Session Log（会话日志），并获得事件类型和递增编号。

日志采用 append-only（只追加）约束：新事件只能加入末尾，已经记录的事件不会就地修改。这项约束保留事件的因果顺序：工具结果位于对应调用之后、下一次请求之前，因此可以确定它如何进入后续上下文。

事件卡展示一次工具往返的六条事件：用户消息、第一次请求头、模型回复、工具调用、工具结果、第二次请求头。按编号依次阅读，就能看到请求、执行与反馈的先后关系。

## 4.2 模型可见即已记录

日志不只是流水账，它是模型请求的唯一来源。完整 DSH 有一条运行时不变量：模型可见即已记录。抵达模型请求的一切都必须能从日志重建。因此，新增一项模型可见的输入，就需要新增一类 SessionEvent。

请求重建的路径如下。`request/header` 保存某个 Step 当时的系统规则、Tool Schema、本步说明与投影配置；`build_request()` 先找到目标 Step 的请求头，再把此前的用户、模型和工具事件按原顺序还原成消息，工具结果继续保留产生它的工具名称。历史中存在 checkpoint（上下文检查点）时，构建器用摘要表示检查点覆盖的旧事件，再追加检查点之后的新事件；原始事件仍保留在日志中。

Nano DSH 为每个 Step 都记录一条完整的 `request/header`，请求因此可以重建。页面上的请求对比、Trace（执行过程视图）和事件卡都从同一份日志生成，各自维护副本只会让它们逐渐不一致。

## 4.3 持久化是完整版的选择

内存日志能演示记录与重建，但进程重启后仍然丢失。完整 DSH 把同一组 Event 追加写入 JSON Lines（JSONL，每行一条 JSON 记录）文件或数据库，重新加载会话时再从持久化记录恢复日志。存储介质的选择不会改变本章的事件结构。

Nano DSH 在一次运行中把事件保存在内存的 `SessionLog` 里，教程生成器把这些事件写入网站使用的 `tutorial-python.json`，页面随后根据这份静态记录重建请求并回放 Trace。这份最小实现保留了事件记录、请求投影和回放共用同一数据源的关系。

边界需要说明：本章重建的是语义一致的统一请求，不保证与模型服务商的原始请求逐字节相同；回放不会重新调用模型或执行工具，模型的流式分片、网络重试和服务商请求编号没有进入这份最小日志。
