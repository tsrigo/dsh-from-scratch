# 让相同前缀尽可能长

第一章的循环每走一步，都会把更多消息带进下一次请求。短任务里，这个做法足够直观；工具返回很长的文本后，模型输入会很快占满上下文窗口。运行时此时要同时保留两份数据：**完整事实用于审查和恢复，当前模型视图用于本次推理。**

DSH 的上下文设计先解决输入可控的问题，再利用稳定的请求顺序争取前缀缓存复用。**先让输入可控，再尽量延长稳定前缀。**Python 教学版把这件事缩为消息投影与四个顶层请求部件的比较；真实缓存命中仍以模型服务返回的数据为准。

`context.py` 定义投影、请求构造和前缀比较函数。它们给出后续代码共同使用的规则：多长的工具结果需要裁剪、请求部件如何排序、两次请求从哪里开始不同。

## 2.1 模型视图可以缩短，完整事实必须保留

让 Agent 回答备忘录内容时，`read_note` 可能返回很长的文本。每个 Step 都携带全文会持续增加输入长度；直接覆盖原结果又会让后续审查失去依据。Python 版因此在构建请求时生成一份投影，只处理模型这次要读取的工具结果，原始 `messages` 列表保持不变。

`project_tool_result()` 只裁剪超出限制的字符串。短结果原样保留；长结果保留开头、结尾和省略字符数。开头帮助模型辨认来源，结尾常含结论、状态或错误信息，省略标记明确说明中间内容没有进入本次视图。

这一段实现将裁剪限制在模型视图中：**当前请求可以变短，调用方持有的完整消息不会被改写。**完整 DSH 会把原始事实写入 Session Log（会话日志），供之后的重建、回放和恢复使用。

## 2.2 请求的排列决定变化落在哪里

裁剪控制单条结果的体积，请求部件的顺序决定新增内容会影响哪里。Python 版 `build_request()` 先放系统规则和工具定义，随后按时间放入投影后的消息历史，最后加入每个 Step 都会变化的 `dynamicContext`。相邻请求从开头比较时，变化慢的内容会留下更长的相同前缀。

**变化慢的内容放在前面，新增内容追加到后面。**这个函数不调用模型服务，也不管理缓存；它负责把当前状态排成统一请求，让调用方和比较函数都能依据同一种顺序理解一次模型调用。工具往返增加消息后，新内容自然位于历史尾部。

## 2.3 用可重复的比较检查结构是否稳定

页面可以说明两次请求共享多少开头，却无法直接得知模型服务的真实缓存命中。`approximate_tokens()` 用字符数给出教学估算，`shared_prefix()` 则按 `system`、`tools`、`messages`、`dynamicContext` 的固定顺序查找第一个不同部件。它不会查询服务端缓存，也不会改变请求。

这份比较比 TypeScript 版更小：它检查四个顶层部件，而不逐项规范化每一段内容。**它仍然能稳定说明变化先落在哪个请求部件中。**当工具、提示词或模型适配器在运行中改变时，稳定部分也会相应变化；完整 DSH 用更细的请求描述与日志重建继续处理这些情况。
