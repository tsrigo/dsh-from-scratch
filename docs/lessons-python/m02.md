# 让相同前缀尽可能长

第一章的循环每走一步，请求里就多一份历史：第二次请求比第一次多出 57 token。任务越长，增长越快，请求最终会超过模型上下文窗口。模型服务按前缀复用 KV Cache（Key-Value Cache，键值缓存）：两份请求开头的相同内容只计算一次。前缀越长，成本越低。这一章回答：怎么让相同前缀尽可能长？

## 2.1 长结果先裁剪，再进请求

让 Agent 回答：备忘录里写了什么？`read_note` 返回一份很长的备忘录。第二次请求共约 264 token，其中这条工具结果约 172 token，其余全部内容合计约 92 token。把这样的全文直接放进请求，几个 Step 就会填满上下文窗口。

Nano DSH 的 `project_tool_result()` 在构建请求时裁剪过长的工具结果：超过 520 字符的结果保留前半和后半各约 260 字符，中间插入省略标记，说明删去了多少字符。裁剪只发生在请求构建阶段，完整结果仍保存在记录里。

裁剪的代价是模型看不到中间内容。选择保留头尾，因为开头用于识别结果内容，结尾常包含结论或错误。完整 DSH 会在 token 压力达到阈值后裁剪过长的工具结果；如果请求仍然过长，再用摘要替换较早的历史。Nano DSH 用固定阈值展示同一条路径。

## 2.2 排列决定前缀从哪里开始变化

请求按变化频率分成三个区。固定区在最前，包含系统规则与 Tool Schema（工具定义及参数规则），只在配置变化时改变。中间是累积区，用户消息、模型回复和工具结果按发生顺序追加，只增不改。最后是本步区，只包含当前 Step 的动态说明，每次请求都会变化。

这个顺序把每次都变的内容放在末尾，把长期不变的内容放在开头，相同前缀因此尽可能长。缓存复用比较的是实际内容及其顺序；语义接近但文本不同的内容会产生不同的缓存键。

请求对比卡展示第二次请求与第一次的差异：相同开头约 57 token，正好是固定区与用户消息；首次变化发生在模型回复，之后是约 172 token 的工具结果。

## 2.3 什么会让前缀提前失效

前缀失效的位置取决于变化发生在哪个区。系统规则改变时，前缀从第一段开始变化；插件安装改变工具目录时，变化位置落在 Tool Schema；普通新消息只影响历史末尾。

历史压缩位于更靠前的位置：摘要可以减少请求长度，也会从摘要插入处改变后续前缀。上下文长度与缓存复用率需要分别评估，页面上展示的是教学估算，实际缓存命中与计费以具体模型服务返回的数据为准。

完整 DSH 通过稳定排列系统提示词和工具定义、按顺序追加历史来保留可复用前缀。Nano DSH 的页面进一步标出相邻请求最早发生变化的位置。
