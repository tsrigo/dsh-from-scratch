# 一次工具往返：Agent Loop 的起点

先看一个具体任务：用户要知道北京当前时间。模型理解问题，却没有实时数据；它需要调用 `get_time`，读取返回值，再给出回答。这个过程把模型、工具和运行时放进同一条执行链，是后续 DSH 机制共同依赖的起点。

许多 Agent Harness 都能完成一次工具调用。DSH 的差异会在后面的运行时组织中逐渐显现：工具、提示词、会话和 Agent Loop 可以由插件组装，执行事实也会进入共同日志。Python 教学版先保留最小循环，后续章节再分别补足这些运行时职责。

`agent.py` 声明 `Llm` 模型协议、`Tool` 数据结构、参数检查函数和 `Agent`。读代码前先确认边界：**模型给出下一步建议，运行时准备输入、校验并执行工具，再保存反馈。**

## 1.1 一次回答为什么会变成多个 Step

模型第一次看到系统规则、`get_time` 的参数说明、用户问题和本步编号。它无法从这些文字得出当前时间，于是返回一次工具调用。运行时执行查询，把结果加入消息历史；下一次请求带着这条新事实再次发给模型。模型返回不含工具调用的普通文本时，这个 Turn 结束。

**Step 是一次模型请求及其触发的工具执行，Turn 可以包含多个 Step。**`validate_arguments()` 先覆盖教程所需的 JSON Schema 子集，`Agent.__init__()` 再固定模型、工具表和最大步数。循环开始后，每一轮都能从同一组依赖出发。

<!-- fill {"index":1} -->

准备完成后，`run()` 才处理用户目标。它把目标写入 `messages`，为每个 Step 组成一份请求，调用模型，并把模型文本写回历史。没有 `tool_calls` 时，当前回复就是最终答案；存在调用时，循环进入工具执行阶段。请求构造、模型回复与停止判断位于同一条控制流中。

## 1.2 工具执行需要一条统一的反馈入口

模型只能给出工具名和参数，无法直接决定执行是否安全或成功。运行时需要查找工具，检查参数是否符合 Schema（参数结构规则），再等待工具函数返回。查询成功、工具名不存在、参数不合法和工具抛出异常，都应回到同一种工具结果消息中。

`run()` 因此将这部分逻辑放进遍历 `tool_calls` 的循环。**所有成功与失败都回到消息历史中的工具结果。**未知工具和参数错误先形成 `error`，正常执行中的异常也会被包装成 `error`；每一种结果都作为 `role: "tool"` 的消息写回。下一次请求能够读取同一种反馈形状，并据此改参数或选择其他动作。

## 1.3 这条循环在 DSH 中处于什么位置

这个最小实现把工具往返变成可检查的程序流程，却仍将工具列表和消息历史直接保存在 `Agent` 中。任务变长后，请求输入会增长；运行能力变动后，构造器会逐渐拥挤；程序结束后，内存里的历史无法支撑回放。

完整 DSH 保留这条执行边界，同时把输入投影、能力组装和会话记录交给独立运行时机制。理解本章的 Step 和 Turn，才能看清这些机制分别接住了循环的哪一部分。
