# 一切运行能力都由插件提供

第一章的 `Agent` 直接拿到工具，第二章把工具排进请求。这样的起点便于理解循环，能力一多，修改会集中到少数构造器和全局状态里：新增工具、替换模型适配器、改变工作区设置，都可能碰到同一片核心代码。

完整 DSH 用 Cordis 组织这类变化。Cordis 是 DSH 使用的 TypeScript 插件运行时：**模型适配器、工具注册表、会话日志和 Agent Loop 都作为插件加入同一棵运行时树。**Python 教学版保留共同的生命周期约束：**每项已登记能力都有 owner（来源插件），安装后可以沿清理路径撤销。**它具体实现 Tool 和 Prompt 的登记，`services` 与 `listeners` 容器则为后续扩展预留。

`runtime.py` 先定义插件协议、带 owner 的 `Contribution`，以及 `Context` 持有的运行时状态。当前 Python 示例还没有 `provide()`、`use()` 或依赖关系 API，因此这一章将重点放在能力的来源、安装和完整退出。

## 3.1 安装一项能力时，先确定它的生命周期

Plugin 是一次安装和卸载的单位。它拿到 `Context` 后，可以在 `setup()` 中登记 Tool 或 Prompt。`Context` 为每个贡献保存值和 owner，并为当前正在安装的插件建立一条独立的 effect 栈。这样，运行时至少能回答当前有哪些工具和提示词，以及它们属于哪次安装。

安装时最容易遗漏的是中途失败的状态。一个插件可能已经登记工具，又在贡献提示词时抛出错误；如果此前的贡献留在 Context 中，之后的状态就无法可信。`mount()` 因此先创建 effect 列表，执行 `setup()`，并将清理动作收集到其中。**安装失败和主动卸载都沿同一条逆序清理路径处理。**

## 3.2 注册能力时，同时记录它如何退出

`effect()` 是这套生命周期的公共入口：它只在插件安装期间可调用，并把一次清理函数放入当前插件的列表。`register_tool()` 将工具与 owner 写进表中，再登记删除该表项的动作；`contribute_prompt()` 同样保存提示词及其删除动作。**注册一项能力时，也同时登记它的清理动作和来源。**

这里的顺序有实际用途。主动卸载时，后注册的清理动作先运行，相关贡献会依次退出；`mount()` 中的 `disposed` 标记还保证返回的卸载函数只生效一次。Python 版没有实现完整 DSH 的 Service 注入与级联依赖，却保留了它们共同依赖的可逆安装边界。

## 3.3 同一条账目覆盖当前示例中的工具和提示词

工具与提示词参数不同，运行时对它们采用相同的登记方式：写入带 owner 的容器，再把删除动作交给 `effect()`。`inspect()` 从这些容器生成当前插件、工具和提示词的快照；`_require_owner()` 则阻止在安装期之外偷偷修改运行时状态。

源码的这一段将贡献登记、状态读取和回滚辅助集中在 `Context` 中。**每个插件都沿同一套规则接入当前 Python 运行时。**后续需要加入 Service、监听器和依赖关系时，也应把它们接到这条 owner 与 effect 生命周期上。

## 3.4 这正是 DSH 与常见 Harness 拉开距离的地方

工具循环和上下文投影在许多 Harness 中都很常见。**DSH 进一步把组成这些机制的能力也放进插件树。**配置描述当前组合，插件生命周期管理贡献的进入和退出，运行时检查工具可以追溯来源和依赖。

Python 教学版只展示其中较小的 Tool 与 Prompt 生命周期，完整 DSH 还包含依赖注入、服务就绪等待、配置层叠和隔离作用域。这个差异是实现范围的差异，不改变核心关系：能力应通过可检查的安装进入运行时，也应通过同一生命周期离开运行时。
