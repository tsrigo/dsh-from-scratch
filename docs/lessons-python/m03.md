# “一切皆插件”指的是统一的能力生命周期

一个 Agent 的能力并不只有 Tool。模型提供方可以是一项 Service，行为规则会贡献 Prompt，运行过程需要 Listener，工具本身还可能依赖别的服务。如果这些对象分别用全局变量注册、再由不同代码负责清理，运行时很快会变成一组难以检查和卸载的隐式状态。

DSH 的做法是把进入运行时的能力都交给 Plugin 安装。这里的“一切”不是说每个对象都必须写成插件类，而是说每一项运行时贡献都能回答两个问题：它由哪个插件带来；移除这个插件时应当怎样撤销。

## Context 是插件共同使用的内核

Plugin 在 `setup()` 中拿到同一个 Context，可以提供 Service、注册 Tool、贡献 Prompt 或订阅 Event。Context 在安装期间记住当前插件的名字，于是每一项注册都会自动带上 owner。一个插件使用另一个插件的 Service 时，Context 还可以记录 consumer、service 与 provider 的关系。这里讨论的是可检查的关系，不是完整的依赖解析器：版本选择、拓扑排序和级联卸载不在 Nano 范围内。

Agent Loop 不需要知道这些能力怎样组装。它只从 Context 读取当前工具目录和编译后的系统 Prompt。插件关系稳定时，模型请求也稳定；一个插件被显式卸载、另一项能力重新挂载后，下一次请求自然得到新的能力快照。Nano 没有实现原子“替换”操作。

## 注册能力时，同时登记撤销动作

只记录 owner 还不够，插件必须能够完整退出。Context 在挂载开始时建立一份 effect 栈；每次注册能力，都同时把对应的清理函数压进栈中。`setup()` 全部成功，挂载才算完成，并返回一个只生效一次的卸载函数。

如果 `setup()` 做到一半抛错，Context 会按相反顺序执行已经登记的清理动作。这使普通失败接近一笔小事务：要么整组能力都出现，要么回到安装前。主动卸载复用同一条回滚路径，反向顺序也保证后注册、可能依赖前项的贡献先退出。

这里还有一个刻意保留的实现边界：Nano 假定 cleanup 本身不会失败，也没有实现完整的依赖事务。生产实现还需要确保部分 cleanup 失败时仍清除挂载状态；本章讲清的是生命周期骨架，不把最小实现包装成完整容器。

这套约束带来三个直接结果。能力有归属，所以运行时可以被检查；安装有撤销路径，所以能力能够先卸载再重新组装；所有贡献共用生命周期，所以正常卸载不会只删掉 Tool，却遗留 Prompt 或 Listener。第五章的运行时自进化并不会另造机制，它只是让 Agent 在受控范围内调用这里已经建立的安装与卸载能力。

因此，“一切皆插件”的实现核心不是一个复杂加载器，而是 Context、owner 和 disposer 三件事：统一注册入口，自动记录来源，每次影响都有撤销方法。插件只是能力边界，真正重要的是边界内的变化可以被看见，也可以被完整收回。
