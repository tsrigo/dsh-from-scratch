# 一切运行能力都由插件提供

第二章的请求里，Tool Schema 和系统规则是组装好的。谁提供这些内容？DSH 的答案只有一个：插件。而且这个答案没有例外：模型适配器、工具注册表、会话日志、Agent Loop 本身都是插件。DSH 的设计里不存在需要打补丁的特权内核，扩展 DSH 的方式是把插件挂载到其他插件旁边。这一章回答：插件如何组装运行能力，又如何安全地拆掉？

## 3.1 Context 连接能力的提供方和使用方

如果工具、服务和提示词分别用全局变量注册，并由不同代码清理，运行时会积累难以检查和卸载的隐式状态。插件方案把每项运行时能力都纳入同一套注册流程。Plugin 在挂载时取得 Context（运行时上下文），随后可以提供 Service（共享服务）、注册 Tool（模型可请求的操作）、贡献 Prompt（行为规则）或订阅 Event（类型化事件）。

Context 在挂载期间记录当前插件名称，为每项注册内容添加 owner（来源插件）。一个插件使用另一个插件的 Service 时，Context 还会记录 consumer（使用方）、service（服务）与 provider（提供方）的关系。这些记录用于检查依赖关系，不处理版本选择、拓扑排序和级联卸载。

能力图卡展示本章样本的归属关系：插件 `clock-core` 提供名为 `clock` 的服务，插件 `clock-tools` 注册工具 `get_time`、贡献提示词 `clock-rule`，并依赖 `clock`。Agent Loop 每次发起模型请求前，从 Context 读取当前工具列表和合并后的系统 Prompt；插件加载或卸载后，下一次请求就会使用更新后的内容。

## 3.2 注册是可逆的副作用

owner 记录只能回答能力来自哪里，卸载还需要撤销方法。Context 在挂载开始时建立 effect 栈，即按顺序保存副作用清理函数的列表。每次注册能力时，对应的清理函数也加入这个列表。`setup()` 全部成功后，Context 才确认挂载完成，并返回一个只生效一次的 disposer（卸载函数）。

调用卸载函数时，Context 按相反顺序执行已经登记的清理函数，同时移除该插件提供的 Service、Tool、Prompt 和 Listener。如果 `setup()` 执行到一半抛出错误，Context 沿同一个 effect 栈回滚，使运行时恢复到安装前的状态。主动卸载与失败回滚共用同一组清理函数。

反向顺序有一个实际理由：后注册的内容可能依赖先注册的内容，先撤销依赖方，再撤销被依赖方。Nano DSH 假定 cleanup（清理函数）能够正常完成，没有实现完整的依赖事务；生产实现还需要确保部分清理失败时仍清除挂载状态。

## 3.3 统一生命周期带来的三个结果

owner 让运行时能够列出能力来源；disposer 让插件可以完整卸载后重新安装；同一组清理函数会同时移除 Tool、Prompt 和 Listener，避免只清理部分贡献。三种运行时能力因此遵循同一套安装、检查和卸载流程。
