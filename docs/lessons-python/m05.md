# Agent 自己装一个工具

第四章的日志能够说明当前发生了什么，却不会自动增加能力。假设任务需要统计一段文本中的单词数量，当前 Context 中没有 `word_count` 工具。继续猜测工具名或反复调用无关工具，只会消耗 Step，也不会缩小能力缺口。

DSH 将这类需要处理成受控的运行时变更：**先查看当前能力和接口，再挂载临时插件，调用新增工具验证结果，任务结束后释放插件。**Python 教学版保留同一条变更路径，动态代码以 Python 的 `compile()` 和 `exec()` 加载；它只适合可信教学样本，代码本身不提供安全沙箱。

`runtime_tools.py` 先定义统一的工具包装和 `runtime_tools_plugin()` 的入口。下面的实现围绕一张定义表展开，因此读者可以分清插件代码已被登记、插件正在运行、插件已经释放这三种状态。

## 5.1 先确认缺少什么，再决定补什么

`cordis_inspect` 返回当前 `Context` 中已挂载插件、工具和提示词的快照。**先确认缺少什么，再决定补什么。**调用方根据这份结果确认 `word_count` 缺失，再决定新插件需要提供怎样的工具。能力图中的基线也很重要：它提供变更前的可比较状态，避免把已有能力误判为缺口。

Runtime Tools 自己也要维护生命周期。它用定义表保存动态插件，并在退出时逆序停止仍在运行的插件、清空定义。与此同时，它注册检查接口和一段提示词，说明何时应先检查、再定义和运行插件。这些准备让一次临时扩展拥有明确入口与收尾。

## 5.2 定义代码和挂载能力是两个时刻

检查确认缺口后，调用方通过 `cordis_define` 提交插件名称、用途和 Python 代码。代码需要定义 `plugin_factory()`，并返回带 `name` 和 `setup(context)` 的插件对象。**定义代码和挂载能力是两个时刻。**函数先用 `compile()` 检查代码，再将定义放进表中；此时工具列表没有变化。`cordis_run` 取回定义，执行代码得到 Plugin，并调用第三章的 `context.mount()`，挂载成功后，新工具才进入当前 Context。

区分这两个时刻有实际用途。定义阶段可以报告代码是否可加载，挂载阶段可以报告插件是否真的改变了运行时；失败时也能准确指出发生在哪一步。`instantiate_plugin()` 使用新的命名空间执行代码，再检查工厂函数和返回对象的必要形状。这里没有权限隔离，因此部署时需要用受限执行环境替代这段教学加载方式。

## 5.3 结果验证和释放让变更形成闭环

插件挂载成功后，`word_count` 出现在工具表中。**它已经可供外层重新组装后续 Agent 请求。**当前 Python `Agent` 在构造器中保存自己的工具表，并不会自动订阅 `Context`；调用方需要从 `context.tools` 读取新工具，再建立或更新 Agent 的工具定义。已经发出的请求保持原样。

外层从 `Context` 取出 `word_count` 并得到 `words: 3`，这才证明新能力已经被挂载并完成一次调用。

验证完成后，`cordis_stop` 执行挂载时取得的卸载函数并保留定义，方便稍后再次运行；`cordis_undefine` 则先停止仍在运行的插件，再删除定义。五个 `cordis_*` 工具共享同一个工具包装，辅助函数负责读取参数和实例化插件，让主体集中表达状态转换。Python 最小版没有自动把定义、挂载和释放事件写入 SessionLog；完整 DSH 应当把这些变化补入共同记录。
