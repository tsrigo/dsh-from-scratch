# 让任务跨过 Turn 继续

第一章的 Turn 在模型不再调用工具时结束。第五章结束时，Agent 刚装好工具又卸掉，Turn 停下来。但任务可能还没完：整理三条发布说明，第一轮收集到两条，还缺一条。Turn 结束不等于任务完成。谁决定再来一轮？这一章回答：Goal 怎样保存任务状态，谁来决定继续或停止。

## 6.1 Goal 保存状态，驱动器做决策

DSH 在 Agent Loop 外增加一个续行函数，并用 Goal 和 Round 保存跨 Turn 的状态。Goal 保存整个任务的目标、当前状态和轮数限制；Round 表示其中一个阶段，例如收集已有信息或补全交付。一个 Round 启动一次普通的 Agent Turn，一个 Turn 又包含若干 Step。Goal、Round、Turn 和 Step 分别回答整个任务是什么、当前推进哪个阶段、这次启动 Agent 要完成什么、模型这一步做了什么。

Nano DSH 用 `run_long_task` 浓缩这套关系。`Goal` 保存 objective（目标内容）、status（状态）、已经启动的轮数、最大轮数和最近一次状态变化的原因；每轮开始时，它从预先定义的阶段说明中取出当前任务，把同一个长期目标与这份阶段说明一起传给 `run_round`。每个 Round 就是一次普通 Turn 加上一条追加的目标消息，前五章的机制原样复用。

## 6.2 下一轮沿用同一个 Session

`run_long_task` 不直接请求模型，也不执行工具。它接收外部传入的 `run_round` 函数，并在每轮开始时调用；调用方在 `run_round` 中使用同一个 Agent、Context 和 Session Log 启动普通的 Agent Turn，前一轮的插件、消息和工具结果因此继续保留，Goal 中的长期目标也不会被某一轮的阶段说明替换。

请求对比卡展示两轮请求的差异。第二份请求共约 50 token，开头约 19 token 与第一份相同，包含长期目标与第一轮的进展记录；之后追加第二轮任务。第二轮因此在已有进展上继续，不需要重建一份对话历史。

## 6.3 每轮结束后检查是否继续

这个 Python 最小实现让 `run_round` 返回一段结果文本。文本包含 `accepted` 时，Goal 状态设置为 completed（已完成）；包含 `blocked` 时，状态设置为 blocked（受阻）；两者都没有出现时继续下一轮。Goal 仍未结束但已经达到轮数边界时，状态设置为 limit_reached（达到上限）。`accepted` 是本轮结果中的验收信号，不是 Goal 的状态名称。

事件卡展示这个最小样本的完整过程：Goal 创建、第一轮启动、第二轮启动、completed 状态写入。与 TypeScript 版本相比，这个实现没有单独的 progressed 字段，无法区分仍需继续和这一轮没有取得进展；生产实现需要补充这项判断，避免重复执行没有效果的轮次。

## 6.4 六章合起来看

把六章叠起来：Agent Loop 管理一次工具往返（第一章），投影控制每次请求的长度与顺序（第二章），插件组装与撤销运行能力（第三章），Session Log 记录并重建一切（第四章），Agent 在执行中补齐能力（第五章），Goal 与 Round 让任务跨过 Turn 继续（第六章）。输入、能力、记录与续行都服务于同一条循环。

第六章增加的是 Agent Loop 外面的任务协调层：Goal 保存跨 Turn 的目标状态，Round 表示一次续行，驱动器在每轮结束后决定是否再启动一个 Turn。当前 Nano DSH 只在同一个进程中连续执行多个 Round，没有实现进程重启后的 Goal 恢复、定时唤醒、后台 Job（任务）或 Subagent（子智能体）。到这里，六章覆盖了 DSH 运行机制的一条完整主线：从一次模型调用，到一次可靠的长程执行。
