# 用 Goal 和 Round 分阶段推进同一个任务

第一章的 Agent Loop 只管理一个 Turn：接收一条本轮任务，反复请求模型并执行工具，直到模型不再调用工具。Turn 结束只表示这一轮交互已经停止，不表示长期目标一定完成。购物车修复任务可以分成诊断、修复、验证提交三个阶段，每个阶段分别启动一个 Turn。

DSH 在 Agent Loop 外增加一个续行函数，并用 Goal 和 Round 保存跨 Turn 的状态。Goal 保存整个任务的目标、当前状态和轮数限制；Round 表示其中一个阶段，例如诊断或验证。一个 Round 可以启动一次普通的 Agent Turn，一个 Turn 又包含若干 Step，每个 Step 对应一次模型请求及其工具结果。Goal、Round、Turn 和 Step 因此分别回答“整个任务是什么”“当前推进哪个阶段”“这次启动 Agent 要完成什么”和“模型这一步做了什么”。

## run_long_task 决定是否启动下一轮

Goal 保存 objective（目标内容）、status（状态）、已经启动的轮数、最大轮数和最近一次状态变化的原因。`run_long_task` 只在状态为 active（进行中）且尚未达到轮数上限时启动下一轮。每轮开始时，它从预先定义的阶段说明中取出当前任务，把同一个长期目标与这份阶段说明一起传给 `run_round`。文件读取、工具调用和结果反馈仍可由前五章的机制处理。

这个 Python 最小实现让 `run_round` 返回一段结果文本。文本包含 `accepted` 时，Goal 状态设置为 completed（已完成）；包含 `blocked` 时，状态设置为 blocked（受阻）；两者都没有出现时继续下一轮。Goal 仍未结束但已经达到轮数边界时，状态设置为 limit_reached（达到上限）。`accepted` 是本轮结果中的验收信号，不是 Goal 的状态名称。

## 下一轮沿用同一个目标和已有记录

`run_long_task` 不直接请求模型，也不执行工具。它接收一个外部传入的 `run_round` 函数，并在每轮开始时调用这个函数。调用方可以在 `run_round` 中使用同一个 Agent、Context 和 Session Log 启动普通的 Agent Turn，让前一轮的插件、消息和工具结果继续保留。Goal 中的长期目标也不会被某一轮的阶段说明替换。

右侧比较两份模型请求。第二份请求先保留长期目标和第一轮的进展记录 `已找到两项，仍缺一项`，然后追加第二轮任务。这个顺序说明第二轮不是从空白状态重新开始，而是在已有消息和工具结果后继续处理同一个 Goal。

教程中的 Goal 事件记录外层续行状态：Goal 创建、每次 Round 启动，以及最终的 completed。每轮具体执行了哪些工具、取得了什么结果，则保存在请求历史和对应的 Turn、Step 事件中。前者解释为什么继续或停止，后者记录 Agent 实际完成了什么。

## 续行需要明确的停止条件

续行函数需要明确的停止条件，不能无限启动新的 Turn。这个 Python 最小实现识别完成、受阻和轮数上限三类结果，并把最终状态和原因保存在 Goal 中。与 TypeScript 版本相比，它没有单独的 `progressed` 字段，因此无法区分“仍需继续”和“这一轮没有取得进展”；生产实现需要补充这项判断，避免重复执行没有效果的轮次。

当前 Nano DSH 只在同一个进程中连续执行多个 Round。它没有实现进程重启后的 Goal 恢复、定时唤醒、后台 Job（任务）或 Subagent（子智能体）。如果任务需要暂停后再恢复，还要把 Goal 与 Session Log 保存到持久化存储中，并由调度器重新启动任务。

第六章增加的是 Agent Loop 外面的任务协调层。它保存长期目标和轮数状态，为每个 Round 生成明确的阶段说明，并根据返回结果决定是否继续。Python 最小实现处理完成、受阻和轮数上限；调用方负责在每个 Round 中沿用已有的 Agent 状态和执行记录。
