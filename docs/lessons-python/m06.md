# 让任务跨过 Turn 继续

第五章可以在任务中补齐工具，当前模型停止调用工具时，一个 Turn 仍会结束。任务是否完成需要另一层判断。整理三条发布说明时，第一轮可能只收集到两条；模型暂时给出回复，目标依然处于进行中。

DSH 将长期目标放在 Agent Loop 外管理。**Goal 决定跨轮任务是否继续，Turn 和 Step 继续承担模型请求与工具执行。**Goal 保存跨轮状态，Round 代表一次新的推进尝试。Python 教学版用较小的 `Goal` 数据类和 `run_long_task()` 展示这条边界；它根据外部回调返回的文本更新状态。

`scenario.py` 先定义 Goal 状态和 `run_round` 回调类型，再给出 `Goal` 与每轮任务说明。它不持有具体 Agent、Context 或 Session Log，这些对象由调用方在每轮中决定是否复用。这个边界让长程协调只做它需要做的事：决定是否再启动一次普通 Turn。

## 6.1 Goal 需要保存能跨轮检查的状态

`Goal` 把目标文本、最大轮数、已经开始的轮数、状态和原因放在一个对象中。`ROUND_INSTRUCTIONS` 则预先定义收集、实施和验证三个阶段说明。**Goal 保存跨轮状态，Round 只描述当前推进的阶段。**外层可以在每轮后读取统一状态，调用方也可以据此决定如何记录或展示任务。

与 TypeScript 版不同，Python 最小实现没有在创建 Goal 时自动写入 `goal/created` 事件，也没有持久化恢复流程。这个省略让代码聚焦在续行判断，同时也指出完整 DSH 需要补上的记录边界。

## 6.2 下一轮仍然调用普通 Agent Loop

Goal 处于 `active` 且未达到轮数上限时，`run_long_task()` 读取当前阶段说明，递增轮数，并调用外部 `run_round`。回调收到同一个长期目标和本轮说明，可以将这一轮交给与前一轮相同的 Agent、Context、工作区和 Session Log；前几章保存的消息、工具结果和插件变化因而仍然可用。

这一层没有复制第一章的工具循环。**Goal 可以启动新的 Turn，却不重写 Agent Loop。**它只负责为下一次 Turn 提供阶段边界，普通 Agent Loop 继续处理模型请求、工具调用和反馈。两层循环分开后，模型停止工具调用与 Goal 是否继续推进可以独立判断。`scenario.py` 本身不构造模型请求，因此真正的消息历史仍属于 `run_round` 的调用方。

## 6.3 续行要依据可观察的结果

Python 版 `run_round` 返回一段结果文本。文本包含 `accepted` 时，Goal 变为 `completed`；包含 `blocked` 时，Goal 变为 `blocked`；其余情况下，循环继续到下一轮或到达上限后变为 `limit_reached`。这些出口都写在一个循环中，状态和原因一起更新。

**这个版本能够表达完成、受阻和上限，却无法区分没有进展与仍需继续。**函数返回的 `Goal` 是这里可直接检查的结果；它不会自行创建 Session Event。TypeScript 版使用结构化 `RoundResult` 的 `progressed`、`completed` 与 `blockedReason`，并把状态变化写入 Session Log。生产实现应采用这类可观察的结果，而不是依赖文本包含某个词。

## 6.4 六章放回同一条 DSH 运行时主线

一次 Step 先在 Agent Loop 中完成模型与工具的往返；上下文层决定该 Step 能看到哪些信息；插件运行时决定当前有哪些能力；Session Log 将输入、动作和能力变化保存为共同事实；Runtime Tools 在任务中补齐能力；Goal 和 Round 则在一个 Turn 结束后判断任务是否需要继续。

Python 教学版保留了这条主线的最小接口，并明确留下了 Service 依赖、自动会话记录、结构化轮次结果和持久化等扩展点。完整 DSH 在这些接口之上增加配置层、权限、沙箱和更多运行时提供方。
