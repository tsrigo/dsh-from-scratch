# 长程任务需要在 Agent Loop 外再保存一层状态

第一章的 Agent Loop 解决的是一个 Turn 内如何行动。模型不再调用工具，这个 Turn 就会结束；但“这一轮可以停了”并不总等于“整个目标已经完成”。研究、迁移或多阶段交付往往需要分段推进，甚至要在一次自然停顿后再次唤起 Agent。

DSH 因而在 Agent Loop 外增加 Goal 与 Round。Goal 保存相对稳定的目标和整体状态；Round 表示为这个目标发起的一次阶段性推进；Round 内部仍然运行普通 Agent Turn，而 Turn 又由若干 Step 组成。四个层级解决不同尺度的问题，不能混为一个无限循环。

## 外循环只负责决定是否再开一轮

Goal 至少保存 objective、status、已经开始的轮数、最大轮数和最近一次状态理由。协调器只在状态仍为 active 时继续。每轮开始前先写下 Round 编号与阶段说明，再调用内层 Agent；内层怎样读文件、调用工具和形成反馈，仍由前五章的机制负责。

协调器依据每轮返回的结果决定下一步：结果已经满足目标就标记 completed，明确受阻就标记 blocked；否则可以继续到下一轮，并最终在轮数边界标记 limit_reached。

## 续行依赖共享状态，而不是重新提问

续行函数本身只接收一个 `run_round` 回调，并不强制回调一定启动 Agent。在本教程的组合层里，这个回调复用同一个 Goal、运行时 Context 和 Session Log，再启动普通 Agent Turn。目标不会被上一轮的临时措辞替换，前一轮产生的消息和工具结果也继续可见。

右侧先比较两份请求：第二份仍保留第一轮的目标与“已找到两项，仍缺一项”，然后才追加第二轮的任务。这段连续历史说明续行不是重新提问，而是带着已经取得的进展继续。

外层事件只记录续行函数真正观察到的边界：Goal 创建、两次 Round 启动，以及最终 completed。第一轮的具体进展属于请求历史；Goal 事件负责说明协调器为什么停止，两者各自保存自己知道的事实。

## 能继续，不等于必须一直继续

长程运行最危险的失败模式不是停得早，而是没有进展仍反复消耗资源。因此，只要某轮没有可观察进展、返回阻塞原因、达到最大轮数或已经完成，协调器都应当停止，并把原因写回 Goal 与 Session Log。是否继续是一项有证据、有上限的决定。

当前 Nano DSH 在单个进程中演示跨 Round 续行，没有实现进程重启后的 Goal 恢复、定时唤醒、后台 Job 或 Subagent。要跨越这些边界，还需要把 Goal 与 Session Log 持久化，并由调度器重新唤醒；那是建立在本章状态机之上的下一层能力。

所以 DSH 持续完成长程任务，并不是让一次 Agent Loop 永不停止，而是保存目标与进展，在每个有界 Round 后重新判断：完成就交付，受阻就说明原因，有进展且仍未完成才继续。
